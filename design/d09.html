Design a ticket flash sale

50 thousand seats, 2 million fans, all clicking at 10:00:00. Sell every seat exactly once, stay up, and be fair.

The ask

A huge concert goes on sale at a fixed time. Demand is 40 times the supply and almost all of it arrives in the first minute. The system must not crash, must never sell the same seat twice, and should feel fair to fans.

Pin down the requirements

What it must do

  • Browse the event and see seats or sections.
  • Hold seats for a few minutes while paying.
  • Pay and get tickets.
  • Release held seats if payment does not finish in time.

How well it must do it

  • Never oversell. Strong consistency on inventory.
  • Survive a 100 times traffic spike at a known time.
  • Fair order for fans, block bots.

Out of scope, say it out loud

  • Resale market, dynamic pricing.

Do the math

2 million fans arrive within 2 minutes. Each refreshes or clicks about 5 times a minute.

Key point

Most requests must never touch the inventory database. A waiting room controls how many people reach the booking flow at once.

The API

GET  /v1/events/{id}                  cached static page
POST /v1/queue/{event_id}/join        -> queue token, position
GET  /v1/queue/{event_id}/status      -> position, or an access token when it is your turn
POST /v1/events/{id}/holds            { section, qty } with access token -> hold_id, expires_at
POST /v1/holds/{hold_id}/purchase     { payment, idempotency_key }

The data model

StoreHolds
seats, SQLseat id, event id, status available, held or sold, hold expiry, version
holdshold id, user, seats, expires at
ordersorder id, user, seats, payment status
queue, Redissorted set of queue tokens by join time

The big picture

  1. CDN serves the event page and seat map images. Seat availability is shown as rough sections, updated every few seconds, not live per seat.
  2. Waiting room with a queue in Redis issues signed access tokens at a controlled rate.
  3. Booking service holds seats with conditional updates or row locks in a SQL database.
  4. Hold expiry job releases unpaid holds.
  5. Payments with idempotency keys, see design 10.
  6. Pre scaling. Since the time is known, scale servers and caches up before 10:00.

Deep dives

Never oversell

Use a conditional update, only change a seat if it is still available, or a row lock in a transaction. Optimistic version numbers also work. Never check then write in two separate steps.

General admission tickets

With no seat numbers, keep a counter of tickets left. Decrement atomically, UPDATE ... SET left = left - 2 WHERE left >= 2, or use a Redis counter as a fast gate followed by the database as truth.

Fairness

Randomize everyone who arrived before the start, then first come after. Limit tickets per account and card. Bot detection at the edge.

Hot rows

Every request touching one counter row creates lock contention. Split inventory by section, so each section is its own row and requests spread out.

Honest status

Tell people quickly when it is sold out. Thousands of fans refreshing a sold out page is load you can avoid with a cached sold out page.

Trade-offs you must name

ChoiceGood atCosts you
Waiting roomProtects the system, fair.Fans wait, the experience must be clear and honest.

Optimistic versionsNo locks held.Many retries when contention is high.

Security and abuse

Flash sales attract bots.

  • Use a waiting room, per account limits and bot detection.
  • Require login and MFA for high value drops.
  • Make purchase calls idempotent so retries do not double charge, and so bots cannot reserve the same item twice.
