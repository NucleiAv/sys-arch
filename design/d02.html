Design a chat app

Two people or a group send messages that arrive instantly, in order, are never lost, and show sent, delivered and read ticks. Like WhatsApp or Messenger.

The ask

Users send text messages one to one and in groups. Messages should arrive in under a second when the other person is online, wait safely when they are offline, and show ticks for delivered and read. Users have several devices.

Pin down the requirements

What it must do

  • One to one and group chats, groups up to 500 people.
  • Online and last seen status.
  • Sent, delivered and read receipts.
  • Message history on every device.
  • Push notifications when offline.

How well it must do it

  • Delivery under 500 ms when both are online.
  • Never lose a message once the sender sees one tick.
  • Messages in a chat appear in the same order for everyone.
  • Highly available, chat is used all day.

Out of scope, say it out loud

  • Voice and video calls, end to end encryption details, media editing.

Do the math

500 million daily users, each sending 40 messages a day. Messages average 100 bytes plus metadata, call it 200 bytes.

Key point

Hundreds of thousands of writes a second and petabytes of data point to a wide column store partitioned by chat. And hundreds of millions of open connections point to a dedicated connection layer.

The API

WebSocket wss://chat.example.com/ws   (one per device, kept open)
  client sends  { "type":"send", "chat_id":"c9", "client_msg_id":"uuid", "text":"hi" }
  server sends  { "type":"ack", "client_msg_id":"uuid", "msg_id":"18273", "ts":... }
  server sends  { "type":"message", "chat_id":"c9", "msg_id":"18274", "from":"u2", "text":"hey" }
  client sends  { "type":"read", "chat_id":"c9", "up_to":"18274" }

GET /v1/chats/{chat_id}/messages?before=18274&limit=50 (history, REST) ```

The data model

Messages are written once and read by chat in time order. A wide column store like Cassandra or ScyllaDB fits well. Discord and many chat apps use exactly this shape.

The big picture

  1. Connection servers hold millions of WebSocket connections each. They are thin, they just move bytes.
  2. A presence registry in Redis maps each online device to its connection server.
  3. The chat service assigns ids, writes to the store, fans out to members' connection servers, and triggers push notifications.
  4. A message store partitioned by chat_id keeps history.
  5. Devices sync on reconnect by asking for messages after the last id they have.

Deep dives

Ordering

Give each message a per chat increasing id, from the chat's partition leader or a Snowflake style id, lesson 15. Clients sort by it. Order across different chats does not matter.

Exactly once feel

Delivery is at least once. The client message id lets the server drop duplicates on retry, and the receiver drops ids it already has.

Groups

For a 500 member group, the chat service looks up members and fans out to each member's connection server. For huge broadcast channels, switch to members pulling recent messages instead of pushing to everyone.

Multiple devices

Each device is its own connection and keeps its own last synced id. Read receipts are stored per user, so reading on the laptop clears the phone.

Presence at scale

Clients send a heartbeat every 30 seconds. Presence is updated in Redis with a TTL, and friends get updates lazily, when they open a chat, rather than a flood of online and offline events.

Connection server failure

If one dies, its phones reconnect to another within seconds and sync from their last id. No message is lost because the store is the truth.
