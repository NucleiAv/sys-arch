Design a link shortener

Turn a long web address into a short one like sho.rt/aZ3k9, and send anyone who clicks it to the right place, fast, billions of times.

The ask

People paste a long link and get a short one back. When anyone opens the short link, they are sent to the long one. Think of services like bit.ly.

It looks tiny, which is why it is the most common first design question. The interesting parts are making short codes that never clash, and serving a huge number of clicks fast.

Pin down the requirements

What it must do

  • Create a short link from a long URL.
  • Opening the short link redirects to the long URL.
  • Optional custom alias, like sho.rt/summer-sale.
  • Links can expire.

How well it must do it

  • Redirects are very fast, under 50 ms at p99.
  • Very high availability for redirects. A dead link breaks other people's websites.
  • Short codes must never point to the wrong place.

Out of scope, say it out loud

  • Click analytics dashboards, user accounts beyond a simple API key.

Do the math

Assume 100 million new links a month and 100 clicks for every link created.

Key point

Reads beat writes 100 to 1. That one fact shapes the design. Cache hard, and keep the redirect path as short as possible.

The API

POST /api/v1/links
  body  { "long_url": "...", "alias": "summer-sale", "expires_at": "..." }
  reply 201 { "short_url": "https://sho.rt/aZ3k9" }

GET /{code} reply 301 or 302 with Location: <long_url> reply 404 if missing or expired ```

301 or 302? A 301, moved permanently, lets browsers cache the redirect, which saves load but means you never see repeat clicks. A 302, found, sends every click through you, which costs more but lets you count clicks and change the target. Many shorteners use 302 for analytics.

The data model

The only lookup is by code, so a key value store such as DynamoDB or Cassandra fits well. A single Postgres with a primary key also works for years at this size.

The big picture

  1. A load balancer in front of stateless link service servers in several zones.
  2. Codes come from a counter handed out in blocks, encoded in base 62.
  3. Links are stored in a replicated key value store keyed by code.
  4. A Redis cache holds hot codes. With 100 to 1 reads, the cache serves most redirects.
  5. A CDN or edge can even cache 301 redirects for the most popular links.
  6. Click events go to a queue for analytics, never slowing the redirect.

Deep dives

How to make short codes

Hash the URL with MD5 and take 7 characters. Simple, but two URLs can clash, so you must check and retry. Counter plus base 62. Every number is unique, so no clash checks, but codes are guessable in order, which you can hide by shuffling the number first. Random codes. Generate 7 random characters and insert only if absent. Most designs pick counter blocks or random codes.

Custom aliases

Check the alias is free with a conditional insert, so two people cannot grab it at once. Keep a block list for offensive or reserved words like api and login.

Scaling redirects

A cache in front absorbs most reads. Links are almost never edited, so cache them for a long time. If a key value store is the main store, it scales out by code.

Abuse

Shorteners are used to hide phishing links. Check new URLs against a safe browsing list, rate limit creation per key, and let people report links.

Expiry

Store expires_at and check it on read. A background job removes expired rows later. Never reuse a code from an expired link, it may still be printed somewhere.

Security and abuse

Link shorteners are popular with spammers and phishers.

  • Scan target URLs against safe browsing lists and block known bad domains.
  • Rate limit link creation per user and per IP.
  • Show a preview page for flagged links.
  • Do not make short codes sequential, or people can list every link. Private links need random codes and access checks.
