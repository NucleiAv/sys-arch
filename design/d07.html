Design file storage and sync

Save a file on your laptop and it appears on your phone a moment later. Edit it offline and the changes merge when you reconnect. Like Dropbox or Google Drive.

The askPin down the requirementsDo the mathThe APIThe data modelWatch it workThe big pictureDeep divesTrade-offs you must nameSecurity and abusePractice. Your turnPractice. Follow-up questionsGo deeper

The ask

Users keep files in a folder that syncs across all their devices. Files can be large. Changes should sync quickly, using little bandwidth, and nothing should ever be lost, even with conflicting edits.

Pin down the requirements

What it must do

  • Upload, download, delete and rename files and folders.
  • Automatic sync across a user's devices.
  • Share files with other users.
  • File version history.

How well it must do it

  • Never lose a file. Very high durability.
  • Sync changes in seconds.
  • Upload only what changed in big files.
  • Works offline and catches up later.

Out of scope, say it out loud

  • Real time co editing inside a document, see design 13.

Do the math

50 million users, average 10 GB stored, 2 million files changed an hour.

Key point

Storage is enormous and many users store the same files. Splitting files into chunks and storing each chunk once, deduplication, saves a lot.

The API

POST /v1/files/commit     { path, chunk_hashes: [...], base_version }  -> missing chunks or new version
PUT  {upload_url}/chunk/{hash}   upload a missing chunk
GET  /v1/changes?cursor=...      long poll for changes since cursor
GET  /v1/files/{id}/versions

The data model

StoreHolds
file metadata, SQLfile id, owner, path, current version
versionsfile id, version, ordered list of chunk hashes, author, time
chunkscontent hash to object storage location, reference count
change logper user ordered list of changes, for sync cursors

Metadata needs transactions, a rename or move touches many rows, so a relational database sharded by user or namespace fits. Chunks live in object storage, named by their hash.

The big picture

  1. Client watches the folder, chunks files, hashes chunks, and keeps a local database of what it has synced.
  2. Metadata service with a sharded SQL database for files, versions and the change log.
  3. Chunk storage in object storage, content addressed, each chunk stored once.
  4. Notification service keeps long polls or WebSockets open and tells devices when to sync.
  5. Sharing adds access lists on folders and makes shared changes appear in each member's change log.

Deep dives

Chunking and deduplication

Fixed size chunks are simple. Content defined chunking finds chunk edges from the data itself, so inserting a byte at the start does not shift every chunk. Identical chunks across all users are stored once.

Conflicts

If the phone edits version 11 offline while the laptop commits version 12, the phone's commit fails because its base version is old. The client saves its copy as report (conflicted copy).docx so nothing is lost, and the user decides.

Sync cursor

Each device remembers a cursor into its user's change log. On reconnect it asks for all changes since the cursor, applies them in order, and moves the cursor.

Durability

Object storage keeps several copies across zones. Chunks are deleted only when no version references them, using reference counts and a delayed garbage collector, so a bug cannot delete live data instantly.

Security

Encrypt chunks at rest. Hash based dedup across users can leak whether someone has a known file, so some services dedup only within one user.

Trade-offs you must name

ChoiceGood atCosts you
Fixed size chunksSimple and fast.An insert near the start changes every later chunk.
Content defined chunksSmall edits change few chunks.More CPU on the client.
Global dedupBig storage savings.Privacy risk, cross user reference counting.
Conflicted copiesNever loses data, simple.User must merge by hand.

Security and abuse

File sync holds people's most private files.

  • Encrypt files at rest and in transit. Consider client side encryption for sensitive users.
  • Check sharing permissions on every download. Shared links should expire and allow revocation.
  • Keep file versions so ransomware on one laptop does not destroy the cloud copy.
  • Scan for malware so sync does not spread it to every device.
