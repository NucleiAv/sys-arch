Design a secure platform for autonomous AI agents

A company wants many AI agents that run on their own. They triage support tickets, fix failed deployments, reconcile invoices and answer suppliers, day and night. Design the shared platform that runs them, connects them to real systems, and keeps them from doing harm when they are wrong or tricked.

The ask

Teams should be able to define an agent, give it a goal, tools and triggers, and let it run without a person watching every step. The platform must make every agent observable, limited, reversible where possible, and safe even when an agent reads hostile content. Security, audit and finance teams must be able to see and stop anything.

Pin down the requirements

What it must do

  • Register agents with an owner, a purpose, tools, triggers and limits.
  • Start runs from events, schedules or people, and run them for minutes or hours.
  • Connect agents to tools and data through a governed tool layer.
  • Pause runs for human approval of risky actions.
  • Show a full trace of every run, and stop any agent at once.

How well it must do it

  • A tricked agent must not be able to leak data or take high impact actions alone.
  • Runs survive crashes and never repeat side effects.
  • Cost per run is bounded and visible per team.
  • 50,000 runs a day, peaks of 200 runs at once.

Out of scope, say it out loud

  • Training models, the agents' business logic, the chat user interface.

Do the math

50,000 runs a day. A run averages 12 model calls of 4,000 input and 500 output tokens. Input costs 3 dollars and output 15 dollars per million tokens. Each run makes about 6 tool calls.

Key point

The load is modest. The design is driven by control, trust boundaries and evidence, like the medical device platform in d17, not by raw scale.

The big picture

  1. Agent registry. Every agent is defined as code, reviewed, versioned and risk rated, with an owner. No unregistered agent can run.
  2. Triggers. Events, schedules or people start runs through a queue, with idempotency keys so one event starts one run.
  3. Agent runtime with durable execution. State is saved after every step, so crashes resume without repeating side effects. Limits on steps, time, tokens and money are enforced here, with a loop detector.
  4. Model gateway, lesson 8.2. Provider keys, routing, budgets, fallbacks, input and output guardrails.
  5. Policy engine. Every proposed tool call is checked against rules written as code, such as allowed tools, amount limits, allowed recipients, data scope and time of day. Decisions are allow, deny or require approval.
  6. Tool gateway. The only path from agents to real systems. It exchanges the run's identity for short lived, narrowly scoped credentials, calls internal APIs or reviewed MCP servers, and enforces rate limits.
  7. Approval service. Paused actions with full context go to the right people, with timeouts and escalation.
  8. Sandboxes for any code execution, with no secrets and an egress allow list.
  9. Untrusted content handling. External text is labelled and, for high risk agents, read only by a quarantined model without tools, following the dual LLM idea.
  10. Observability and control. Traces of every step, dashboards for cost and denials, alerts on unusual behaviour, and a kill switch per agent, per team or for all agents.

Deep dives

Policy as code

Rules live in a policy language or plain code, are reviewed like code and are tested with unit tests. Example, refunds.create allowed if amount <= 50 and order belongs to the ticket's customer, otherwise require approval from role support_lead. Policies apply per agent version.

Identity for agents

Each run gets its own short lived credential, derived from the agent's registered identity and the triggering event, for example with OAuth token exchange. Downstream systems see which agent and which run acted, never a shared admin account.

Durable execution and side effects

The runtime records each step before and after a tool call. If the worker dies, another resumes from the log. Tool calls carry idempotency keys built from the run id and step number, so a replay never refunds twice.

Approval fatigue

If people must approve everything, they stop reading. Route only high impact or unusual actions to people, show a clear diff of what will happen, measure how often reviewers override, and automate a class of actions only after a long record of correct proposals.

Rolling out a new agent

Start in shadow mode, where the agent proposes actions but nothing runs. Then read only, then low risk writes with approval, then automatic low risk writes. Each step needs passing evals, red team cases and an owner's sign off, lessons 8.5 and 6.11.

Memory isolation

An agent's memory can be poisoned by a hostile document, and can leak across tenants. Scope memory per tenant and per agent, store where each memory came from, and let owners review and delete it.

Trade-offs you must name

ChoiceGood atCosts you
Central platformOne set of strong controls, audit and cost tracking.Teams must adopt it, the platform team becomes a bottleneck.
Each team builds its own agentsFast for the first team.Inconsistent security, no shared audit, repeated work.
Strict policies and approvalsVery low risk.Slower, less autonomy, approval fatigue.
Quarantined reading of untrusted contentStrong defence against injection.More model calls, less flexible agents.

Security and abuse

This whole design is a security design. Threat model it with STRIDE and the OWASP LLM Top 10. The highest risks are prompt injection through tickets and emails, excessive agency through tools, data leaks through outbound channels, poisoned memory, compromised MCP servers, and runaway cost. Govern it with an AI inventory entry per agent, owners, risk ratings, and evidence from evals, traces and approvals, as in lesson 8.8.
