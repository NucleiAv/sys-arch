Design a peer to peer file sharing network

Millions of computers share big files with each other, with no central server holding the data. Like BitTorrent, IPFS or the peer to peer part of game and system updates.

The ask

Users share large files, from 100 MB to 50 GB. Anyone with a short link can download a file from other users who already have it. The system must work with no central file server, keep working when many peers leave, and make sure nobody receives a corrupted or fake file.

Pin down the requirements

What it must do

  • Publish a file and get a short link, a magnet link with the file's hash.
  • Find peers who have the file, with or without a central tracker.
  • Download pieces from many peers at once and upload to others.
  • Check every piece so corrupted or fake data is rejected.

How well it must do it

  • Scale to millions of peers and files with no single point of failure.
  • Fast downloads that grow as more people share.
  • Work behind home routers that use NAT.
  • Resist bad peers that lie or send junk.

Out of scope, say it out loud

  • Payments, search for content by name, legal and licensing checks.

Do the math

A popular 2 GB file is downloaded by 1 million people in its first day. Pieces are 1 MB each.

Key point

With peer to peer, every downloader also uploads. Capacity grows with demand instead of being crushed by it.

The API

magnet:?xt=urn:btih:<info hash>&dn=ubuntu.iso      the short link
Peer wire messages over TCP or uTP
  handshake(info_hash, peer_id)
  bitfield(pieces I have)
  interested / not_interested
  choke / unchoke
  request(piece, offset, length)       blocks of 16 KB
  piece(piece, offset, data)
  have(piece)                          tell peers about a new piece
DHT messages over UDP
  ping, find_node(target_id), get_peers(info_hash), announce_peer(info_hash, port)

The data model

ItemWhereHolds
MetadataFetched from peers by info hashFile names, sizes, piece size, list of piece hashes
Info hashInside the linkHash of the metadata, so the metadata itself can be checked
Routing tableEach peer, in memoryAbout 160 buckets of up to 8 contacts, ordered by XOR distance
Peer listDHT nodes closest to the info hashAddresses of peers that have the file, with a timeout
Piece bitmapEach peerWhich pieces it has

Everything is content addressed. You name data by its hash, so anyone can check that what they got is what they asked for.

The big picture

  1. Content addressing. A file is described by metadata, and the metadata's hash is the file's name, the info hash.
  2. Peer discovery. A tracker server is simplest. A DHT removes the central point. Peers also swap peer lists with each other, called peer exchange.
  3. Piece transfer. Files are split into pieces, pieces into 16 KB blocks. Each piece has a hash in the metadata.
  4. Choosing pieces. Rarest first, so no piece disappears when its last owner leaves.
  5. Fairness. Each peer uploads to the few peers that give it the best speed, and every 30 seconds tries one random peer, an optimistic unchoke, so newcomers get a start.
  6. NAT traversal. Home routers block incoming connections. Peers use UPnP to open ports, hole punching with help from a third peer, or relays as a last resort.

Deep dives

How Kademlia finds things

Every node and every file key has a 160 bit id. Distance is the XOR of two ids, read as a number. Each node keeps contacts in buckets by distance, with many near itself and a few far away. A lookup asks the closest known nodes for even closer ones, a few in parallel. Each step roughly halves the distance, so a lookup takes about log2 of the number of nodes steps, around 20 for a million nodes, and usually fewer in practice.

Churn

Peers come and go all the time. Peer lists in the DHT expire unless peers announce again. Data lives on the k closest nodes, often 8, so a few leaving does not lose it. Rarest first keeps every piece spread out.

Why rarest first

If everyone grabbed piece 1 first, the last pieces would be held by only the first seeder. When that seeder leaves, nobody can finish. Rarest first makes rare pieces common quickly.

Tracker or DHT

A tracker is simple and fast and gives stats, but it is a single point of failure and an easy target to shut down. A DHT has no center but is slower to start and harder to secure. Many clients use both.

Hybrid peer to peer

Many companies use peer to peer only to save bandwidth, with a central server as the source of truth. Windows Delivery Optimization and some game launchers share updates between nearby machines, while signatures come from the vendor.

Trade-offs you must name

ChoiceGood atCosts you
Pure peer to peerNo server costs, scales with users, no single point of failure.Slow start for rare files, hard to control, hard to secure.
Central serverSimple, fast, full control.Bandwidth costs grow with every user.
Small piecesShare sooner, less lost on a bad piece.Bigger metadata, more hashes to check.
DHT discoveryNo central tracker to fail or block.Open to Sybil and poisoning attacks.

Security and abuse

Peer to peer networks are open to anyone, so assume some peers are hostile.

  • Integrity. Hash every piece and check the metadata against the info hash. This stops corrupted and fake data.
  • Authenticity. A hash proves the file matches the link, not that the link is from a trusted source. For software updates, sign the metadata with the publisher's key.
  • Sybil attacks. One attacker makes thousands of fake nodes to control parts of the DHT. Defenses include tying node ids to IP addresses, keeping long lived contacts and querying several paths.
  • Eclipse attacks. Bad nodes surround a victim so all its contacts are attackers. Keep diverse contacts and prefer peers that stay online a long time.
  • Privacy. Your IP address is visible to everyone in the swarm. Encryption of the peer link hides content from your network, but not your IP from peers.
  • Malware. A correct hash of a bad file is still a bad file. Users must trust the source of the link.
