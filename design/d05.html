Design search autocomplete

As you type "how to", the box suggests "how to tie a tie". Suggestions must appear in under 100 ms on every keystroke, for billions of searches.

The askPin down the requirementsDo the mathThe APIThe data modelWatch it workThe big pictureDeep divesTrade-offs you must nameSecurity and abusePractice. Your turnPractice. Follow-up questionsGo deeper

The ask

Show the top 5 suggestions for whatever prefix the user has typed so far, ranked by popularity. Every keystroke is a request, so this is one of the most read heavy systems there is.

Pin down the requirements

What it must do

  • Return the top 5 completions for a prefix.
  • Rank by how often each query is searched, with recent trends counting more.
  • Filter out offensive suggestions.

How well it must do it

  • Under 100 ms end to end, so the backend gets about 20 to 50 ms.
  • Huge read volume, highly available.
  • Suggestions can be minutes or hours stale.

Out of scope, say it out loud

  • Spelling correction, personalized suggestions, the search results page itself.

Do the math

100 million daily users, 10 searches each, about 6 keystrokes per search sent to the server.

Key point

Reads are enormous and freshness can lag. So precompute the answers for every popular prefix offline, and serve them from memory and caches.

The API

GET /v1/suggest?q=how%20to&limit=5
  reply { "prefix": "how to", "suggestions": ["how to tie a tie", "how to screenshot", ...] }

The browser waits about 50 ms after a keystroke before sending, called debouncing, and cancels older requests.

The data model

The trie

A trie is a tree where each step down adds one letter. The path h, o, w spells "how". Each node can store the top 5 completions under it, computed ahead of time, so answering a prefix is just walking down a few letters and reading the list. No searching at query time.

Watch it work

The big picture

  1. Browser debounces keystrokes and caches recent answers itself.
  2. CDN or edge cache answers popular prefixes with a short TTL.
  3. Suggest servers hold the trie fully in memory. They are read only and stateless, so they scale out easily.
  4. Trie sharding by first letters if the trie is too big for one machine, with a smarter split for busy letters like "s".
  5. Data pipeline builds a new trie from search logs on a schedule. A stream job can add fast rising trends between builds.

Deep dives

Why store the top 5 in every node

Without it, answering "s" means scanning millions of completions under that node. With precomputed lists, every answer is a short walk and a read. It costs memory and build time, which is fine because builds are offline.

Trending queries

A nightly build misses breaking news. A stream job counts queries in 5 minute windows and boosts fast risers into a small overlay that is merged with the trie's results.

Filtering

Remove offensive, dangerous or private suggestions at build time with block lists and review, and keep a fast kill switch that removes a suggestion within minutes.

Memory size

Only store queries searched more than a few times. A few hundred million popular queries fit in tens of GB, which a cluster of servers can hold.

Trade-offs you must name

ChoiceGood atCosts you
Precomputed top k per nodeInstant answers.More memory, results only as fresh as the last build.
Compute at query timeAlways fresh.Too slow at 100 thousand requests a second.
Edge cachingRemoves most load.Popular prefixes stay stale for the TTL.
Shard by prefixFits large tries.Uneven load, some letters are far more common.

Security and abuse

Autocomplete can leak and can be gamed.

  • Never suggest private data, like other users' search history.
  • Filter harmful or offensive suggestions.
  • Attackers may try to push a term by searching it many times. Limit the weight of repeated queries from one source.
