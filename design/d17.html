Design a secure platform for connected medical devices

A maker runs 50000 connected infant incubators in 1000 hospitals. Design the device, network and cloud platform with security, safety and compliance built in from the first drawing.

The ask

Each incubator sends readings and alarms to the hospital's nurse stations and summary data to the maker's cloud for maintenance. The maker pushes firmware updates. Hospitals demand strict security, regulators demand evidence, and nothing may ever put a baby at risk.

Pin down the requirements

What it must do

  • Readings every second to the local nurse station, alarms in under 1 second.
  • Hourly summaries and device health to the maker's cloud.
  • Signed firmware updates over the air, approved by each hospital.
  • Technician service access with personal accounts.
  • A fleet dashboard for the maker's support team.

How well it must do it

  • Safety functions work with no network at all.
  • Every device has a unique identity. No shared secrets.
  • All traffic encrypted and authenticated.
  • Full audit trail of setting changes and updates.
  • Evidence for FDA section 524B, the EU rules for medical devices, HIPAA and GDPR.

Out of scope, say it out loud

  • The heater control algorithm, hospital billing, the electronic health record itself.

Do the math

50000 devices send an hourly summary of 50 KB to the cloud. Each device logs about 2 MB a day locally.

Key point

When the numbers are small, the design is driven by trust boundaries, safety and evidence. Say that out loud in an interview.

The API

Device to hospital gateway      MQTT over TLS 1.3, mutual TLS with a device certificate
  publish  ward3/inc-0042/readings     { t_air, t_skin, humidity, ts }
  publish  ward3/inc-0042/alarms       { code, level, ts }
  subscribe ward3/inc-0042/commands    signed by an enrolled nurse station
Gateway to maker cloud          HTTPS with mutual TLS, outbound only
  POST /v1/telemetry/summary          pseudonymous device id, no patient data
  GET  /v1/updates/manifest           signed manifest, TUF style
Technician                       service app with SSO, MFA and a hospital work order id

The big picture

  1. Device. Secure boot, a secure element for keys, signed firmware, a local safety controller that limits temperature in hardware, no open debug ports.
  2. Hospital zone. Devices on their own network segment. A gateway terminates mutual TLS, keeps local data, serves nurse stations and is the only path out.
  3. Maker cloud. Telemetry, device registry, update distribution and SBOMs, in separate accounts per environment, with no patient data.
  4. Signing and release. An HSM backed signing service with two person approval and a TUF style signed manifest.
  5. Support access. Just in time, hospital approved, recorded sessions, read only by default.
  6. Security operations. Logs from gateways and cloud to a SIEM, vulnerability monitoring against SBOMs, incident and disclosure processes.

Deep dives

Safety first

Security controls must never block care. Alarms show locally even if login fails. The heater limit is enforced by a hardware cut off. Security risk analysis feeds into the ISO 14971 safety risk file.

Device identity at scale

Use a private device certificate authority with short lived operational certificates renewed by the gateway. Revoke a stolen device's certificate and the gateway refuses it within minutes.

Least data

The cloud needs device health, not patient identity. Use a pseudonymous device id and drop names at the gateway. Less data means less breach impact and simpler GDPR and HIPAA scope.

Update supply chain

Reproducible builds, SBOM per release, SAST and SCA in CI, signing in an HSM with two person approval, and a signed manifest with expiry so a stale or replayed manifest is rejected.

Evidence by design

Every requirement has an id, a test and a trace to its source. CI stores test results, SBOMs and scan reports per release. The release decision report is built from this evidence.
