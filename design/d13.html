Design collaborative document editing

Several people type in the same document at the same time and everyone sees the same result, with no lost words. Like Google Docs or Notion.

The ask

Many users edit one document at once. Each sees others' cursors and changes within a fraction of a second. If two people type in the same spot at the same moment, the document must end up the same for everyone, and nobody's text may vanish.

Pin down the requirements

What it must do

  • Open, edit and save documents.
  • Real time edits and cursors from other users.
  • Offline edits that merge on reconnect.
  • Version history.

How well it must do it

  • Edits appear for others in under 200 ms.
  • All copies converge to the same document.
  • Never lose an accepted edit.

Out of scope, say it out loud

  • Comments, permissions in depth, rich media.

Do the math

10 million daily users, 1 million documents open at any moment, average 3 editors per open document, each typing about 2 changes a second while active.

Key point

Each document is small and its editors are few. So route all editors of one document to the same server. That makes ordering simple and keeps cross server traffic low.

The API

WebSocket /docs/{id}/session
  client sends  { op: insert, pos: 120, text: "hi", base_rev: 341, client_id, seq }
  server sends  { op: ..., rev: 342, author }        broadcast to all editors
  client sends  { cursor: 124 }                      presence, not stored
GET /v1/docs/{id}?rev=latest     snapshot plus ops after it

The data model

StoreHolds
operations logdoc id, revision, op, author, time, append only
snapshotsfull document every N revisions in object storage
documentsmetadata, owner, title, latest revision
presencecursors and who is online, in memory only

Loading a document is the latest snapshot plus the operations after it.

Watch it work

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

The big picture

  1. Session routing sends all editors of a document to the same doc server, using consistent hashing on the doc id, lesson 2.4.
  2. Doc server keeps the live document in memory, orders and transforms operations, appends them to the operations log, then broadcasts.
  3. Operations log is the durable truth, with periodic snapshots to load documents fast.
  4. Presence like cursors is broadcast but not stored.
  5. Offline clients keep a local queue of ops and send them with their base revision on reconnect.

Deep dives

OT, operational transformation

Each operation is adjusted against the operations that were applied before it, as in the animation. A central server decides the order. Google Docs uses OT. It works well with a server, but the transform rules are tricky to get right for rich text.

CRDTs

A conflict free replicated data type gives every character a unique, ordered id, so inserts from anywhere merge in the same order without a central server. Great for offline and peer to peer. Libraries like Yjs and Automerge do the hard part. The cost is extra metadata per character.

Doc server failure

Clients reconnect, are routed to a new owner, which loads the snapshot plus log. Clients resend any ops not yet acknowledged, and duplicates are dropped using client id and sequence numbers.

Very popular documents

A document with 10 thousand viewers but few editors. Separate viewers from editors and fan out updates to viewers through a broadcast layer.

History

The op log already is the history. Named versions are just bookmarks to a revision.

Security and abuse

Shared documents need careful access control.

  • Check permissions on every edit operation, not only when the document opens.
  • When access is removed, close the live connection.
  • Keep a full version history for audit and recovery.
  • Sanitize rich content, so a pasted script cannot run in other users' browsers.
