Design a distributed job scheduler

Millions of jobs must run at the right time, such as sending a reminder at 9 am, retrying a failed payment in an hour or building a report every night. Workers crash. Design a scheduler that runs every job, on time, without running it twice by mistake.

The ask

Teams submit jobs that run once at a set time, after a delay, or on a repeating schedule like cron. The scheduler must start each job close to its time, survive worker and server crashes, retry failures with backoff, and let teams see the status of every job.

Pin down the requirements

What it must do

  • Submit one time, delayed and recurring jobs with a payload.
  • Run jobs on a pool of workers, with priorities.
  • Retry failed jobs with backoff, then move them to a dead letter list.
  • Cancel jobs and see job status and history.

How well it must do it

  • Start jobs within a few seconds of their due time.
  • Never lose a job. Running twice is rare and jobs must be safe to repeat.
  • 10 million jobs a day, with peaks at the start of each hour.
  • No single point of failure.

Out of scope, say it out loud

  • Workflows with many dependent steps, this is a single job scheduler.

Do the math

10 million jobs a day. Many teams schedule on the hour, so 20 percent of a day's jobs are due in the first minute of some hour. Use 100 thousand seconds a day.

Key point

The hard parts are not the volume. They are finding due jobs fast, handing each one to exactly one worker at a time, and recovering cleanly when that worker dies.

The API

The big picture

  1. API and store. Jobs are written to a durable store, such as PostgreSQL or a sharded database, with a unique idempotency key.
  2. Scheduler. A small set of scheduler instances, each owning some shards, polls for due jobs every second and moves them to a ready queue. Leader election, lesson 3.8, makes sure each shard has one active scheduler.
  3. Workers. Pull from the ready queue, claim a job with a lease, renew it while running, then mark it done or failed.
  4. Retries. A failed job gets a new run_at with exponential backoff and jitter. After max attempts it moves to a dead letter list and alerts the owning team.
  5. Recurring jobs. A schedules table stores each cron rule and its next run time. When a run is created, next_run_at is advanced in the same transaction, so a crash cannot skip or double a run.
  6. Observability. Metrics for due but not started jobs, lateness, failures and dead letters per job type.

Deep dives

Finding due jobs fast

Index on (status, run_at) and query WHERE status = 'scheduled' AND run_at <= now() ORDER BY run_at LIMIT 500. PostgreSQL's SELECT ... FOR UPDATE SKIP LOCKED lets several schedulers pick batches without blocking each other. Redis sorted sets with the run time as score are another common choice for the near future.

Exactly one worker at a time

A worker claims with UPDATE jobs SET lease_owner = me, lease_until = now() + 60 s WHERE id = ? AND (lease_until IS NULL OR lease_until < now()). One row changed means it owns the job. SQS calls this the visibility timeout.

Why jobs can run twice

A worker can finish the work and crash before marking it done, or pause past its lease. The system is at least once. Jobs must be idempotent, and anything that writes shared data can use fencing tokens.

The top of the hour spike

Many jobs share 9:00. Spread them with a little random delay when exact timing does not matter, scale workers ahead of known peaks, and use priorities so urgent jobs go first.

Time zones and daylight saving

Store cron schedules with a time zone and compute the next run in that zone. A 2:30 am job may not exist, or may happen twice, on daylight saving change days. Decide and document the rule.

Security and abuse

Jobs run code with real permissions, so treat the scheduler as a powerful system. Authenticate every team that submits jobs and allow only job types it owns. Never put secrets in job payloads, pass a reference to a secrets manager instead. Validate payloads in workers, since a stored job is still untrusted input. Log who created, changed or cancelled each job.
