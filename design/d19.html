Design a photo sharing app like Instagram

People upload photos from phones and scroll through thousands of others, fast, on slow networks, all over the world. Design the upload path, the image processing, and how photos reach a phone in a few hundred milliseconds.

The ask

Users post photos with a caption, follow other users and scroll a feed of photos. Photos must look sharp on any screen but load fast on a weak mobile network. The feed itself is covered in the news feed design, d03. Here, focus on storing, processing and serving photos.

Pin down the requirements

What it must do

  • Upload one or more photos with a caption.
  • Show photos in a feed, on profiles and in full screen.
  • Serve the right size for each screen.
  • Delete a photo everywhere when the owner deletes it.

How well it must do it

  • Feed thumbnails load in under 300 ms for most users worldwide.
  • Uploads work on slow networks and can resume.
  • Photos are never lost once the upload is confirmed.
  • Reads outnumber uploads by more than 100 to 1.

Out of scope, say it out loud

  • Stories, video, the ranking of the feed, comments and likes.

Do the math

100 million photos uploaded a day. The average phone original is 3 MB. We keep the original plus 4 resized variants that together add about 1 MB. Each photo is viewed about 200 times on average. A feed thumbnail is about 50 KB.

Key point

Storage grows by hundreds of TB a day, and reads are petabytes. That points to object storage for bytes, a CDN for delivery, and a separate database only for small metadata.

The API

POST /v1/uploads                 -> { upload_id, presigned_url, expires_in: 900 }
PUT  <presigned_url>             the phone sends bytes straight to object storage
POST /v1/posts                   { upload_ids: [...], caption }   -> post id, status processing
GET  /v1/posts/{id}              caption, author, image URLs for each size
DELETE /v1/posts/{id}

The data model

Ids can carry a time part so posts sort by time without a lookup, like the Snowflake ids in lesson 3.4.

The big picture

  1. Upload service hands out presigned URLs and records upload ids. Bytes go straight from phone to object storage with resumable multipart upload.
  2. Image pipeline. Storage events go on a queue. Workers validate the file, strip metadata such as GPS, make several sizes and formats, and mark the post ready.
  3. Metadata store. Posts and media rows, sharded by user id.
  4. Delivery. A CDN in front of object storage. URLs include the size and a version, so they can be cached for a long time.
  5. Feed and profiles return post ids and image URLs. The client picks the size that fits its screen.
  6. Deletion. Mark the post deleted, remove objects, and purge CDN caches. Cached copies expire anyway because URLs include a version.

Deep dives

Why presigned URLs

If 3 MB uploads passed through API servers, those servers would spend their time moving bytes. A presigned URL lets the phone write directly to object storage, while the API stays small and only checks who may upload.

Choosing sizes and formats

A phone showing a 360 px wide feed should not download a 3 MB original. Modern formats like WebP and AVIF are often much smaller than JPEG at similar quality. Clients send their screen size, or the server lists sizes and the client picks.

Cache keys and versions

Put the size and a version in the URL, such as /p/81/640/v2.webp. Then the CDN can cache it for a year. Editing a photo creates a new version, so no purge is needed for updates.

Hot photos

A celebrity post can get millions of views in minutes. The CDN absorbs this. Origin shielding, where edge caches fetch through one mid tier cache, stops a stampede of cache misses on origin.

Instagram's ids

Instagram's engineers described 64 bit ids made of a timestamp, a logical shard id and a sequence number, generated inside PostgreSQL. Ids sort by time and also tell you which shard holds the row.

Security and abuse

Images carry hidden data. Strip GPS and camera metadata so a photo does not reveal a home address. Check file types by content and process images in sandboxed workers, since image parsers have had many security bugs. Presigned URLs should allow only one object, one content type, a size limit and a short expiry. For private accounts, use signed CDN URLs that expire, so a copied link stops working. Scan uploads for known illegal content as the law requires.
