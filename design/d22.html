Design a central logging system

Thousands of servers write log lines every second. During an incident, engineers need to search them in seconds, exactly when traffic and errors are highest. Design a pipeline that never drops logs at the worst moment and does not cost a fortune.

The ask

Every service writes logs. Engineers want to search all logs from the last two weeks in seconds, filter by service, level and request id, and keep older logs cheaply for audits. The system must keep working during incidents, when log volume jumps.

Pin down the requirements

What it must do

  • Collect logs from every server and container.
  • Search and filter recent logs in seconds.
  • Keep some logs for a year for audit, cheaply.
  • Alert on patterns, such as a burst of errors.

How well it must do it

  • Do not lose logs during traffic spikes or when the index is slow.
  • New logs searchable within about a minute.
  • Control cost, logs grow faster than most data.

Out of scope, say it out loud

  • Metrics and traces, which are separate systems, see lesson 4.2.

Do the math

5,000 servers each write 200 log lines a second on a normal day. A line is about 500 bytes. During an incident, volume can jump 5 times.

Key point

The busiest moment for logs is also the moment you need them most. A durable buffer between collection and indexing is the core of the design.

The API

Structured log line, one JSON object per line
{"ts":"2026-11-26T10:15:03.120Z","level":"ERROR","service":"checkout",
 "request_id":"r-81f2","msg":"payment timeout","duration_ms":3012}

GET /v1/logs/search?q=level:ERROR AND service:checkout&from=-15m POST /v1/alerts { "query": "level:ERROR service:checkout", "threshold": 100, "window": "1m" } ```

The big picture

  1. Structured logs. JSON with a timestamp, level, service and request id on every line.
  2. Agents on each node collect, add metadata, redact secrets and batch lines. They keep a small disk buffer for short network problems.
  3. Kafka buffer. Partitioned by service, with days of retention, so slow consumers never cause loss.
  4. Indexers consume from Kafka into the hot search store. Indexes are split by day, so old days are dropped cheaply.
  5. Archivers write compressed files to object storage, partitioned by date and service, for cheap long term keeping and occasional queries.
  6. Alerting runs queries on the stream or the index and pages on thresholds.
  7. Controls on volume. Per service quotas, log levels set to INFO in production, sampling of noisy lines.

Deep dives

Why a buffer

Agents that send straight to the index must either drop lines or block when the index is slow. A durable buffer like Kafka separates the speed of producing logs from the speed of indexing them, which is exactly what an incident needs.

Full text index or labels

Elasticsearch and OpenSearch index the words of every line, so any word is searchable, but the index is large. Grafana Loki indexes only a few labels, such as service and level, stores the text compressed, and scans it at query time. It is much cheaper, but free text search over long periods is slower.

Retention tiers

Most searches look at the last few hours. Keep 7 to 14 days hot, then only in object storage. Indexes split by day make deletion a quick drop of a whole index instead of deleting billions of rows.

Cost control

Logs grow with traffic and with every new log line a developer adds. Use quotas per team, drop or sample DEBUG in production, and count bytes per service on a dashboard, so each team sees its own cost.

Request ids

Put a request id on every line and pass it between services. During an incident, searching one id shows the whole path of a failing request, much like a trace.

Trade-offs you must name

ChoiceGood atCosts you
Kafka bufferNo loss during spikes, many consumers.Another system to run and pay for.

Label index such as LokiCheap storage.Slower free text search.
Sampling noisy logsBig savings.Some lines are not kept.

Security and abuse

Logs leak secrets more often than databases do. Redact passwords, tokens, card numbers and personal data in the agent, before lines leave the host, and test the redaction rules. Limit who can search production logs, log those searches, and encrypt logs in transit and at rest. Some laws limit how long personal data may be kept, so set retention by data type, and make audit logs append only so attackers cannot erase their tracks.
