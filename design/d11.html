Design a web crawler

Visit billions of web pages, follow their links, store what you find, and do it politely, without hammering any one website. The first step of every search engine.

The ask

Start from a list of seed URLs, download each page, extract its links, and keep going. Store the pages for a search index. Revisit pages over time to catch changes.

Pin down the requirements

What it must do

  • Download pages starting from seeds and following links.
  • Store page content and metadata.
  • Revisit pages, important ones more often.

How well it must do it

  • Crawl a billion pages a month.
  • Be polite, obey robots.txt and limit requests per site.
  • Avoid traps and duplicates.
  • Keep going when machines fail.

Out of scope, say it out loud

  • Ranking and the search index itself, running JavaScript heavy pages.

Do the math

1 billion pages a month, average page 100 KB.

Key point

400 pages a second is easy for compute. The hard parts are politeness per site, never visiting the same page twice, and not getting stuck in traps.

The API

This is an internal batch system, so instead of a public API it has components.

frontier.add(url, priority)
frontier.next(worker_id) -> url        respects per host timing
fetcher.fetch(url) -> status, headers, body
store.save(url, content_hash, body)

The big picture

  1. URL frontier with two layers. Front queues by priority, back queues one per host so each host is visited at a polite rate.
  2. Fetchers spread across many machines, with DNS caching, timeouts and size caps.
  3. Parsers extract text and links and compute content hashes.
  4. Dedup of URLs with normalization plus a Bloom filter, and of content with hashes.
  5. Storage of pages in object storage, compressed.
  6. Recrawl scheduler revisits pages based on how often they change and how important they are.

Deep dives

Politeness

Obey robots.txt. Keep one back queue per host and a minimum delay between hits to the same host. Assign each host to one worker so the rule is easy to enforce.

URL normalization

Lowercase the host, remove fragments like #top, sort query parameters and drop tracking ones, so many spellings of one URL count as one.

Bloom filters

A Bloom filter is a bit array that can say an item is definitely not in the set, or probably is. Billions of URLs fit in a few GB. A rare false positive means skipping a page, which is acceptable.

Traps

Calendars with infinite next month links or URLs that grow forever. Cap URL length and depth per site, and limit pages per host.

Failure

Store the frontier on disk and checkpoint it, so a crashed worker's URLs are handed to another.

Trade-offs you must name

ChoiceGood atCosts you
Breadth firstCovers many sites quickly.May miss deep important pages.
Priority by importanceBetter pages first.Needs a way to score pages before you have them.
Bloom filter for seen URLsTiny memory.Rare false positives skip new pages.
Exact seen set in a databaseNo mistakes.Much more storage and slower checks.

Security and abuse

A crawler visits the open internet, which includes hostile sites.

  • Respect robots.txt and rate limits, or you become the attacker.
  • Parse pages in sandboxed workers. Pages can be huge, malformed or built to crash parsers.
  • Block internal and cloud metadata addresses so a link cannot make the crawler fetch your own private systems.
