Rate limiting, saying slow down politely

A rate limiter caps how many requests someone can make in a time window. It protects your system from abuse, bugs and sudden floods, and keeps things fair.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Without limits, one buggy client in a loop, one scraper or one attacker can use up all your servers and everyone else suffers. A rate limiter counts requests per user, per key or per IP, and when someone goes over their limit, it answers 429 Too Many Requests instead of doing the work.

Think of it like this

A water park lets each child on the big slide only so many times an hour. A kid who tries to go 50 times is asked to wait, so everyone gets a turn and the slide is not overloaded.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Rate limit
The maximum number of requests allowed in a time window.
Token bucket
A bucket of tokens that refills at a steady rate. Allows short bursts.
Leaky bucket
Requests drain out at a fixed rate like water from a hole. Smooths traffic perfectly.
Fixed window
Count requests per clock minute. Simple, but allows double bursts at window edges.
Sliding window
Count over the last 60 seconds from now. Fairer, a bit more work.
429
The HTTP status for Too Many Requests.
Throttling
Slowing down instead of rejecting outright.
Load shedding
Dropping some requests on purpose when the whole system is overloaded, to save the rest.

How it works

The algorithms

AlgorithmHow it worksGoodBad
Fixed windowCounter per user per minute, reset each minuteVery simple2 times the limit can slip through around the minute edge
Sliding window logKeep timestamps of recent requestsExactUses memory per request
Sliding window counterBlend this minute and last minute countsAccurate and cheapSmall approximation
Token bucketTokens refill steadily, requests spend themAllows bursts, popularTwo numbers to tune
Leaky bucketQueue that drains at a fixed rateSmooth outputBursts wait or drop

Where to put it

  • At the edge, in an API gateway or load balancer, to block floods before they reach your servers.
  • In the service, for limits that need business knowledge, like "3 password tries a minute".
  • For calls you make, so you do not exceed someone else's API limits.

Many servers, one limit

If you have 20 API servers, each one counting alone lets a user get 20 times the limit. So counters usually live in a shared fast store like Redis, updated with an atomic increment or a small script. For very high traffic, servers can keep local counts and sync often, accepting a little slack.

Be kind to clients

Return 429 with Retry-After, and headers like X-RateLimit-Remaining. Good clients back off. Document the limits.

Key point

Choose what you limit by. Per IP hurts people behind one office network. Per API key or user is fairer. Use several limits together, per user, per IP for logins, and a global cap.

Real life scenarios

GitHub API limits

GitHub's API allows a set number of requests an hour per token and tells you the remaining count in response headers. Clients that read the headers never get blocked.

A login brute force attack

Attackers tried thousands of passwords per account. A limit of 5 login attempts per account per 15 minutes, plus per IP limits, stopped it without hurting normal users.

A mobile bug that looked like an attack

A new app version retried failed requests instantly in a loop. Traffic jumped 40 times. Per user rate limits kept the backend alive until a fix shipped.

Trade-offs

ChoiceGood atCosts you
Fixed windowSimplest to build.Edge bursts up to double the limit.
Token bucketAllows healthy bursts, smooth average.Tuning size and rate.

Common mistakes

  • Counting on each server separately and calling it a global limit.
  • Limiting by IP only, which blocks whole offices and mobile carriers.
  • Returning 500 or a vague error instead of 429 with Retry-After.
  • Letting the rate limiter itself become a single point of failure.

Security lens

Rate limiting is a core security control.

  • Slows password guessing and credential stuffing. Limit by account and by IP.
  • Slows scraping and enumeration of ids.
  • Protects expensive endpoints from denial of service.
  • Attackers rotate IPs, so combine limits with bot detection, CAPTCHAs on suspicious flows and MFA.
