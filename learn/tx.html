Transactions, isolation and deadlocks

Moving money takes two writes. If the server dies between them, money vanishes. Learn how transactions make many writes act as one, what isolation levels really promise, and why two transactions can wait for each other forever.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

A transaction is a group of writes that the database treats as one. Either all of them happen, or none of them do.

Think of a transfer of 100 rupees from Asha to Ben. That is two writes. Take 100 from Asha. Add 100 to Ben. If the server crashes after the first write, Asha lost money and Ben got nothing. Inside a transaction, the crash undoes the first write. Nothing is lost.

Databases describe this promise with four letters, ACID.

  1. Atomicity. All or nothing.
  2. Consistency. Rules you set, like "balance can never be negative", hold before and after.
  3. Isolation. Transactions running at the same time do not see each other's half done work.
  4. Durability. Once the database says "committed", the data survives a crash.
Think of it like this

A transaction is like a parcel. You put several things in the box and seal it. The courier delivers the whole box or returns the whole box. It never delivers half.

Words you need

Transaction
A group of reads and writes that succeed or fail as one unit.
Commit
The moment a transaction becomes permanent.
Rollback
Undoing every change of a transaction that did not commit.
Write-ahead log
An append-only file where the database records changes before applying them, so it can recover after a crash.
fsync
A call that forces data from memory to the disk. A commit is only durable after this.
Isolation level
How much one transaction can see of others running at the same time.
Lock
A mark on a row or table that stops other transactions from changing it until the lock is released.
Deadlock
Two or more transactions each waiting for a lock the other holds. None can continue.
Lost update
Two transactions read the same value, both change it, and one change overwrites the other.

How it works

Isolation levels

Full isolation is slow, so databases let you choose. The SQL standard names four levels. Each level stops more problems.

LevelDirty readNon-repeatable readPhantom read
Read uncommittedPossiblePossiblePossible
Read committedStoppedPossiblePossible
Repeatable readStoppedStoppedPossible in the standard
SerializableStoppedStoppedStopped
  • A dirty read sees data that another transaction has not committed yet.
  • A non-repeatable read reads the same row twice and gets two values.
  • A phantom read runs the same search twice and gets new rows.

PostgreSQL uses read committed by default. MySQL with InnoDB uses repeatable read by default. Real databases differ in details, so read your database's documentation.

The lost update, the bug you will meet first

-- two requests at the same time, both read balance = 500
SELECT balance FROM accounts WHERE id = 1;      -- 500
UPDATE accounts SET balance = 400 WHERE id = 1; -- each subtracts 100 in app code

Both write 400. One withdrawal is lost. Three fixes.

  1. Do the math in the database. UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100.
  2. Lock the row while you read it. SELECT ... FOR UPDATE.
  3. Optimistic check. Add a version column and update only WHERE version = 7. If no row changed, read again and retry.

Deadlocks

Transaction A locks Asha's row, then wants Ben's. Transaction B locks Ben's row, then wants Asha's. Each waits for the other forever. That is a deadlock.

Databases find these cycles. PostgreSQL checks after a waiting transaction has waited for deadlock_timeout, 1 second by default. InnoDB checks right away by default. Both kill one transaction, the victim, with an error. Your code must catch that error and retry.

The best fix is to stop deadlocks from forming. Always lock rows in the same order, for example by account id. Then two transfers between the same accounts lock in the same order, and no cycle can form.

Key point

Keep transactions short. Never wait for a user, an email or an HTTP call while a transaction holds locks.

Real life scenarios

A crash during a transfer

A wallet app first wrote the debit, then called a second service for the credit, with no transaction around them. During a deploy, a few hundred transfers lost money in the middle. Moving both writes into one database transaction, and a nightly check that totals match, fixed it.

Deadlocks after a new feature

A shop added a job that updated stock in alphabetical order of product name, while checkout updated stock in cart order. Deadlocks appeared at peak times. Sorting both by product id removed them.

Durability turned off

Some teams switch off waiting for fsync to make commits faster. A power cut then loses the last second of committed orders. It is a valid trade for logs or caches, not for money.

Trade-offs

ChoiceGood atCosts you
Serializable isolationNo anomalies, easiest to reason about.Slower, more retries under load.
Read committedFast and the common default.You must handle lost updates yourself.
Pessimistic locks, FOR UPDATESimple when conflicts are common.Waiting, and deadlocks if the order differs.
Optimistic version checksNo waiting when conflicts are rare.Retries when conflicts are common.

Common mistakes

  • Reading a value into the app, changing it and writing it back without a lock or a version check.
  • Calling another service or waiting for a user while a transaction is open.
  • Locking rows in a different order in different code paths.
  • Not retrying a transaction that the database chose as a deadlock victim.
  • Assuming every database means the same thing by "repeatable read".

Security lens

Race conditions are security bugs too. If two withdrawal requests arrive at once, a lost update can let a user spend the same money twice. Attackers send many requests in parallel on purpose. Protect balances, coupons and stock with conditional updates or locks, and test with concurrent requests.
