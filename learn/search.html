Query plans, composite indexes and search engines

The same query can read 20 rows or 20 million. Learn to read a query plan, design an index that matches the query, and see why a search engine finds "running shoes" when SQL LIKE cannot.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

When you send SQL, the database does not run it word by word. A part called the planner looks at your query, the indexes and some statistics about the data, and picks a plan. The plan is the list of steps, such as "scan the whole table" or "walk this index".

You can see the plan with EXPLAIN. EXPLAIN ANALYZE runs the query and also shows the real times and row counts. Reading a plan is the fastest way to find out why a query is slow.

Search boxes are a different problem. A user types "running shoe" and expects to find "Shoes for runners". SQL LIKE '%running shoe%' cannot use a normal index and misses that match. A search engine such as Elasticsearch or OpenSearch builds an inverted index, a map from each word to the documents that contain it, and ranks the results.

Think of it like this

A query plan is a route for a delivery driver. The driver can visit every house on every street, or look up the right street in a map first. The planner picks the route. EXPLAIN shows you the route it picked.

Words you need

Planner
The part of the database that chooses how to run a query.
EXPLAIN
Shows the plan. EXPLAIN ANALYZE also runs the query and shows real times and row counts.
Seq Scan
Reads every row of a table. Fine for small tables or when most rows match.
Index Scan
Walks an index to find matching rows, then reads them.
Index only scan
Answers from the index alone because it holds every column the query needs.
Composite index
One index over several columns, in a set order.
Selectivity
The share of rows a filter keeps. Indexes help most when it is small.
Inverted index
A map from each word to the list of documents that contain it.
Stemming
Cutting words to a root so that running, runs and run match each other.
BM25
A common formula for ranking search results by how well they match the words.

How it works

How to read a plan

  • Read from the innermost step outwards. That runs first.
  • Compare estimated rows with actual rows. A big gap means the statistics are old. Run ANALYZE on the table.
  • Look for Seq Scan on big tables, Sort steps on many rows, and nested loops that run thousands of times.

Design a composite index for the query

A composite index on (user_id, created_at) is sorted by user first, then by date inside each user. Rules of thumb.

  1. Put columns you test with equals first.
  2. Then the column you sort by or filter by range.
  3. The index helps only queries that use its leftmost columns. (user_id, created_at) helps WHERE user_id = 42 but not WHERE created_at > '2026-01-01' alone.

Add only indexes that real queries need. Each index slows every insert and update and uses disk.

Why LIKE is not search

WHERE name LIKE '%shoe%' with a wildcard at the start cannot use a B-tree index, so it scans. It also has no idea that "shoes" and "shoe" are related, and no ranking.

How a search engine works

  1. Analyze. Split text into words, make them lowercase, remove very common words if you choose, and stem them. "Shoes for Runners" becomes shoe, runner.
  2. Index. For each word, keep a posting list of document ids, like shoe → 4, 18, 77.
  3. Query. Analyze the search text the same way, fetch the posting lists and combine them.
  4. Rank. Score each document. Elasticsearch uses BM25 by default. Rare words that appear often in a short document score high.

Search engines are built for finding and ranking, not for being the source of truth. Keep the real data in your database and copy changes into the search index, often with change data capture. New documents appear after a refresh, about once a second by default in Elasticsearch, so search is near real time, not instant.

Key point

Use the database for exact lookups and transactions. Use a search engine for free text, typo tolerance, filters and ranking over many fields.

Real life scenarios

A missing index in a growing app

An order history page took 40 ms with 10,000 orders and 9 seconds two years later with 30 million. EXPLAIN showed a Seq Scan and a Sort. One composite index on user and date brought it under 1 ms.

The wrong column order

A team built an index on (created_at, user_id) for the same query. The planner could not use it well, because the first column was the date. Swapping the order fixed it.

Search on LIKE

A shop searched products with LIKE '%term%'. It was slow and missed plurals and typos. Moving search to OpenSearch, synced from the database, made it fast and found far more matches.

More indexesFaster reads for those queries.Slower writes, more disk, more to maintain.

Common mistakes

  • Guessing why a query is slow instead of running EXPLAIN ANALYZE.
  • Putting the range or sort column before the equals column in a composite index.
  • Adding an index for every column.
  • Using LIKE with a leading wildcard for user search.
  • Treating the search engine as the main database.

Security lens

Never build SQL by joining strings with user input. Use parameters, even for search terms, or you open the door to SQL injection. Search engines need care too. Do not expose the search cluster directly to the internet, and apply the user's permissions to search results, so a search never returns documents the user may not see.
