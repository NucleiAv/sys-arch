Security foundations and design principles

Before you can secure a system, you need words for what "secure" means. Learn the goals of security, a short history of how we got here, and the classic design principles every architect still uses.

The idea in one minute

Security means a system keeps doing what it should, and only that, even when someone tries to make it do something else. A normal bug happens by accident. A security bug is one that a person chooses to trigger, again and again, at the worst time.

We describe the goals with three letters, CIA.

  1. Confidentiality. Only the right people can read the data.
  2. Integrity. Nobody can change the data or the system without being allowed to.
  3. Availability. The system works when people need it.

Many teams add authenticity, you know who sent something, and non-repudiation, a person cannot later deny that they did it.

In this level we follow one product from start to finish. It is a connected infant incubator in a hospital. It keeps a baby warm, it reports to a nurse station over the network, and it gets software updates. For this product, integrity and availability can be a matter of life. A wrong temperature is worse than a leaked log.

Think of it like this

Think of a diary with a lock. Confidentiality means your brother cannot read it. Integrity means he cannot rip out a page or write in it. Availability means you can still open it when you want to write.

Words you need

Asset
Something of value that you must protect. Patient data, the device, the hospital's trust.
Threat
Something or someone that can cause harm. A thief, a bored teenager, a nation state, a flood.
Vulnerability
A weakness that a threat can use. A missing check, an old library, a weak password.
Exploit
The method or code that uses a vulnerability.
Attack surface
Every place where an attacker can try to get in. Ports, APIs, USB, update channels, people.
CIA triad
Confidentiality, integrity and availability. The three classic security goals.
Safety
Freedom from harm to people. In medical devices, security failures can become safety failures.
Trust boundary
A line where data or control passes between parts that trust each other differently.

The classic design principles

In 1975 Saltzer and Schroeder wrote eight principles. They still guide good architecture.

  1. Economy of mechanism. Keep the design small and simple. Simple things have fewer bugs.
  2. Fail-safe defaults. Deny by default. Give access only when a rule says yes.
  3. Complete mediation. Check every access, every time. Do not trust an old check.
  4. Open design. The design can be public. Security must come from keys, not from secrets about how it works.
  5. Separation of privilege. Ask for two conditions for very important actions, like two keys or two people.
  6. Least privilege. Give each user and program only the access it needs, for only as long as it needs it.
  7. Least common mechanism. Share as little as possible between users, since every shared part is a path between them.
  8. Psychological acceptability. Make security easy to use, or people will work around it.

Two more ideas are used everywhere today. Defense in depth means several layers, so one failure is not a breach. Secure by default means the product is safe when it leaves the box, without extra setup.

Key point

A good architect can name the principle behind each control. "We check the token on every call" is complete mediation. "The service account can only read one table" is least privilege.

Real life scenarios

The Morris worm, 1988

A student released a program that copied itself across the internet using known bugs and weak passwords. A coding mistake made it spread far faster than planned, and it slowed or crashed thousands of machines. It led to the first computer emergency response team, CERT.

Stuxnet, found in 2010

A worm reached machines in an industrial plant that had no internet link, probably on USB drives. It changed how centrifuges spun while showing normal values to operators. It proved that software attacks can cause physical damage.

Insulin pump warnings, 2019

The US regulator warned that some older insulin pumps had radio links with no proper authentication. A nearby attacker could change the dose. The maker could not patch them and offered patients newer models instead.

Common mistakes

  • Thinking security is only about confidentiality. In devices, integrity and availability often matter more.
  • Treating security as a feature you add at the end.
  • Allowing access by default and blocking known bad things, instead of denying by default.
  • Relying on a secret design instead of strong keys.
  • Making security so painful that people bypass it.
