Consensus, leader election and distributed transactions

How do many machines agree on one answer when any of them can crash? And how do you change data in two services so both change or neither does? The deepest ideas in the course, in plain words.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Some decisions must be made by exactly one machine, or agreed by all. Who is the database leader? Which value was written last? Did this payment happen? Getting machines to agree, even when some crash or messages get lost, is called consensus.

The popular way is Raft. Machines elect a leader by majority vote. The leader writes every decision to a log and only counts it as final once a majority has a copy. With 5 machines, any 3 make a majority, so the system keeps working with 2 dead.

A related problem is changing data in two places at once, like taking money in the payment service and creating the order in the order service. Either both happen or neither. That is a distributed transaction.

Think of it like this

Five friends choose a movie by majority. Even if two fall asleep, three can still decide, and when the sleepers wake up they are told the choice. Nobody can decide alone, so two different movies can never both be chosen.

Words you need

Consensus
Many machines agreeing on one value or one order of events, even with failures.
Raft
A consensus method built to be easy to understand. Leader, terms, log, majority.
Paxos
An older consensus method, famous for being hard to understand.
Quorum or majority
More than half the nodes. With 5 nodes, 3.
Term
A numbered election period in Raft.
Two phase commit
A coordinator asks every participant to prepare, then tells all to commit or all to abort.
Saga
A chain of local transactions. If a later step fails, earlier steps are undone with compensating actions.
Outbox pattern
Save the data change and the event to send in one local transaction, then send the event from that table.

How it works

Where you meet consensus

You rarely write Raft yourself. You use tools built on it. etcd and ZooKeeper for configuration, locks and leader election. Kubernetes stores its state in etcd. CockroachDB, TiDB and Kafka KRaft use Raft inside. Your job is knowing when you need it, like "only one scheduler may run this job".

Key point

Clusters use odd numbers like 3 or 5. With 4 nodes the majority is 3, so you can still only lose 1, the same as with 3 nodes, but with more machines to pay for.

Two phase commit, 2PC

  1. Prepare. The coordinator asks every participant, "can you commit?" Each locks its data and says yes or no.
  2. Commit. If all said yes, the coordinator says "commit". If anyone said no, "abort".

It is correct, but slow, and if the coordinator dies after prepare, participants sit holding locks. It is used inside databases and some enterprise systems, rarely across microservices.

Sagas, the microservice way

Break the big transaction into local steps, each with an undo step.

StepUndo if a later step fails
Create order, status pendingCancel order
Reserve stockRelease stock
Charge cardRefund card
Mark order confirmednone needed

Sagas give up isolation. Others may see the pending order in the middle. They can be orchestrated, one coordinator tells each service what to do, or choreographed, each service reacts to the previous one's events.

The outbox pattern

A common bug is "save to database, then publish event", where the app crashes in between and the event is lost. Instead, write the change and the event row into an outbox table in one local transaction. A separate process reads the outbox and publishes. Now both happen or neither.

Real life scenarios

Kubernetes keeps its brain in etcd

Every Kubernetes cluster stores what should be running in etcd, a Raft cluster usually of 3 or 5 nodes. If etcd loses its majority, the cluster can no longer make changes, though running apps keep running.

Uber's trip saga

Booking a ride touches pricing, payments, driver matching and more. These services coordinate with workflows that retry and compensate, not one big transaction. Uber built and open sourced the workflow engine Cadence, later Temporal grew from it.

A lost order email

A shop saved orders and then published an event to send email. When the process crashed between the two, customers got no confirmation. The outbox pattern fixed it.

Trade-offs

ChoiceGood atCosts you
Consensus with RaftStrong agreement that survives failures.Every write needs a majority round trip, slower, small clusters only.
Two phase commitTrue atomic change across systems.Blocking on coordinator failure, locks held, slow.
SagaScales across services, no global locks.No isolation, you must write and test undo steps.
Orchestrated sagaOne place shows the whole flow.The orchestrator is more to build and run.
Choreographed sagaServices stay loosely coupled.Hard to see and debug the whole flow.

Common mistakes

  • Using an even number of consensus nodes.
  • Spreading a 3 node Raft cluster so that one data center holds 2 nodes, then losing that data center.
  • Using 2PC across many microservices.
  • Saving to the database and publishing an event as two separate steps.
  • Sagas without idempotent steps, since retries will happen.

Security lens

Consensus systems hold the most important data in a cluster.

  • Stores like etcd hold Kubernetes secrets and config. Encrypt them, use mutual TLS between members and limit who can reach them.
  • Raft and Paxos assume nodes fail by stopping, not by lying. If nodes may be malicious, you need Byzantine fault tolerance, as in blockchains.
  • Distributed transactions must not let a partial failure leave money or stock in a state attackers can exploit.
