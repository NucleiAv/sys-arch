Caching, remembering answers to go faster

A cache keeps popular answers in fast memory so you skip slow work. It is the biggest speed win in most systems, and the source of some of the trickiest bugs.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Many requests ask the same thing. The top 100 products, the home page, a celebrity's profile. Doing the same slow database work again and again is wasteful. A cache stores the answer in memory the first time, and serves it from there next time.

Memory is about 1,000 times faster than disk and a cache like Redis can answer in under a millisecond. A good cache can absorb 90 percent or more of reads.

The two hard questions are what to keep, because memory is small, and when to throw an answer away, because the real data changes.

Think of it like this

If people keep asking you the time, you look at your watch once and remember it for a minute. That is a cache. If you remember it for a whole day, you will give wrong answers. That is a stale cache.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Cache hit
The answer is in the cache.
Cache miss
It is not, so you do the slow work.
Hit ratio
Hits divided by all lookups. 90 percent or more is common for good caches.
TTL
Time to live. How long an entry stays before it expires.
Eviction
Throwing entries out when memory is full.
LRU
Least recently used. Evict what nobody has asked for in the longest time.
Invalidation
Removing or updating cached data when the real data changes.
Cache stampede
Many requests miss at once and all hit the database together.

How it works

Where caches live

From closest to the user to farthest. Browser cache, CDN, load balancer or reverse proxy, the app's own memory, a shared cache like Redis or Memcached, and the database's own buffer.

The main patterns

PatternHow it worksGood for
Cache asideApp checks cache, on a miss reads the DB and fills the cacheThe default, most apps
Read throughThe cache itself loads from the DB on a missSimpler app code
Write throughWrite to cache and DB togetherData read right after writing
Write behindWrite to cache, flush to DB laterVery fast writes, risk of loss

Keeping it fresh

  • TTL puts an upper limit on staleness. Short for prices, long for avatars.
  • Delete on write. After updating the database, delete the cache key. Deleting is safer than updating, because two updates racing can leave the wrong value.
  • Accept some staleness where it is harmless. A like count that is 10 seconds old is fine. A bank balance is not.

Eviction

Memory fills up. LRU throws out what was used longest ago. LFU throws out what is used least often. LRU is the common default.

Stampedes and hot keys

When a very popular key expires, thousands of requests miss at once and hammer the database. Fixes are letting only one request rebuild the key while others wait or get the old value, adding a little random jitter to TTLs so keys do not all expire together, and refreshing hot keys before they expire.

Key point

"There are only two hard things in computer science, cache invalidation and naming things." A famous joke, and true. Decide up front how stale each kind of data may be.

Real life scenarios

Facebook's memcache at enormous scale

Facebook built one of the largest Memcached deployments, serving billions of requests a second, and wrote about leases, a trick that stops stampedes and stale sets by letting only one client refill a missing key.

A sale price that would not change

A shop cached product pages for 24 hours. The marketing team changed prices for a flash sale, but customers saw old prices all day. They moved to delete on write plus a 5 minute TTL.

The midnight stampede

A news site set every cache key to expire at midnight. At 00:00 every page missed at once and the database fell over. Random jitter on TTLs spread the expiries out.

Trade-offs

ChoiceGood atCosts you
Long TTLHigh hit ratio, fast.More stale data.
Short TTLFresher data.More misses and more database load.

Common mistakes

  • Caching data that must be exactly right, like stock levels at checkout, without a check.
  • Updating the cache on write instead of deleting, which allows races.
  • Same TTL on every key, so they all expire together.
  • No plan for the cache going down. Can the database survive full load alone?
  • Caching per user pages in a shared CDN and showing one user's data to another.

Security lens

Caches remember answers, including the wrong answers for the wrong people.

  • Cache keys must include the user when content is private. Otherwise one user's page can be served to another.
  • Web cache poisoning. An attacker makes a shared cache store a harmful response. Do not cache responses that depend on unkeyed headers.
  • Cache deception. A private page at a URL that looks static, like /account.css, gets cached by a CDN. Set Cache-Control: private on private pages.
  • Do not put secrets or full personal records in Redis without access control and TLS.
