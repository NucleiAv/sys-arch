Secure software development and security testing

Most security bugs are written by tired, busy people, not by bad ones. Learn the habits and tools that keep code clean, how security testing differs from normal testing, and how to tie tests back to the threat model.

The idea in one minute

A secure software development life cycle, SSDLC, adds security work to each step of normal development. You plan with threat models, you code with safe patterns, tools check every change, and testers try to break the product the way an attacker would.

Cyber hygiene is the daily, boring part. Keep dependencies up to date, never put secrets in code, review every change, and fix warnings before they pile up. Like washing your hands, it stops most problems before they start.

Security testing is different from functional testing. A functional test asks "does the feature do what it should?" A security test asks "can someone make it do what it should not?" Functional tests use expected inputs. Security tests use strange, broken and hostile inputs.

Think of it like this

A functional test checks that your front door opens with your key. A security test checks that it stays shut when someone tries a hairpin, a credit card, a kick and the window next to it.

Words you need

SSDLC
Secure software development life cycle. Security activities in every phase of building software.
Cyber hygiene
Basic, regular practices that keep systems healthy. Updates, least privilege, no secrets in code, backups.
SAST
Static application security testing. Reads source code to find bugs without running it. Semgrep, CodeQL, Bandit for Python.
DAST
Dynamic application security testing. Attacks the running app from outside. OWASP ZAP.
SCA
Software composition analysis. Finds known vulnerable libraries. Dependabot, pip-audit.
SBOM
Software bill of materials. A list of all components and versions in a product. SPDX and CycloneDX formats.
Fuzzing
Sending huge numbers of random or mutated inputs to find crashes and hangs.
Penetration test
Skilled people try to break into the system, within agreed rules.
Abuse case
A test case written from the attacker's goal, like replaying an old command.
Negative test
A test that checks a bad input or action is refused.

How it works

Frameworks for a secure development life cycle

  • NIST SSDF, SP 800-218. Four groups. Prepare the organization, protect the software, produce well secured software, respond to vulnerabilities. US government buyers ask for it.
  • Microsoft SDL. Training, requirements, threat modeling, tools, testing and response.
  • OWASP SAMM. A model to measure how mature your practices are and plan the next step.
  • IEC 81001-5-1. The same ideas, written for health software.

Security testing versus functional testing

Functional testingSecurity testing
QuestionDoes it do what it should?Can it be made to do what it should not?
InputsExpected, validUnexpected, broken, hostile
Pass meansThe feature worksThe attack fails, safely
CoverageRequirements and user storiesThreats, abuse cases, trust boundaries
WhoDevelopers and QAAlso security testers and outside experts

Kinds of security testing

  1. Vulnerability scanning. Automated checks for known issues.
  2. Fuzzing. Random and mutated inputs at parsers and protocols. Great for device firmware. Tools include AFL++ and Atheris for Python.
  3. Penetration testing. Humans chain small issues into real attacks.
  4. Red teaming. A longer exercise that tests the people and the detection too.

Tie tests to the threat model

Every mitigation from the threat model should have at least one test. Spoofing threat T2 maps to a test that connects with a fake certificate and expects a refusal. Then you can show coverage. "All 24 threats rated high have passing tests."

Careful

A tool with 600 open warnings is not a control. Tune the rules, fix or triage the findings, and block new high findings in CI. Otherwise people stop reading the results.

Real life scenarios

Heartbleed, 2014

A missing length check in OpenSSL let attackers read up to 64 kilobytes of server memory per request, including private keys. Fuzzing tools later found the same bug in minutes. It pushed big companies to fund core open source projects and fuzzing programs like OSS-Fuzz.

The xz backdoor, 2024

Over two years, a contributor gained trust in a small compression library and hid a backdoor in its release files. An engineer noticed that SSH logins were half a second slower and dug in. It showed that supply chain risk includes the people behind libraries.

MOVEit, 2023

A SQL injection flaw in a file transfer product let a ransomware gang steal data from hundreds of organizations. SQL injection is one of the oldest bug classes and parameterized queries prevent it.

Trade-offs

ChoiceGood atCosts you
SASTRuns early on every change, sees all code paths.False positives, misses logic and config issues.
DASTTests the real running app.Needs a running system, misses hidden code paths.
FuzzingFinds crashes humans never think of.Needs setup and compute, mostly finds memory and parser bugs.
Pen testingFinds chained and logic attacks.Expensive, a snapshot in time.

Common mistakes

  • Running scanners but never fixing the findings.
  • Only testing the happy path.
  • Secrets in code, even in private repositories.
  • No SBOM, so you cannot answer "do we use the bad library?"
  • A pen test the week before release, with no time to fix what it finds.
