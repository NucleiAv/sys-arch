Idempotency, making retries safe

Networks lose replies, not only requests. When a client cannot tell whether a payment went through, it retries, and the customer may pay twice. Learn how idempotency keys turn "at least once" into "exactly once in effect".

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

An operation is idempotent if doing it twice has the same effect as doing it once. Setting your phone number to 98765 is idempotent. Adding 100 rupees to a balance is not.

Retries are everywhere. A mobile app on a weak network sends "pay 500", the server charges the card, and the reply is lost on the way back. The app sees a timeout and sends the request again. Without protection, the card is charged twice.

The fix is an idempotency key. The client makes a unique id, such as a UUID, for each intended action and sends it with every retry. The server remembers each key and the result. When the same key comes again, it returns the saved result instead of doing the work again.

Think of it like this

You post a letter with a tracking number. If you are not sure it arrived and post a copy with the same tracking number, the post office sees it already delivered that number and throws the copy away.

Words you need

Idempotent
Doing it twice has the same effect as doing it once.
Idempotency key
A unique id the client sends with a request, reused on every retry of the same intended action.
At least once
Every message or request is delivered, maybe more than once.
Exactly once effect
Repeats are possible, but the result happens only once, thanks to dedup.
Dedup table
A table of keys already processed, often with a unique constraint.
Safe method
An HTTP method that does not change state, such as GET.

How it works

Which HTTP methods are idempotent

MethodIdempotent by the HTTP standard?Why
GET, HEAD, OPTIONSYesThey only read.
PUTYesIt sets a resource to a value. Twice gives the same state.
DELETEYesDeleting twice leaves it deleted. The second reply may be 404.
POSTNoIt usually creates something new each time.
PATCHNot guaranteedDepends on the change, "add 1" is not idempotent.

POST is where you need idempotency keys most. Stripe and many other payment APIs accept an Idempotency-Key header, and the IETF is writing a standard for that header.

How to build it on the server

1. Store the key first, inside the same transaction as the work if you can, in a table with a unique constraint on the key. 2. If the insert fails because the key exists, look at the saved state. - Finished. Return the saved response. - In progress. Return 409 Conflict, so the client waits and retries later. 3. Also save a hash of the request body. If the same key comes with a different body, reject it with an error. That is a client bug. 4. Keep keys for a set time, for example 24 hours, then delete them.

Idempotent consumers

Queues and Kafka deliver at least once. Make consumers safe by recording each processed message id in a dedup table, in the same transaction as the work. Or make the work naturally idempotent, for example UPDATE orders SET status = 'paid' WHERE id = 81, which is safe to repeat. "Add 500 to balance" is not.

Where the key comes from

The key must be made by the client, once per user intention, and reused on retries. If the server made it, a retry would get a new key. Use a random UUID, or something tied to the action, such as the order id.

Key point

Exactly once delivery across a network is not possible in general. Exactly once effect is. It is at least once delivery plus idempotent processing.

Real life scenarios

Stripe's idempotency keys

Stripe lets clients send an Idempotency-Key header on POST requests. Retries with the same key return the first result, including errors. Its engineers have written about building this on top of PostgreSQL transactions.

Double orders on a slow network

A food app saw some customers charged twice on trains and in lifts. The app retried on timeout with a new request each time. Adding a key per checkout tap stopped it.

The webhook that fired twice

A payment provider sent the same paid webhook twice after a timeout. The shop shipped two parcels. Storing the event id with a unique rule and skipping repeats fixed it.

Trade-offs

ChoiceGood atCosts you
Idempotency keysSafe retries for non idempotent actions.A table of keys to store, expire and look up.
Naturally idempotent operationsNo extra storage.Not every action can be written that way.
Dedup in consumersMakes at least once delivery safe.Must keep ids at least as long as redelivery can happen.

Common mistakes

  • Retrying POST requests without a key.
  • Making a new key on every retry.
  • Checking for the key, then inserting it later, so two parallel retries both pass.
  • Saving the key outside the transaction that does the work.
  • Treating the same key with a different body as a normal request.

Security lens

Idempotency keys are not secrets, but scope them per user or per API account. Otherwise one customer could guess another's key and read a saved response. Also rate limit retries. A retry storm from a buggy client can look like an attack and overload the payment provider.
