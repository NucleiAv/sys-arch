Connection pooling, borrowing database connections

Opening a database connection is slow and each one uses memory on the server. Learn why apps borrow connections from a pool, how to size it with simple math, and what happens when the pool or the database runs out.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Before your app can run a query, it needs a connection to the database. Opening one is not cheap. It needs a TCP handshake, often a TLS handshake, a login check, and on PostgreSQL the server starts a new process for it.

If every request opened its own connection and closed it after, you would pay that cost every time, and a traffic spike would open thousands of connections at once. The database has a hard limit. PostgreSQL allows 100 by default.

A connection pool keeps a small number of connections open and lends them out. A request borrows a connection, runs its queries and returns it. The next request reuses it at once.

Think of it like this

A library does not print a new book for every reader. It keeps a few copies on the shelf. You borrow one, read, and bring it back. If all copies are out, you wait in line for a short time.

Words you need

Connection
An open, logged in link between your app and the database.
Connection pool
A set of open connections that the app reuses.
Pool size
The most connections the pool will open.
Acquire timeout
How long a request waits for a free connection before giving up.
Idle timeout
How long an unused connection stays open before the pool closes it.
PgBouncer
A separate pooler that sits in front of PostgreSQL and shares a few real connections among many clients.
Little's law
Busy items = arrival rate × time each item takes. Here, busy connections = queries a second × seconds per query.

How it works

Size the pool with Little's law

Connections busy at once = queries a second × seconds per query.

Queries a secondTime per queryBusy connections

2,0005 ms10
2,00050 ms100

Add headroom for spikes, often about double. A bigger pool is not always better. The database has a fixed number of CPU cores. Hundreds of active connections fight for those cores and the disk, and every query gets slower. A small pool with a short queue is often faster than a huge pool.

Count every pool, on every server

Total connections = pool size × app instances. 20 connections × 30 pods = 600, which is far over PostgreSQL's default of 100. Autoscaling the app can break the database this way.

Two places to pool

WhereExampleGood for
Inside the appHikariCP for Java, SQLAlchemy pool for PythonOne app with a few instances
In front of the databasePgBouncer, RDS ProxyMany instances or serverless functions

PgBouncer has three modes. Session gives a client a server connection for its whole session. Transaction gives it one only during a transaction, which shares connections far better. Statement gives one per statement and is rarely used. Transaction mode breaks features that depend on the session, such as session level settings and some uses of prepared statements, so check before you switch.

Settings that matter

  • Acquire timeout. Fail fast, about 1 to 3 seconds, rather than piling up requests.
  • Max lifetime. Recycle connections now and then, so a database failover or a firewall that drops idle links does not leave dead connections.
  • Validation. Check a connection is alive before lending it, or after an error.
Key point

When the pool is exhausted, the real problem is usually slow queries or a leak, not a small pool. Fix the slow query first.

Real life scenarios

Serverless meets PostgreSQL

A team moved an API to serverless functions. Each function instance opened its own connection. A traffic spike started 800 instances and the database refused connections at 100. A pooler in front of the database, such as RDS Proxy, shared a small number of real connections among them.

The leak

A code path forgot to return its connection when an exception was thrown. The pool slowly emptied over a day and then every request timed out. Using a with block that always returns the connection fixed it, and a leak detection setting in the pool now logs any connection held longer than 10 seconds.

Trade-offs

ChoiceGood atCosts you
Small poolDatabase stays fast, fair queueing.Requests wait during spikes.
Large poolFewer waits in the app.Database overloaded by too many active queries.
App side poolSimple, no extra hop.Total connections grow with every instance.
External poolerCaps connections for the whole fleet.One more component, some session features limited.

Common mistakes

  • Opening a new connection for every request.
  • Setting pool size without multiplying by the number of instances.
  • Making the pool huge to hide slow queries.
  • Not returning connections on errors.
  • No acquire timeout, so requests wait forever.

Security lens

Each pool logs in with a database user. Give that user only the rights the app needs, and keep its password in a secrets manager, rotated on a schedule. Use TLS between the pool and the database. A pooler in front of the database is also a good place to cap connections, so a bug or an attacker cannot exhaust the database.
