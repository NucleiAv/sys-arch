Secure by design and security in system architecture

Security is cheapest when it is part of the first drawing. Learn how systems engineering models place security in every phase, and how to read an architecture for trust boundaries, attack surface and weak spots.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Secure by design means you plan security from the first day, the same way you plan for weight or power. You do not wait for testers to find holes at the end.

The reason is money and time. A missing check found on a whiteboard costs one meeting. The same missing check found after 10,000 incubators are in hospitals costs a recall, a regulator report and maybe harm to a patient.

As an architect you look at the drawing of the system and ask four things.

  1. What are the parts and the data flows?
  2. Where are the trust boundaries? Places where data moves between parts that trust each other differently.
  3. What is the attack surface? Every way in.
  4. What happens when one part is broken into? How far can an attacker move?
Think of it like this

Building a house with a safe room is easy if you draw it in the plan. Adding a safe room after the house is built means breaking walls.

Words you need

Secure by design
Security is planned and built in from the start, and products are safe by default.
Systems engineering
A way to build complex systems by moving from needs to requirements, design, build and test in clear phases.
V model
A systems engineering model. The left side goes down from needs to design. The right side goes up through tests that check each level.
Shift left
Doing security work earlier in the life cycle, where fixes are cheaper.
Trust boundary
A line where data or commands pass between parts with different trust.
Attack surface
All the ways an attacker can try to interact with the system.
Blast radius
How much harm one broken part can cause.
Zero trust
No part is trusted because of its network location. Every request is checked.
Segmentation
Splitting a network into zones with rules between them.

How it works

The V model with security

Left side, define and designRight side, verify and validate
Needs and concept. Find assets and threats.Acceptance. Pen test against the real use case.
System requirements. Write security requirements.System test. Test every security requirement.
Architecture. Threat model the design.Integration test. Test trust boundaries and interfaces.
Detailed design. Choose controls per part.Unit test. Test input checks and crypto calls.
Code. Secure coding rules, code review.Static analysis and review results.

Each level on the left has a matching test level on the right. Agile teams do the same work in small loops instead of one big pass.

Drivers and principles of secure design

  • Drivers. Patient safety, laws, customer contracts, brand trust and cost of incidents.
  • Minimize attack surface. Turn off unused ports, services and features. Every open thing is a way in.
  • Secure defaults. Ship with security on. No default passwords. The US agency CISA calls this out in its Secure by Design pledge.
  • Zero trust. Do not trust a request because it comes from inside the network. NIST SP 800-207 describes this model.
  • Segmentation. Put devices in their own zone. IEC 62443 calls these zones and conduits.
  • Fail safe. When something breaks, go to a safe state. An incubator that loses its network keeps heating to the last safe setting and sounds an alarm.

Why security is hard in real projects

  • Deadlines push security to "later", and later never comes.
  • Devices live 10 to 15 years, but the software inside them ages in 2.
  • Many parts come from suppliers you do not control.
  • Security work is invisible when it succeeds, so it is hard to show its value.
  • Usability and safety can pull against security. A locked screen must not stop a nurse in an emergency.
Key point

A good security architect does not say "no". They say "yes, if", and offer a design that meets the business goal with acceptable risk.

Real life scenarios

Target breach, 2013

Attackers stole login details from a heating and air conditioning vendor. That vendor's access let them reach the network that also held the payment terminals. About 40 million card numbers were stolen. Segmentation between vendor access and payment systems would have limited the blast radius.

Jeep Cherokee, 2015

Researchers reached a car's media system over the mobile network and from there sent commands to the brakes and steering. The car had no strong boundary between entertainment and driving systems. The maker recalled 1.4 million vehicles.

Secure by Design pledge, 2024

Many software makers signed a pledge with the US agency CISA. They promised goals like more MFA, fewer default passwords and whole classes of bugs removed. It moved security from the customer's job to the maker's job.

Trade-offs

ChoiceGood atCosts you
Strong segmentationSmall blast radius.More network rules to manage, harder troubleshooting.
Zero trustNo free pass for insiders.Needs identity for every user, device and service.
Small attack surfaceFewer ways in.Fewer features or remote tools that support teams like.
Fail safe statesProtect people when things break.A safe state may stop normal work for a while.

Common mistakes

  • Drawing the architecture without trust boundaries.
  • Trusting everything inside the hospital or company network.
  • Leaving debug and service ports open in the shipped product.
  • Sending more data to the cloud than the feature needs.
  • Saying "no" to the business instead of offering a safer "yes, if".
