Securing agents that run on their own

An agent that runs at night with real permissions is a new kind of insider. It can be tricked by what it reads, it can make mistakes at machine speed, and nobody is watching. Learn the controls that let agents act independently while keeping the damage small when something goes wrong.

The idea in one minute

Securing an agent is not mainly about the model. It is about the system around it. Assume the model can be confused or tricked by prompt injection, lesson 8.6. Then ask what the worst thing is that the agent could do, and make that small.

A useful rule, named by Simon Willison in 2025, is the lethal trifecta. An agent is in serious danger when it has all three of these at once.

  1. Access to private data.
  2. Exposure to untrusted content, such as web pages, emails or tickets from outsiders.
  3. A way to communicate externally, such as sending email, calling URLs or posting messages.

With all three, an attacker can plant instructions in content, make the agent read private data, and send it out. Remove any one leg for a given task and that path closes.

The other controls are familiar from earlier levels, applied to a non human actor. Give each agent its own identity with least privilege. Run code in a sandbox. Limit network egress. Require human approval for risky actions. Set budgets. Log everything, and keep a kill switch.

Think of it like this

A new intern works the night shift alone. You give them a badge that opens only the rooms they need, a spending limit, a rule to call the manager before any big decision, and cameras in the hallways. If something goes wrong, the damage is small and you can see what happened.

Words you need

Lethal trifecta
Private data, untrusted content and external communication together in one agent.
Agent identity
A separate, non human identity for each agent, with its own credentials and permissions.
Scoped token
A short lived credential limited to specific resources and actions.
Policy engine
Code that decides whether an action is allowed, outside the model.
Sandbox
An isolated environment for running code, with limited files, network and resources.
Egress control
Rules on which outside hosts a system may connect to.
Kill switch
A fast way to stop one agent, or all of them.
Dual LLM pattern
A privileged model that never sees untrusted text, and a quarantined model that reads it but cannot use tools.

Break the lethal trifecta

For each task, check the three legs. A research agent that browses the web should not also hold customer data and a send email tool. Split it into separate agents with separate permissions, or remove one leg, for example by requiring a person to send any external message.

Separate trusted and untrusted text

  • Dual LLM pattern. A privileged LLM plans and calls tools but never reads untrusted content. A quarantined LLM reads untrusted content and returns results as opaque values that the privileged side handles without interpreting.
  • Google DeepMind's CaMeL design, published in 2025, builds on this idea. Code tracks where each value came from and checks policies before tools run.

These designs reduce flexibility, but they turn "hope the model resists" into "the system will not allow it".

Trust in tools and MCP servers

Every tool or MCP server an agent uses is part of its supply chain. A malicious or compromised server can return injected instructions or misuse the credentials it is given. Install only reviewed servers, pin versions, give each server its own narrow credentials, and log its traffic.

Agents inside real systems

  • Agents should call the same APIs as other clients, through the same authentication, authorization and rate limits, lesson 4.3.
  • Run agents on queues and workflows with durable state, lesson 8.4, so they can be paused, retried and audited.
  • Treat agent actions like deployments. Start read only, then allow low risk writes, then expand step by step as evals and logs show it is safe.
Key point

Do not ask "will the model behave?". Ask "if the model is fully tricked, what can it reach, what can it change, and where can data go?". Make each answer small.

Real life scenarios

The coding assistant extension, 2025

In July 2025 a malicious change was merged into the Amazon Q Developer extension for VS Code and shipped in one release. It added a prompt telling the agent to delete files and cloud resources. Amazon pulled the version and said no customer resources were affected. It showed that agent instructions are part of the software supply chain.

Simon Willison names the trifecta

In 2025 Simon Willison described the lethal trifecta to explain why many agent data leaks share one shape. It gives architects a quick test for any agent design.

A safe rollout

A bank gave its operations agent read only access first, logged every proposed action, and had staff approve them for a month. Only actions with a near perfect approval record were then automated.

Trade-offs

ChoiceGood atCosts you
Human approval for many actionsStrong safety.Slow, people get tired and approve without reading.

Common mistakes

  • Running agents with a human's credentials or an admin account.
  • Long lived tokens with broad scopes.
  • Combining private data, untrusted content and outbound messaging in one agent.
  • Letting the sandbox reach the whole internet.
  • No alert when an agent is repeatedly denied.

Security lens

This lesson is about security. Add each agent to your threat model as an actor that may be under attacker control. Review its identity and scopes like any service account, include agent abuse cases in red teaming and evals, and make sure your incident response plan, lesson 6.9, covers "stop all agents and revoke their tokens".
