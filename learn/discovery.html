Service discovery, health checks and stale lists

In the cloud, servers come and go every minute and their addresses change. Learn how services find each other through a registry, how health checks remove dead copies, and why a crashed server can still get traffic for a while.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

When the order service wants to call the payment service, it needs an address, such as 10.0.3.17:8080. With one server you could write that in a config file. With 20 copies that scale up and down, crash and move, a fixed list is always out of date.

Service discovery keeps a live list. Each copy of a service registers itself in a registry when it starts and sends a heartbeat every few seconds. If heartbeats stop, the registry removes it. Callers ask the registry for the current list and pick one copy.

There is a catch. Callers usually cache the list for a short time, so they do not ask the registry on every request. After a crash, traffic can still go to the dead copy until the registry notices and the cache expires. Good clients also retry on another copy.

Think of it like this

A taxi stand keeps a board of which drivers are free. Drivers wave every minute to show they are still there. If a driver stops waving, the board removes them. But a customer who looked at the board two minutes ago may still walk to a car that already left.

Words you need

Service registry
A database of which copies of each service are running and where.
Registration
A copy adding itself to the registry when it starts.
Heartbeat
A small regular message that says I am still alive.
Health check
A test, such as calling /health, that decides if a copy should get traffic.
Client side discovery
The caller gets the list and picks a copy itself.
Server side discovery
The caller sends to a load balancer or proxy, which picks a copy.
Readiness
Whether a copy is ready for traffic right now, for example warmed up and connected to its database.

How it works

Two styles

StyleHowExamples
Client sideCaller asks the registry and load balances itselfConsul with a client library, Netflix Eureka
Server sideCaller calls one stable name, a proxy picks a copyKubernetes Services, cloud load balancers, service meshes

How Kubernetes does it

A Service gives a set of pods one stable name and virtual IP, such as payments.shop.svc.cluster.local. Kubernetes tracks the pods behind it in EndpointSlices. Only pods whose readiness probe passes are added. Cluster DNS answers the name, and the node's proxy forwards traffic to a ready pod. You rarely run a separate registry inside Kubernetes.

Health checks that tell the truth

  • Liveness. Is the process stuck? If it fails, restart it.
  • Readiness. Can it serve right now? If it fails, stop sending traffic but do not restart.
  • Keep checks cheap. Do not make readiness depend on every other service, or one outage takes everything out of rotation.

Timing is a trade-off

Time to stop sending traffic to a dead copy is roughly missed heartbeats × interval + cache time. 3 × 5 s + 30 s is up to 45 seconds. Shorter values react faster but add load and can remove copies that only had a short pause. Clients should add retries on another copy with a timeout, and a load balancer can do outlier detection, removing a copy that returns many errors.

DNS as discovery

DNS is the simplest registry. Clients and resolvers cache answers for the record's TTL. Some language runtimes cache DNS longer than the TTL by default, so check your runtime's settings.

Shutting down gracefully

Before a copy stops, it should fail its readiness check, wait for callers to notice, finish the requests it already has, and only then exit. Otherwise every deploy causes a burst of errors.

Key point

Discovery is eventually consistent. Design callers to expect a few dead addresses and to retry elsewhere.

Real life scenarios

Netflix Eureka

Netflix built Eureka for client side discovery in AWS, where instances come and go often. Clients cache the registry and keep working even if the registry is briefly unreachable, choosing availability over a perfectly fresh list.

Errors on every deploy

A team saw a spike of connection errors each time they deployed. Pods were killed at once, while callers still had them in their lists. Adding a preStop wait and failing readiness first removed the spike.

The cached DNS answer

An app kept calling an old database address for hours after a failover, because its runtime cached DNS answers far longer than the record's TTL. Setting the runtime's DNS cache time fixed it.

Trade-offs

ChoiceGood atCosts you
Short heartbeat and cache timesDead copies leave fast.More load on the registry, more false removals.
Client side discoveryNo extra hop, smart client balancing.A library in every language you use.
Server side discoverySimple clients, one stable name.An extra hop and a component that must be highly available.
DNS based discoveryWorks everywhere, nothing new to run.Caching makes changes slow to spread.

Common mistakes

  • Hard coding IP addresses of other services.
  • No retry on another copy when a call fails to connect.
  • Readiness checks that call every downstream service.
  • Killing pods without draining them first.
  • Trusting DNS changes to apply at once.

Security lens

A registry decides where traffic goes, so protect it. Require authentication to register, or an attacker could add their own server as a copy of the payment service and receive real requests. Use mutual TLS between services, so a caller checks the identity of the copy it reached, not only its address.
