Machine learning systems, from data to a live model

A model is a small part of a machine learning system. Most of the work is the data around it. Learn how data becomes a trained model, how the model serves live requests, and why a model that was right last month can be wrong today.

The idea in one minute

A machine learning model is a program whose behaviour is learned from examples instead of written by hand. Show it thousands of past card payments marked "fraud" or "not fraud", and it learns patterns that score new payments.

An ML system has two halves.

  1. Training, offline. Collect data, turn it into features, train a model, test it and save it in a model registry.
  2. Inference, online. A live request arrives, the system builds the same features, runs the model and returns a prediction in milliseconds.

The two halves must agree. If training computes "payments in the last hour" one way and the live service computes it another way, the model sees numbers it never learned from. This is called training and serving skew.

The world also changes. Shopping habits, fraud tricks and prices move, so the data a model sees in production slowly stops looking like the data it was trained on. This is drift. ML systems must be monitored and retrained, not built once.

Think of it like this

A model is like a student who learned from old exam papers. If the teacher changes the style of questions, the student starts to get answers wrong. You must check the student's results and give them new papers to study.

Words you need

Model
A function learned from data that maps inputs to a prediction.
Training
Fitting the model to past examples.
Inference
Using a trained model to predict for new inputs.
Feature
An input value the model uses, such as account age or payments in the last hour.
Label
The right answer for a training example, such as fraud or not fraud.
Feature store
A system that computes and serves features the same way for training and live predictions.
Model registry
A store of model versions with their data, code, settings and test results.
Training and serving skew
Differences between features in training and in production.
Drift
Production data or the meaning of labels changing over time, so the model gets worse.
MLOps
Practices for building, deploying and running ML systems reliably, like DevOps for models.

Online or batch predictions

  • Online. A request needs an answer now, such as a fraud score at checkout. Latency budget is tight.
  • Batch. Score everything every night, such as "which customers may leave". Results go into a table. Cheap and simple.

Pick batch when the answer can be a few hours old.

Test a model honestly

Split data into training and test sets, and for data over time, test on a later period than training. Otherwise the model can look great by remembering answers or by seeing the future. Compare against a simple baseline, such as "block every payment over 50,000", to prove the model adds value.

Watch three things in production

  1. Inputs. Are feature values shifting? Many nulls? A broken upstream field?
  2. Outputs. Is the share of high scores suddenly different?
  3. Outcomes. When true labels arrive, often days later, is accuracy falling?

Roll out models like code

Shadow mode first, where the new model scores live traffic but its answers are not used. Then a canary with a small share of traffic. Keep the old version ready for instant rollback.

Key point

Most ML failures are data failures. A missing field, a changed unit, or a feature computed differently online will hurt more than a weaker algorithm.

Real life scenarios

Uber's Michelangelo

Uber described its ML platform, Michelangelo, in 2017. It popularized the feature store idea, so features were defined once and used the same way in training and in live predictions across many teams.

Zillow's home buying

In 2021 Zillow closed its business of buying and reselling homes, which relied on price forecasts, after large losses in a fast changing housing market. It is often cited as a lesson in how models trained on the past can fail when conditions shift.

The changed unit

A delivery app's ETA model suddenly predicted 60 times too long. An upstream team had changed a field from minutes to seconds. Input monitoring with range checks would have caught it within minutes.

Trade-offs

ChoiceGood atCosts you
Online predictionsFresh answers per request.Tight latency, live features needed.
Batch predictionsSimple and cheap.Answers can be hours old.
Frequent retrainingFollows change quickly.More cost and more chances to ship a bad model.
Complex modelHigher accuracy in tests.Harder to explain, serve and debug.

Common mistakes

  • Computing features one way in training and another way in production.
  • Testing on random rows when the data is ordered by time.
  • No baseline, so nobody knows if the model helps.
  • Deploying a model with no monitoring of inputs and accuracy.
  • No way to roll back to the previous model.

Security lens

Training data is an attack surface. If attackers can add or change examples, they can poison the model, for example by making their own fraud look normal. Control who can write to training data, track where data came from, and test new models on trusted held out sets. Models can also leak training data, so avoid training on secrets and personal data you do not need. See lesson 8.6.
