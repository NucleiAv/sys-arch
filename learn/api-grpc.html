gRPC and Protocol Buffers, fast calls between services

Inside a company, services call each other millions of times a second. gRPC makes those calls fast, typed and easy to write. Learn the .proto contract, the four call types and deadlines.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

gRPC is a framework for one program to call a function in another program over the network, as if it were a local function. This idea is called a remote procedure call, or RPC. Google made gRPC open source in 2015.

You describe the service once in a .proto file, using Protocol Buffers, or protobuf. A tool then generates client and server code in many languages. Messages travel as compact binary data over HTTP/2.

Think of it like this

Two friends who speak different languages share one dictionary. Each friend uses it to turn words into a short code and back. The .proto file is the dictionary. The short codes are small and fast to send.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

RPC
Remote procedure call. Calling a function that runs on another machine.
Protocol Buffers
Google's format to define and encode structured data in compact binary.
.proto file
The contract file that defines messages and services.
Stub
The generated client code that you call like a normal function.
HTTP/2
A newer version of HTTP that sends many requests at once over one connection, with binary frames.
Streaming
Sending many messages over one call, in one or both directions.
Deadline
The latest time by which a call must finish. After it, the call is cancelled.
Status code
gRPC's own result codes, such as OK, NOT_FOUND, UNAVAILABLE and DEADLINE_EXCEEDED.
gRPC-Web
A variant that lets browsers call gRPC services through a proxy.

How it works

The contract

syntax = "proto3";
package shop;

service Inventory { rpc Reserve (ReserveRequest) returns (ReserveReply); rpc WatchStock (StockQuery) returns (stream StockUpdate); }

message ReserveRequest { string sku = 1; int32 qty = 2; } message ReserveReply { bool ok = 1; int32 left = 2; } ```

The numbers, such as = 1, are field numbers. They go on the wire instead of field names. That is one reason protobuf is small. Never reuse or change a field number. Add new fields with new numbers. Then old and new clients keep working.

Four kinds of call

KindClient sendsServer sendsExample
UnaryOne messageOne messageReserve stock
Server streamingOne messageMany messagesWatch stock changes
Client streamingMany messagesOne messageUpload sensor readings
Bidirectional streamingMany messagesMany messagesChat between two services

Deadlines and status codes

Always set a deadline. If the checkout gives inventory 200 ms, inventory knows when to stop. Deadlines pass down the chain, so deeper services stop too. Failed calls return a status code, such as UNAVAILABLE, which is safe to retry, or INVALID_ARGUMENT, which is not.

gRPC in browsers

Browsers cannot use all the HTTP/2 features gRPC needs. Use gRPC-Web with a proxy, or put a REST or GraphQL layer in front for browsers.

Key point

A common pattern. REST or GraphQL at the edge for apps and partners, gRPC inside between services.

Real life scenarios

Google's internal RPC

gRPC grew from Stubby, the RPC system Google used inside its data centers for many years. It was designed for very high call volumes between services.

A field number reused by mistake

A team removed field 3, then later added a new field with number 3 and a different type. Old services read garbage from it. The rule is to mark removed numbers as reserved.

Deadlines stop a pile up

Without deadlines, a slow pricing service made checkout calls wait for 30 seconds. With a 300 ms deadline passed down every call, the system failed fast and stayed up.

Trade-offs

ChoiceGood atCosts you
gRPCFast, small messages, typed contracts, streaming, code generation.Not human readable, browsers need gRPC-Web, needs HTTP/2.
REST with JSONReadable, works everywhere, easy to debug with curl.Bigger messages, no enforced contract unless you add OpenAPI.
Protobuf field numbersSafe evolution of messages.Rules you must follow strictly.

Common mistakes

  • Calls without deadlines.
  • Reusing or changing protobuf field numbers.
  • Exposing gRPC directly to browsers without gRPC-Web or a gateway.
  • Retrying calls that are not safe to repeat.
  • Long lived HTTP/2 connections behind a layer 4 load balancer, so all calls go to one server. Use client side or layer 7 balancing.

Security lens

gRPC is often used inside a network, where teams relax. Do not.

  • Use TLS, and mutual TLS between services, so each side proves its identity.
  • Check authorization in each method, using the caller's verified identity from the certificate or token.
  • Set message size limits and deadlines, so one slow or huge call cannot tie up a server.
  • Reflection helps debugging but shows your whole API. Turn it off where it is not needed.
  • Protobuf does not validate business rules. A field can still hold a negative amount. Validate values in code.
