Inside a database, indexes and storage engines

Why does one query take 2 ms and another 20 seconds? Learn how databases find data with indexes, how they write it safely, and the two big designs for storing it.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Without help, a database finds a row by reading every row, one by one. That is a full table scan. Fine for 1,000 rows, terrible for 100 million.

An index is a sorted list that points to where each row lives, like the index at the back of a book. With an index on email, finding one user out of 100 million takes a few steps instead of 100 million.

But indexes are not free. Every insert or update must also update every index. More indexes mean faster reads and slower writes.

Think of it like this

Finding "photosynthesis" in a textbook by reading every page takes hours. The index at the back says page 142. But every time the book gets a new page, someone must update the index too.

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Index
A sorted structure that points to rows, so lookups skip most of the table.
B-tree
The most common index. A wide, shallow tree of sorted pages. Great for lookups and ranges.
Composite index
An index on several columns, like (user_id, created_at). Order matters.
WAL
Write-ahead log. The database writes every change to an append-only log first, so it can recover after a crash.
LSM tree
Log-structured merge tree. Writes go to memory and are flushed to sorted files, which are merged later. Very fast writes.
Compaction
Merging LSM files in the background to remove old versions and keep reads fast.
Query plan
The steps the database chooses to answer a query. EXPLAIN shows it.

How it works

Writing safely, the write-ahead log

When you save something, the database first appends a note to the write-ahead log on disk, "set balance of account 7 to 50". Appending is fast. Then it updates the real data pages later. If the power dies, it replays the log on restart. This is how databases keep the durable promise. Replicas, lesson 2.3, are fed from this same log.

Indexes, the practical rules

  1. Index the columns you search and join on, like user_id and email.
  2. For "my latest posts", index (user_id, created_at). The first column filters, the second sorts.
  3. A composite index on (a, b) helps queries on a and on a and b, but not on b alone.
  4. Do not index everything. Each index costs disk and slows writes.
  5. Use EXPLAIN to see if the database actually uses your index.
Key point

An inverted index is the special index search engines use. It maps each word to the list of documents that contain it. You will meet it in the autocomplete design.

Real life scenarios

A dashboard that took 40 seconds

The query filtered orders by shop_id and sorted by date, with no index. Adding an index on (shop_id, created_at) made it take 30 ms.

Writes slowed down after a growth spurt

A table had 14 indexes, many unused. Every insert updated all 14. Dropping 9 unused ones made inserts three times faster.

Choosing RocksDB for a metrics store

A team stored a million metric points a second. A B-tree database could not keep up with the random writes. An LSM engine turned them into sequential writes and handled the load.

Trade-offs

ChoiceGood atCosts you
More indexesFaster reads for more kinds of query.Slower writes and more disk.
Fewer indexesFast writes, less disk.Some queries scan the table.
B-tree engineSteady, fast reads and ranges.Heavy random writes cost more.
LSM engineVery fast writes.Reads may touch several files. Compaction needs spare disk and CPU.

Common mistakes

  • Adding an index for every column just in case.
  • Building a composite index in the wrong column order.
  • Putting a function on an indexed column, like LOWER(email), so the index cannot be used.
  • Paging with huge offsets, which makes the database walk past many rows.
  • Forgetting that an index on a column with only two values, like is_active, rarely helps.

Security lens

Indexes and storage engines have security edges too.

  • Deleted rows may stay on disk until compaction or vacuum. Use encryption at rest so leftovers on old disks are unreadable.
  • Search indexes and replicas copy data. Apply the same access control and encryption to every copy.
  • A slow, unindexed query can be a denial of service. Limit query time and page size.
