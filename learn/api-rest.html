REST APIs in depth, HTTP the way it was meant

REST is the most common way to build web APIs. Learn the ideas behind it, the HTTP methods and headers it uses, how caching and CORS work, and how to describe an API with OpenAPI.

The idea in one minute

REST means Representational State Transfer. Roy Fielding described it in his PhD thesis in 2000. It is a set of rules for web APIs, not a product or a library.

In REST, everything is a resource, a thing with a name. A user, an order or a photo is a resource. Each resource has a URL, such as /orders/42. You do things to resources with the normal HTTP methods, such as GET to read and DELETE to remove. The server sends back a representation of the resource, usually as JSON.

Think of it like this

A library has shelves with labels. The label is the URL. The book is the resource. You can ask to read a book, add a new book or remove a book. You always use the same few actions, whatever the book is. That is REST.

Words you need

Resource
A thing with a name and a URL, such as /users/7.
Representation
The form the server sends a resource in, usually JSON.
JSON
JavaScript Object Notation. Text that holds data as keys and values, such as {"id": 42}.
Endpoint
One URL and method pair, such as POST /orders.
Header
A name and value line sent with a request or response, such as Content-Type: application/json.
Safe method
A method that does not change data. GET, HEAD and OPTIONS.
Idempotent method
Sending it many times has the same effect as once. GET, HEAD, PUT, DELETE and OPTIONS.
Stateless
Each request carries everything the server needs. The server keeps no session for the conversation.
ETag
A tag that names one version of a resource. Used to check if it changed.
CORS
Cross-Origin Resource Sharing. Rules that let a web page call an API on a different origin.
OpenAPI
A standard file format that describes a REST API, its paths, inputs and outputs.

How it works

The REST constraints

Fielding listed six rules. An API that follows them is "RESTful".

  1. Client and server. They are separate and change separately.
  2. Stateless. Each request has all the information that the server needs.
  3. Cacheable. Responses say if and how long you can keep them.
  4. Uniform interface. Same methods, URLs for resources, self describing messages.
  5. Layered system. Proxies, caches and gateways can sit in the middle.
  6. Code on demand. Optional. The server can send code, such as JavaScript.

Caching headers

  • Cache-Control: max-age=60 lets clients and caches keep it for 60 seconds.
  • Cache-Control: no-store forbids any copy. Use it for private data.
  • ETag and If-None-Match let a client ask "did it change?". The server answers 304 with no body if not.

CORS in plain words

A browser blocks a page on shop.example from reading responses from api.other.example, unless the API agrees. This is the same origin policy. For many requests, the browser first sends a preflight, an OPTIONS request. The API answers with headers like Access-Control-Allow-Origin: https://shop.example. CORS only affects browsers. It does not protect your API from other clients such as scripts.

Maturity, from not REST to REST

The Richardson maturity model has four levels. Level 0 sends everything to one URL. Level 1 has resources. Level 2 uses HTTP methods and status codes correctly. Level 3 adds links in responses, called HATEOAS. Most good public APIs are at level 2.

Key point

Describe your API in an OpenAPI file. Tools then make documentation, client libraries and tests from it.

Real life scenarios

A GET that deleted data

An old admin page used links like GET /delete?id=5. A search engine crawler followed every link and deleted many records. GET must never change data, because tools assume it is safe.

A news API saves bandwidth with ETags

Phones refresh the headlines every minute. With ETags, most refreshes get 304 Not Modified and no body. Data use dropped sharply.

The CORS error that was not a server bug

A team saw the API work in a terminal with curl but fail in the browser. The API did not return Access-Control-Allow-Origin for the web app's origin. One header fixed it.

Common mistakes

  • Changing data with GET.
  • Returning 200 for every error with a message in the body.
  • Verbs in paths, such as /createOrder, instead of POST /orders.
  • Fixing CORS errors with Access-Control-Allow-Origin set to all origins on an API that uses cookies.
  • No version and no description file, so clients guess.

Security lens

REST APIs fail in the same few ways again and again.

  • IDOR. GET /orders/1002 returns someone else's order. Check ownership on every request.
  • Mass assignment. The client sends "role": "admin" in a JSON body and the server saves it. Allow only listed fields.
  • Excessive data. The API returns the whole user object and the app hides fields. Attackers read the raw response. Return only what is needed.
  • Unsafe methods. Protect PUT, PATCH and DELETE more strictly than GET, and use CSRF protection when cookies carry the session.
  • CORS. Never reflect any origin with credentials allowed.
