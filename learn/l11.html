CDNs and object storage, big files done right

Photos, videos and app files are big and read all over the world. Store them in object storage and serve them from a CDN near every user.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Databases are built for small records, not 50 MB videos. Big files, also called blobs, go into object storage like Amazon S3, Google Cloud Storage or Azure Blob. It is cheap, almost never loses data and holds unlimited files. The database keeps only a small record that points to the file.

A CDN, content delivery network, is a set of servers in hundreds of cities. It keeps copies of your files close to users. A user in Chennai gets the image from a server in Chennai, not from your origin in Virginia.

Think of it like this

Object storage is a giant safe warehouse. A CDN is a corner shop in every town that keeps the popular items in stock, so nobody has to drive to the warehouse.

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Object storage
Stores files, called objects, by key in buckets. Cheap, durable, huge. S3 is the best known.
Bucket
A container of objects with its own access rules.
Presigned URL
A link with a signature and an expiry that allows one upload or download without your server in the middle.
CDN
Servers around the world that cache and serve your content near users.
Edge
A CDN server in a city near users. Also called a point of presence.
Origin
Where the CDN fetches the real file from, like your bucket or web server.
Cache busting
Putting a version in the file name, like app.3f9a.js, so a new version gets a new URL.
Durability
How unlikely it is to lose data. S3 is designed for eleven nines, 99.999999999 percent.

How it works

Why not keep files on the app server or in the database?

App servers come and go, so local files vanish. Databases get huge, slow and costly to back up with blobs inside. Object storage is built for exactly this, and the database just keeps a pointer.

Push or pull CDN

  • Pull CDN. The edge fetches from the origin on the first request, then caches. Zero setup, the usual choice.
  • Push CDN. You upload files to the CDN ahead of time. Good for big releases like a game patch everyone downloads at once.

Getting updates out

Cached files may live at the edge for days. To change a file, either purge it from the CDN, or better, give the new version a new name with cache busting, logo.v2.png. The HTML points to the new name and old copies simply stop being used.

Storage classes

Object storage has tiers. Hot for files read often, infrequent access for older files, archive for files almost never read, at a fraction of the price but slow to fetch. Lifecycle rules move files down automatically, for example after 90 days.

Key point

CDNs are not just for images. They also absorb attacks, end TLS near users, and can cache API responses that are the same for everyone.

Real life scenarios

Netflix puts servers inside internet providers

Netflix built its own CDN, Open Connect, with boxes placed inside internet providers' networks. Most video bytes travel only a short distance, which saves money and makes streams start fast.

An app server disk fills with uploads

A small startup saved user videos to the app server. The disk filled, the server crashed, and a replacement server had none of the files. Moving uploads to S3 with presigned URLs fixed both problems.

A logo that would not update

A company changed its logo but kept the file name logo.png. Users saw the old one for a week because the CDN cached it for 7 days. With versioned names, the switch is instant.

Trade-offs

ChoiceGood atCosts you
Pull CDNNo setup, caches what is actually used.First request in each area is slow.
Push CDNReady before the rush.You manage uploads and storage on the CDN.
Long CDN TTLVery high hit ratio, cheap.Hard to update unless you version names.
Direct upload with presigned URLServers stay light, scales easily.Upload checks must happen after the fact, like scanning files.
Archive storageVery cheap.Slow and costly to read back.

Common mistakes

  • Streaming large uploads through your app servers.
  • Storing images as blobs inside the main database.
  • Making a bucket public by mistake. Many data leaks start here.
  • Caching personal or logged in pages on a CDN with the wrong cache rules.
  • Overwriting files with the same name and fighting the CDN cache.

Security lens

Public storage buckets are one of the most common breach causes.

  • Block public access by default and share files with signed URLs that expire.
  • Scan uploads for malware and check file types by content, not by name.
  • Serve user uploads from a separate domain so a harmful file cannot run scripts on your main site.
  • Turn on versioning and object lock for important data, so ransomware cannot delete it.
