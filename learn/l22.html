Batch and stream processing, making sense of big data

Apps produce mountains of events. Some questions can wait until tonight, others need an answer in seconds. Learn the two ways to process big data and how they fit together.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Every click, view, payment and sensor reading is an event. Turning billions of events into useful answers, like top songs this week or fraud right now, is data processing.

Batch processing collects data over a period, then crunches it all at once. "Every night, count yesterday's sales by city." Simple, thorough, but the answer is hours old.

Stream processing handles each event as it arrives. "Flag a card used in two countries within 10 minutes." Answers in seconds, but harder to build correctly.

Think of it like this

Batch is doing all your laundry on Sunday. Stream is washing each sock the moment it gets dirty. Sunday laundry is easier. Instant washing means you always have clean socks.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Batch processing
Processing a large, fixed set of data in one run, often on a schedule.
Stream processing
Processing events continuously as they arrive.
MapReduce
Split work into map steps that run in parallel on pieces of data, then reduce steps that combine results.
Data lake
Raw data stored cheaply as files, usually in object storage.
Data warehouse
Cleaned, structured data built for analytics queries. BigQuery, Snowflake, Redshift.
ETL
Extract, transform, load. Moving data from sources, cleaning it, and loading it somewhere useful.
Window
A slice of time a stream job groups events by, like every 5 minutes.
Event time
When the event actually happened, versus when it was processed.
Watermark
The stream system's guess that it has seen all events up to a certain time.
CDC
Change data capture. Turning every database change into an event.

How it works

MapReduce in one picture

To count words in a billion documents, the map step runs on many machines, each turning its documents into pairs like (cat, 1). The shuffle groups all pairs with the same word together. The reduce step adds them up, (cat, 48211). Spark does the same idea much faster by keeping data in memory.

Windows in streams

WindowExample
Tumbling, fixed and not overlappingPlays per minute
Sliding, overlappingAverage over the last 10 minutes, updated every minute
Session, based on gapsOne user's visit, ends after 30 minutes of quiet

Late events

A phone in a tunnel sends events 10 minutes late. Should they count in the window when they happened, or when they arrived? Good stream systems use event time and watermarks to wait a little for stragglers, and update results when late events arrive.

Architectures

  • Lambda architecture. Run both a batch path for exact results and a stream path for fast ones, then merge. Powerful, but two codebases.
  • Kappa architecture. Only a stream path. To recompute, replay the event log from the start. One codebase.

Change data capture

Instead of apps writing to both the database and the event log, CDC tools like Debezium read the database's own log and publish each change as an event. This keeps search indexes, caches and warehouses in sync without extra code in the app.

Key point

Keep raw events forever in cheap storage if you can. Bugs in processing are common, and with raw events you can always fix the code and recompute.

Real life scenarios

Google's MapReduce

Google described MapReduce in 2004 to build its search index from the whole web on thousands of cheap machines. Hadoop copied the idea and started the big data era.

Fraud detection in seconds

Card companies run stream jobs that score every transaction as it happens, checking things like many purchases in a short time or two distant countries within minutes, and block suspicious ones before they complete.

Uber's real time pricing

Surge pricing needs supply and demand per small area every minute. Stream processing over rider and driver events computes it continuously.

Trade-offs

ChoiceGood atCosts you
BatchSimple, exact, easy to rerun.Results are hours old.
StreamResults in seconds.Harder, late and duplicate events, state to manage.
LambdaFast and exact answers.Two code paths to keep in agreement.
KappaOne code path, replay to fix.Needs a long retained, replayable log.
Data warehouseFast analytics with SQL.Data must be modelled and loaded first.

Common mistakes

  • Running heavy analytics queries on the main production database.
  • Using processing time when event time matters, so late events land in the wrong window.
  • Throwing away raw events and losing the ability to recompute.
  • Building a stream pipeline when a nightly batch would answer the question fine.
  • Not handling duplicate events in at least once pipelines.

Security lens

Data pipelines copy data everywhere, which multiplies privacy risk.

  • Minimize what you collect, and drop or hash personal fields early.
  • Control who can query the warehouse. Analysts rarely need names.
  • Track lineage, where each field came from, so you can delete a person's data on request.
  • Streams can also power security, for example real time fraud and anomaly detection.
