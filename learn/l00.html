System design versus system architecture

People often use the two words as if they mean the same thing. They overlap, but they are not the same. Learn what each word means, where one stops and the other starts, and how architects draw both.

The idea in one minute

System architecture is the big shape of a system. It names the main parts, the job of each part, and how the parts connect. It also records the big decisions that are hard to change later.

System design is the more detailed work inside that shape. It decides how each part does its job. It picks the data model, the API, the algorithms and the exact tools.

The two overlap. A "system design interview" asks for both. You draw the architecture first, then you design the important parts in detail.

Think of it like this

Think of a new school building. The architecture says "two floors, classrooms on the left, a hall in the middle, the kitchen next to the hall". The design says "this classroom has 30 desks, the kitchen has two ovens, the doors open outward". You need both. You do the architecture first, because it is hard to move a wall after you build it.

Words you need

Architecture
The main parts of a system, their jobs, their connections, and the rules and decisions that are hard to change.
Design
The detailed decisions about how each part works, such as data models, APIs and algorithms.
High level design
HLD. The boxes and arrows view of the whole system. Mostly architecture.
Low level design
LLD. The detail of one part, such as classes, tables and functions.
Quality attribute
A property the whole system must have, such as speed, availability or security. Also called a non-functional requirement.
Architectural style
A known pattern for the big shape, such as client server, monolith, microservices or event driven.
ADR
Architecture decision record. A short document that records one decision, the reason for it and what you gave up.
C4 model
A way to draw software at four zoom levels. Context, containers, components and code.

How it works

A formal definition

The standard ISO/IEC/IEEE 42010 says that architecture is the fundamental concepts or properties of a system in its environment. These show in its elements, its relationships and the principles of its design and change. In simple words, architecture is about the parts, the links and the rules.

Where one stops and the other starts

QuestionArchitectureDesign
Which main parts do we have?Yes
How do the parts talk, calls or events?Yes
Which part owns which data?Yes
What are the columns of the orders table?Yes
Which cache keys do we use, with which TTL?Yes
Which algorithm makes short codes?Yes
How fast and how available must the whole system be?YesIt must meet it
Key point

A simple test. If a choice is expensive to change later and affects many parts, it is architecture. If you can change it inside one part without telling the other teams, it is design.

Common architectural styles

  • Client server. Clients ask, servers answer. Almost every app uses it.
  • Layered. Presentation, business logic and data access sit in separate layers.
  • Monolith. One program that you deploy as one unit.
  • Microservices. Many small services. Each service owns one business area and its data. See lesson 4.4.
  • Event driven. Parts publish events and other parts react. See lesson 3.2.
  • Serverless. You give the cloud small functions and it runs them on demand.

Draw it at four zoom levels, the C4 model

  1. Context. Your system as one box, with its users and the outside systems.
  2. Containers. The apps and data stores inside, such as a web app, an API and a database.
  3. Components. The main pieces inside one container.
  4. Code. Classes and functions. Draw this only when it helps.

Record decisions

Write one short ADR for each big decision. Use four parts. The context, the decision, the options you rejected, and the results you accept. Later, new team members can read why the system looks the way it does.

Real life scenarios

A startup that skipped architecture

Three teams built features in one shared database. Each team changed tables that other teams used. Every release broke something. The fix was an architecture decision. Each area got its own data and a clear API. After that, the teams could release on their own.

An ADR saves a long meeting

A new engineer asked, "Why do we use a queue between orders and email?" The team showed ADR 7. It said the email provider was often slow and the queue stopped it from slowing checkout. The question took two minutes instead of a long debate.

The same architecture, two designs

Two shops both use a web app, an API and a database. One shop keeps carts in the database. The other keeps carts in Redis. The architecture is the same. The design is different.

ChoiceGood atCosts you

Detailed design up front for every partFewer surprises.Wasted work when requirements change.

Common mistakes

  • Starting with database tables before you know the main parts.
  • Calling a list of tools, such as "React, Node, Postgres", an architecture. Tools are design choices inside the architecture.
  • Drawing one huge diagram with every detail. Use zoom levels.
  • Making big decisions and not writing down why.

Security lens

Security is an architecture concern, not only a design detail. The architecture fixes the trust boundaries, which parts talk to which, and where data lives. Those choices decide most of your attack surface before anyone writes code.

  • Record security decisions in ADRs, like "all service calls use mutual TLS".
  • Draw trust boundaries on the architecture diagram.
  • Run a threat model on the architecture, see lesson 6.5.
Key point

Fixing a bad trust boundary later means changing the architecture. Fixing a missing input check later means changing one function. Get the boundaries right first.
