Sagas, compensations and inventory holds

Placing an order touches stock, payment and delivery, each owned by a different service with its own database. There is no single transaction across them. Learn how sagas undo finished steps when a later one fails, and how holds stop you selling the last phone twice.

The idea in one minute

In one database, a transaction makes many writes all or nothing, as in lesson 2.7. With microservices, each service has its own database. A single ACID transaction across them is not practical.

A saga is a chain of local transactions, one per service. Each step commits on its own. If a later step fails, the saga runs compensating actions for the steps that already finished, in reverse order. A compensation is a new action that undoes the business effect, such as a refund for a payment or a release for a stock hold.

Stock needs extra care. Ten phones and hundreds of buyers clicking at once is a race. If each buyer's request checks "is there stock?" and then writes "sold", two buyers can pass the check for the last phone. That is overselling. A hold, also called a reservation, takes a unit out of available stock the moment the buyer clicks Buy, for a short time. If the buyer pays, the hold becomes a sale. If not, the hold expires and the unit returns.

Think of it like this

You plan a trip. You book the train, then the hotel, then try to rent a car. No car is free. So you cancel the hotel and then the train, the newest booking first. That is a saga with compensations.

Words you need

Saga
A sequence of local transactions in different services, with compensations if a step fails.
Compensating action
A new action that undoes the business effect of an earlier step, such as a refund.
Orchestration
One coordinator tells each service what to do next.
Choreography
Each service reacts to events from the others, with no central coordinator.
Outbox pattern
Write the event to an outbox table in the same transaction as the data, then publish it from there.
Hold
A short reservation of stock or money that expires if not confirmed.
Overselling
Selling more units than you have.

How it works

Orchestration or choreography

OrchestrationChoreography
Who decidesA saga coordinatorEach service, by listening to events
Easy to see the flowYes, in one placeNo, spread across services
CouplingCoordinator knows every stepServices know each other's events
Good forLong flows with many stepsShort flows with few services

Workflow engines such as Temporal or AWS Step Functions help with orchestration, and keep the saga's state if a server crashes.

Rules for sagas

  1. Every step and every compensation must be idempotent, because they can be retried.
  2. Compensations must not fail for good. Retry them until they succeed, and alert a human if they keep failing.
  3. Compensate in reverse order of the finished steps.
  4. Save the saga's state after each step, so a crash can resume it.
  5. Publish events reliably with the outbox pattern. Writing to the database and then to a queue as two separate actions can lose one of them in a crash.
  6. No isolation. Others can see the in between states, such as a held phone. Design screens and rules for that.

Stop overselling with a conditional update

UPDATE stock SET available = available - 1
WHERE sku = 'PHONE-128' AND available >= 1;
-- 1 row changed: hold placed. 0 rows: sold out.

The check and the write happen in one atomic statement, so two buyers can never both take the last unit. Record the hold with an expiry time, and run a job that releases expired holds by adding the unit back.

Choosing the hold time

Too short, and buyers lose the item while typing their card. Too long, and abandoned holds block real buyers. Ticket sites often use 5 to 15 minutes and show a countdown.

Key point

A saga gives you all or nothing eventually, by undoing, not instantly. Plan for the moments in between.

Real life scenarios

The original saga paper

Hector Garcia-Molina and Kenneth Salem described sagas in 1987, for long running database transactions that should not hold locks for hours. Microservices brought the idea back.

The flash sale that oversold

A shop checked stock in one query and wrote the order in another. During a sale it sold 140 phones that did not exist. A single conditional update for each hold stopped it.

Holds that never expired

A ticket site placed seat holds but its cleanup job crashed for a day. Thousands of seats looked sold but were never paid. The team added an alert on the age of the oldest hold, and the release job became idempotent and safe to run often.

ChoiceGood atCosts you
SagaWorks across services and databases, no long locks.No isolation, more code for compensations.

Common mistakes

  • Check then write for stock, in two steps.
  • Compensations that are not idempotent, such as refunding twice on retry.
  • Forgetting to release expired holds.
  • Writing to the database and the queue separately, without an outbox.
  • Assuming a saga hides in between states from users.

Security lens

Holds can be abused. A bot can hold every item without paying, which denies stock to real customers. Limit holds per account, per card and per IP, require login for scarce items, and watch the ratio of holds to purchases. Compensations move money too, so log them, protect them with idempotency keys and alert on unusual refund volumes.
