Choosing a database, SQL or NoSQL

There is no best database, only the best fit for how your data is shaped and how you read it. Learn the families and a simple way to choose.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesCheck yourselfInterview questionsPractice deskGo deeper

The idea in one minute

A database keeps data safe on disk and lets you find it again fast. There are two big families.

SQL databases, also called relational, like PostgreSQL and MySQL, keep data in tables with fixed columns. Tables link to each other, and you can ask almost any question with the SQL language. They are careful. A transfer of money either fully happens or does not happen at all.

NoSQL databases is a name for everything else. They give up some of SQL's features to be faster or easier to spread over many machines for one kind of access.

Think of it like this

A SQL database is a neat filing cabinet with labelled folders that cross reference each other. A key value NoSQL store is a wall of lockers. Give the locker number, get the box. Very fast, but you cannot ask "show me every locker with red shoes" unless you planned for it.

Words you need

Table
Rows and columns, like a spreadsheet with strict column types.
Schema
The shape of the data. Which tables, which columns, which types.
Join
Combining rows from two tables that share a key, like orders and users.
Transaction
A group of changes that all happen or none happen.
ACID
Atomic, consistent, isolated, durable. The promises a SQL transaction keeps.
Key value store
Look up a value by its key. Redis, DynamoDB.
Document store
Keeps JSON like documents with flexible fields. MongoDB.
Wide column store
Rows with many columns spread across machines, built for huge write volume. Cassandra, ScyllaDB.
Graph database
Stores things and the links between them. Good for friends of friends. Neo4j.

How it works

ACID in plain words

  • Atomic. All or nothing. If step 3 fails, steps 1 and 2 are undone.
  • Consistent. Rules always hold, like "stock is never below zero".
  • Isolated. Two transactions at once do not see each other's half done work.
  • Durable. Once it says "saved", it survives a crash.

A simple way to choose

  1. Is the data related and do you need transactions? Start with SQL. It is the right default for most apps.
  2. Do you mostly fetch by one key at enormous scale? Key value.
  3. Do you write a flood of events and read them by key and time? Wide column or time series.
  4. Do you mostly walk relationships? Graph.
  5. Do you need to search text? Add search next to your main database.
Key point

Modern SQL databases also store JSON and can be spread over machines, and many NoSQL databases now offer transactions. The lines are blurrier than they used to be. Choose by your access pattern, not by fashion.

Real life scenarios

A bank uses SQL for money

Moving money from one account to another must never lose or create money, even if a server dies halfway. ACID transactions in a relational database make that simple.

Discord moved messages to a wide column store

Billions of chat messages are written all the time and read by channel and time. Discord moved them from MongoDB to Cassandra and later to ScyllaDB because those spread huge write loads across many machines.

A product catalog with endless fields

A marketplace sells phones, shoes and sofas. In one SQL table this meant hundreds of mostly empty columns. Storing each product as a JSON document, in MongoDB or in a Postgres JSON column, fit much better.

Trade-offs

ChoiceGood atCosts you
SQLTransactions, joins, any question you can write, mature tools.Spreading writes over many machines is harder.
Key valueFastest lookups, easy to scale out.Only by key. No real queries.
DocumentFlexible fields, whole object in one read.Joins and cross document rules are weak.
Wide columnMassive writes, always on, many machines.You must design tables around queries up front.
GraphRelationship questions are fast and natural.Narrow use, harder to scale.

Common mistakes

  • Choosing NoSQL because it sounds more scalable when the data is relational and small.
  • Using a search engine like Elasticsearch as the only copy of important data.
  • Adding a new database for every feature. Each one needs backups, upgrades and on call.
  • Designing wide column tables without knowing the queries first.
