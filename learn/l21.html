Multi-region systems and disaster recovery

Whole data centers fail. Learn how systems survive losing a region, how to serve users worldwide, and how to plan recovery with two simple numbers.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Cloud providers group data centers into availability zones, separate buildings with their own power, and zones into regions, like Mumbai or Frankfurt. Running in several zones protects you from a building failing. Running in several regions protects you from a whole area going down, and puts servers close to users around the world.

But regions are far apart. Copying data between them takes 50 to 200 ms. That makes every decision harder, especially about writes.

Two numbers drive the plan. RPO, recovery point objective, is how much data you can afford to lose, like "the last 5 minutes". RTO, recovery time objective, is how long you can be down, like "30 minutes".

Think of it like this

A shop with branches in two cities can keep selling if one city has a blackout. But if both branches share one stock list, every sale needs a long phone call to the other city to update it.

Words you need

Region
A geographic area with several data centers, like eu-west or ap-south.
Availability zone
One or more data centers in a region with separate power and network.
RPO
Recovery point objective. The most data loss you accept, measured in time.
RTO
Recovery time objective. The longest outage you accept.
Active passive
One region serves, another waits ready to take over.
Active active
Several regions serve users at the same time.
Geo routing
Sending each user to the nearest healthy region.
Data residency
Laws requiring some data to stay in a country or region.

Active active and the write problem

Reads are easy everywhere. Writes are the hard part. You have four options.

  • Single writer region. All writes go to one home region, reads served locally. Simple, but far away users have slower writes.
  • Home region per user. Each user's data lives and is written in their nearest region. Works well, needs routing.
  • Multi leader with conflict resolution. Any region writes, conflicts merged, lesson 2.3.
  • Globally consistent databases like Spanner or CockroachDB. Strong consistency, every write pays cross region latency.

Practice or it does not work

A failover plan nobody has tested will fail. Run game days where you actually fail over. Check that backups really restore. Watch for hidden dependencies, like a login service that only runs in the failed region.

Key point

Many outages in a second region come from things that are global, like DNS, a config push or a certificate, which break every region at once. Roll out changes one region at a time.

Real life scenarios

AWS us-east-1 outages

Several big outages in one AWS region have taken down well known apps that ran in only that region, while companies with tested multi region setups kept running.

Netflix region evacuation

Netflix practices moving all traffic out of a whole AWS region in minutes, so a regional outage becomes a non event for viewers.

A backup that would not restore

A company had nightly backups for years. During a real incident they found the restore took 3 days and some backups were empty. Test restores regularly.

Trade-offs

ChoiceGood atCosts you
Single region, multi zoneSimple, cheap, handles most failures.A regional outage takes you down.
Active passiveSurvives region loss, simpler writes.Standby costs money, failover takes minutes and some data loss.
Active activeLow latency worldwide, near zero downtime.Hard write conflicts, highest cost and complexity.
Async cross region replicationFast writes.Some data loss on failover, RPO above zero.
Sync cross region replicationNo data loss.Every write waits for another region.

Common mistakes

  • Calling backups a disaster recovery plan without ever testing a restore.
  • A hidden single region dependency, like auth or secrets.
  • Pushing a config change to every region at the same time.
  • Using active active for everything when a few minutes of downtime would be fine.
  • Ignoring data residency laws when copying data abroad.

Security lens

Multi-region designs must respect law and resist disasters, including cyber ones.

  • Data residency. Some laws require personal data to stay in a country or region.
  • Disaster recovery plans must include ransomware. Keep immutable backups in a separate account.
  • Practice failover. A recovery plan nobody tested is a hope, not a control.
  • Each region is another place to patch, monitor and secure. Use the same code and config for all.
