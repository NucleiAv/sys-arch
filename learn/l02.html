APIs, how programs talk to each other

An API is a menu of things a server will do for you. Learn the common styles, when each one fits, and how to keep a live line open for chat and live updates.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesCheck yourselfInterview questionsPractice deskGo deeper

The idea in one minute

An API, application programming interface, is the list of requests a server accepts and what it sends back. The client cannot reach inside the server. It can only order from the menu.

A good API is boring in the best way. Clear names, the same rules everywhere, and it never breaks the apps already using it.

Think of it like this

A restaurant menu is an API. You do not walk into the kitchen. You say "one pizza, no onions" in a way the kitchen understands, and a pizza comes out. If the restaurant changes the kitchen, the menu can stay the same.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

REST
The most common style. Things are nouns at URLs, like /users/42, and HTTP methods are verbs, GET, POST, PUT, PATCH, DELETE.
GraphQL
One endpoint where the client writes a query for exactly the fields it wants. Good for apps with many screens.
gRPC
Fast calls between servers using a compact binary format and a strict contract file. Common inside a company.
WebSocket
A connection that stays open so both sides can send at any time.
Server-sent events
A one way open stream from server to browser. Simpler than WebSocket when only the server talks.
Webhook
The server calls your URL when something happens, instead of you asking again and again.
Idempotent
Doing it twice has the same effect as doing it once. GET, PUT and DELETE should be. POST usually is not.
Pagination
Returning a long list in pages, so one request never returns a million rows.

How it works

REST in one picture

CallMeaning
GET /ordersList my orders
GET /orders/17Show order 17
POST /ordersCreate an order
PATCH /orders/17Change part of order 17
DELETE /orders/17Cancel order 17

Use nouns, not verbs, in paths. Use status codes honestly. Return 201 when you create, 404 when it is missing, 409 when it clashes.

Pagination, done right

Offset paging, ?page=500, makes the database skip 10 thousand rows, and it repeats or skips items when new ones arrive. Cursor paging, ?after=msg_9812, says "give me the 20 after this one". It stays fast and stable, so feeds and chats use it.

Versioning

Apps on old phones keep calling your old API for years. Add new fields freely, but never remove or rename one. When you must break things, publish /v2 and keep /v1 alive until traffic fades.

Idempotency keys

A phone sends "pay 20 dollars", the network drops, and the phone retries. Did it pay twice? The fix is an idempotency key. The client sends a unique id with the request. The server remembers ids it has seen and returns the first result again instead of paying again. Every payment API does this.

Real life scenarios

A food app shows the same restaurant twice

The list used ?page=2. Between page 1 and page 2, a new restaurant was added at the top, which pushed one item down onto page 2 again. Switching to a cursor, ?after=rest_881, fixed it.

A mobile app breaks after a server update

A developer renamed price to amount in the response. The app in the store still read price, so every price showed as empty. The rule is add, never rename. Keep price and add amount next to it.

A payment provider charges a customer twice

This happens when an API does not support idempotency keys and a client retries after a timeout. This is why Stripe and other payment APIs ask for an Idempotency-Key header.

Trade-offs

ChoiceGood atCosts you
RESTSimple, cacheable, every tool understands it.Screens may need many calls, or get more data than they need.
GraphQLOne call fetches exactly what a screen needs.Harder to cache and to protect from very heavy queries.
gRPCFast, typed, great between your own services.Not native in browsers, harder to read and debug by hand.
WebSocketInstant two way updates.Each open connection costs server memory, harder to load balance.
PollingDead simple, works everywhere.Wasteful and slow to notice changes.

Common mistakes

  • Putting verbs in URLs, like /getUser, instead of using HTTP methods.
  • Returning 200 with an error message inside. Use real status codes.
  • Using offset paging on a feed that changes all the time.
  • Retrying a payment without an idempotency key.
  • Removing or renaming a field that old apps still read.
