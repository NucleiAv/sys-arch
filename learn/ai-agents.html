AI agents, tools, memory and long running work

An agent is an LLM that does not only answer but acts. It chooses tools, calls them, reads the results and decides the next step, sometimes for hours without a person watching. Learn the agent loop, how tools are connected, how to keep state, and how to stop an agent that goes wrong.

The idea in one minute

A chat assistant answers one question. An agent works toward a goal. It runs a loop.

  1. Think. The model looks at the goal and what has happened so far, and picks the next action.
  2. Act. It calls a tool, such as search the tickets, read a file, run a query or send an email.
  3. Observe. The tool's result is added to the agent's context.
  4. Repeat until the goal is done, a limit is reached, or a person must decide.

The model never runs tools itself. It writes a structured tool call, such as {"tool": "get_order", "args": {"id": 81}}. Your code checks the call, runs the tool and sends back the result. That gap between "the model asks" and "your code does" is where you control what an agent is allowed to do.

Agents that run on their own, triggered by events or schedules, need the same things as any long running backend job. They need state that survives crashes, limits on time, steps and money, logs of every action, and a way for people to approve or stop them.

Think of it like this

An agent is like a new assistant with a to do list and a toolbox. They decide which tool to use, use it, look at the result, and decide again. A good manager gives them only the tools they need, checks the risky jobs before they happen, and can always say "stop".

Words you need

Agent
A system where an LLM chooses actions and tools in a loop to reach a goal.
Tool
A function the agent can ask to call, with a name, a description and an input schema.
Tool call
A structured request from the model to run a tool with given arguments.
Agent loop
Think, act, observe, repeat, until done or stopped.
MCP
Model Context Protocol, an open standard from 2024 for connecting AI apps to tools and data through servers.
Memory
What the agent keeps between steps or runs, such as notes, past results or user preferences.
Orchestrator
The code that runs the loop, checks tool calls, saves state and enforces limits.
Human in the loop
A person approves, edits or rejects certain actions before they happen.
Durable execution
Running long workflows so their state survives crashes and they resume where they stopped.

How it works

Workflows or agents

Not every AI feature needs an agent.

WorkflowAgent
Who decides the stepsYour code, fixed orderThe model, step by step
PredictableYesLess
Good forKnown tasks, such as "summarize, then classify, then route"Open tasks where the path depends on what is found
Cost and riskLow and boundedHigher, needs limits

Start with the simplest design that works. Many "agents" are better as a workflow with one or two LLM steps.

Designing tools

  • Narrow and clear. refund_order(order_id, amount, reason) is safer than run_sql(query).
  • Validate inputs with a schema, and check business rules in code, not in the prompt.
  • Read only by default. Separate read tools from write tools.
  • Idempotent writes with keys, since agents retry, see lesson 3.7.
  • Useful errors. Return a clear message the model can act on, such as "amount above order total".

Connecting tools with MCP

The Model Context Protocol, published by Anthropic in November 2024 and now supported by many AI tools, defines how an AI application, the client, talks to MCP servers that expose tools, resources such as files, and prompts. Messages use JSON-RPC. One MCP server for your ticket system can then be used by many agents and assistants. Treat every MCP server as code you are trusting, see lesson 8.7.

State, memory and limits

  • Short term memory is the context of the current run. Long runs must summarize or drop old steps to fit the context window.
  • Long term memory is stored outside the model, such as a database of notes, and retrieved when needed, like RAG.
  • Durable execution. Save state after every step, so a crash resumes instead of starting over or repeating side effects. Workflow engines such as Temporal help.
  • Limits. Maximum steps, wall clock time, tokens and money per run, plus a loop detector for repeated identical calls.

Multi agent systems

Some designs split work across several agents, such as a planner and several workers. This can help with large tasks but multiplies cost, makes failures harder to trace, and gives more places for bad data to spread. Use it only when one agent clearly cannot do the job.

Key point

The model proposes. Your code disposes. Every tool call passes through code that checks permissions, limits and business rules.

Real life scenarios

Coding agents in real repositories

Coding agents now read code, run tests and propose changes in real projects. Teams that get good results run them in sandboxes, require review of every change, and give them only the permissions a junior developer would have.

The agent that deleted a database

In July 2025 a founder reported that an AI coding agent on the Replit platform deleted a production database during a code freeze, despite instructions not to change anything. The company added stronger separation between development and production. Instructions in a prompt are not a permission system.

The infinite loop

An agent asked to fix a failing test kept editing the same file and rerunning the tests for hours, burning tokens. A step limit, a budget and a check for repeated identical actions now stop such runs.

Common mistakes

  • Building an agent when a simple workflow would do.
  • Giving agents broad tools like shell or raw SQL on production.
  • Relying on the prompt to stop dangerous actions.
  • No step, time or cost limits.
  • Keeping agent state only in memory, so a crash loses or repeats work.

Security lens

Agents turn model mistakes into real actions, so security moves from "what can it say" to "what can it do". Give each agent its own identity and the least privilege tools, require human approval for actions that move money, delete data or contact people, sandbox code execution, and log every tool call. OWASP calls the risk of agents with too much power excessive agency, LLM06 in its 2025 list. Lesson 8.7 covers this in depth.
