Scaling up, scaling out and staying stateless

When one server is too busy, you can buy a bigger one or add more. Adding more only works if servers forget everything between requests. Learn why.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Scaling up, or vertical scaling, means a bigger machine, more CPU, more memory. It needs no code change. But it has a ceiling, it gets very expensive near the top, and it is still one machine that can die.

Scaling out, or horizontal scaling, means more machines doing the same job. There is almost no ceiling, and if one dies the rest carry on. But it only works if any server can answer any request. That means servers must be stateless. They keep nothing about a user in their own memory. Sessions, carts and uploads live in a shared store instead.

Think of it like this

A busy shop can hire one super fast cashier, or open ten checkout lanes. Ten lanes only work if any cashier can serve any customer. If your shopping list was stored in the head of cashier 3, you would have to queue for cashier 3 forever.

Words you need

Vertical scaling
Making one machine bigger.
Horizontal scaling
Adding more machines.
Stateless
The server keeps no user data between requests. Any copy can answer.
Session
What the system remembers about a logged in user between clicks.
Autoscaling
Adding or removing servers by itself based on load, like CPU above 70 percent.
Sticky sessions
The load balancer always sends a user to the same server. A shortcut with real downsides.
JWT
A signed token that carries who the user is. The server checks the signature instead of looking up a session.

How it works

Where state should live

StateWhere it goes
Login sessionsA shared store like Redis, or a signed token like a JWT
Shopping cartsDatabase or Redis
Uploaded filesObject storage like S3, never the server's disk
Jobs in progressA queue

Autoscaling

Cloud platforms watch a number, like CPU or requests per server, and add servers when it is high and remove them when it is low. New servers need a few minutes to start, so set the trigger early, around 60 to 70 percent, not 95.

Key point

Stateless servers are also what make deploys painless. You can replace servers one by one with a new version and nobody gets logged out.

When scaling up is the right answer

Scaling up is great early on and for databases, which are hard to split. A big database machine can carry a surprising amount. Many companies scale the database up for years while scaling the app servers out.

Real life scenarios

A school results site crashes every year

Results day brings 100 times normal traffic for two hours. They kept buying a bigger server. Moving sessions to Redis and putting the app behind a load balancer with autoscaling let them run 2 servers all year and 40 for those two hours.

Users lose uploads

An app saved profile photos to the local disk of whichever server got the upload. Later requests went to other servers and the photo was missing. Uploads must go to shared object storage.

Stack Overflow scaled up for years

Famously, Stack Overflow ran a huge site on a small number of very powerful servers. Scaling up is a valid, simple choice when it fits the numbers.

Trade-offs

ChoiceGood atCosts you
Scale upNo code change, simple to run.Ceiling, high cost at the top, single point of failure.
Scale outNo real ceiling, survives a server dying.Needs stateless servers, a load balancer and shared stores.
Sticky sessionsQuick fix for a stateful app.Uneven load, and users lose their session when their server dies.
Shared session storeAny server can answer.One more component to run, and an extra network hop.
JWT tokensNo lookup on each request.Hard to log a user out before the token expires.

Common mistakes

  • Saving uploads or sessions on the app server's own disk or memory.
  • Using sticky sessions as a permanent design.
  • Autoscaling on a trigger so high that new servers arrive after the crash.
  • Assuming the database scales out as easily as the app servers. It does not, see lessons 2.3 and 2.4.

Security lens

Stateless servers make security easier, if you store state safely.

  • Keep sessions in a protected store or use short lived signed tokens.
  • Do not keep secrets on server disks. Load them from a secrets manager at start.
  • Immutable servers, replaced instead of patched by hand, remove drift and leftover backdoors.
  • More servers means more places to patch. Build images from one source and rebuild often.
