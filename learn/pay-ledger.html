Digital wallets and the double-entry ledger

A wallet balance looks like one number, but a good wallet never just edits that number. Learn why money systems record every movement as balanced entries in a ledger, and how that stops concurrent transfers from creating or destroying money.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

A naive wallet keeps one row per user with a balance column and changes it on every transfer. It works until two transfers touch the same account at the same moment. Both read the old balance, both write a new one, and one change is lost. Money is created or destroyed, and nobody can tell what happened.

Money systems use a ledger instead. A ledger is an append only list of entries. You never edit or delete an entry. To fix a mistake, you add a new entry that reverses it.

The ledger uses double entry, a method accountants have used for over 500 years. Every transaction has at least two entries, and they always add up to zero. Sending 100 rupees from Asha to Ben writes "Asha −100" and "Ben +100". If the entries of a transaction do not sum to zero, the system refuses it. So money can move, but it can never appear from nowhere or vanish.

A balance is then the sum of an account's entries. Many systems also keep a stored balance for speed, updated in the same transaction as the entries.

Think of it like this

Think of a class notebook where every swap of stickers is written on two lines. "Asha gave 3 stickers" and "Ben got 3 stickers". Nobody erases a line. If you want to know how many stickers Ben has, add up all his lines.

Words you need

Ledger
An append only record of every money movement.
Entry
One line in the ledger, an amount added to or taken from one account.
Double entry
Every transaction has entries that sum to zero, so money is never created or lost.
Debit and credit
Accounting words for the two sides of an entry. Which one increases a balance depends on the account type.
Balance
The sum of all entries of an account.
Reversal
A new transaction that undoes an earlier one, instead of editing it.
System account
An account owned by the company, such as fees or money in transit.

How it works

A minimal ledger schema

CREATE TABLE ledger_entries (
  id          bigserial PRIMARY KEY,
  txn_id      uuid NOT NULL,
  account_id  bigint NOT NULL,
  amount      bigint NOT NULL,       -- in paise, never floats
  created_at  timestamptz NOT NULL DEFAULT now()
);
-- every txn_id must sum to 0, checked in the same transaction

Rules that keep money safe

  1. Integer amounts in the smallest unit, such as paise or cents. Never floating point. 0.1 + 0.2 is not exactly 0.3 in floats.
  2. Append only. No UPDATE or DELETE on entries. Mistakes get a reversal.
  3. Every transaction sums to zero, checked before commit.
  4. One database transaction writes all entries of a money transaction, plus any stored balances.
  5. Serialize per account. Lock the account rows, in a fixed order such as account id, or use a conditional update on the stored balance. This stops the lost update and avoids deadlocks, see lesson 2.7.
  6. Idempotency key on every transfer request, see lesson 3.7.

Checking the books

Because entries never change, you can always check. The sum of all entries across all accounts must be zero. Each stored balance must equal the sum of its entries. A job that runs these checks every night finds bugs before customers do.

Hot accounts

A popular merchant account can receive thousands of payments a second, and every one locks the same row. Common fixes are to split it into several sub accounts and sum them, or to write entries without locking the receiving side and update its stored balance in batches. Only the paying side needs a balance check.

Key point

Store movements, not just balances. A balance is a summary you can always recompute. Movements are the truth.

Real life scenarios

500 years of double entry

Luca Pacioli described double entry bookkeeping in a book printed in Venice in 1494. Modern payment companies still use the same rule in code, because it makes errors visible instead of silent.

The float bug

A wallet stored balances as floating point numbers. After millions of small cashback credits, totals drifted by a few rupees, and auditors could not match them. Moving to integers in paise ended the drift.

A hot merchant

A food delivery company's main merchant account was updated on every order and became the slowest row in the database at dinner time. Splitting it into 16 sub accounts and summing them for reports removed the bottleneck.

Ledger only, balance computed by summingSimplest truth, nothing to drift.Slow for accounts with millions of entries.

Common mistakes

  • Updating a balance column with no history of movements.
  • Using floating point for money.
  • Editing or deleting ledger entries to fix mistakes.
  • Reading a balance into the app and writing it back without a lock.
  • Locking accounts in different orders in different code paths.

Security lens

Insiders and attackers both target ledgers. Make entries append only at the database level, for example by revoking UPDATE and DELETE from the application user. Require two people to approve manual adjustments, log who did what, and alert when the nightly sum check is not zero. Race conditions in transfers are real attack paths, so test with many parallel requests.
