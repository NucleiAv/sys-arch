Unique IDs and time across many machines

One database can count 1, 2, 3. A thousand machines cannot share one counter without slowing down. Learn how big systems make unique, sortable ids and why clocks lie.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Every post, order and message needs an id that no other item will ever have. With one database you just use an auto increment counter. Once you have many databases or shards, two of them might both hand out id 1001.

There are a few ways out. UUIDs are random 128 bit numbers, so unlikely to clash that nobody checks. Snowflake style ids pack the time, the machine number and a counter into one 64 bit number, so they are unique and roughly sorted by time.

Time itself is tricky. Every machine has its own clock, and clocks drift apart by milliseconds or more. So "which happened first" is not always clear across machines.

Think of it like this

Two cashiers numbering receipts would clash if both start at 1. Give cashier A the numbers ending in A and cashier B ending in B. Add the time in front, and you can also sort receipts by when they were printed.

Words you need

Auto increment
The database counts 1, 2, 3. Simple, but needs one central counter.
UUID
A random 128 bit id. Unique without coordination, but not sorted and long.
UUIDv7
A newer UUID that starts with the time, so it sorts well in indexes.
Snowflake id
A 64 bit id made of time, machine number and a counter. Created by Twitter.
Clock skew
The difference between two machines' clocks.
NTP
Network Time Protocol. Keeps machine clocks close to real time, usually within a few ms.
Logical clock
A counter that tracks the order of events instead of real time, like a Lamport clock.

Why sorted ids matter

Databases keep B-tree indexes sorted. Random ids like UUIDv4 land all over the index, which causes many page splits and slower inserts. Time ordered ids append near the end, which is much friendlier. They also let you page "older than this id" without a separate time column.

Clocks lie

  • Clocks drift, and NTP corrects them, sometimes even moving time backwards. A Snowflake generator must notice this and wait, or it might repeat ids.
  • Two events on two machines a few ms apart cannot be ordered reliably by timestamps.
  • Logical clocks solve ordering without real time. A Lamport clock is a counter that each machine bumps on every event and on every message it receives, taking the bigger value.
Key point

Never use "last write wins by timestamp" for important data without knowing that clock skew can make the older write win.

Real life scenarios

Twitter built Snowflake

When Twitter moved off a single MySQL, it needed tens of thousands of unique ids a second, roughly sorted by time, in 64 bits. Snowflake was the answer and inspired Discord, Instagram and many others.

Instagram's ids from Postgres

Instagram generated ids inside each Postgres shard using a function that combined time, the shard number and a per shard sequence, a Snowflake idea with no separate service.

A leap second bug

In 2012 a leap second confused some Linux systems and caused high CPU across many sites. Time is a common source of strange outages.

ChoiceGood atCosts you
Auto incrementTiny, simple, perfectly ordered.One central bottleneck, leaks how many records you have.

Common mistakes

  • Exposing auto increment ids in URLs, which lets anyone guess other records and count your orders.
  • Using random UUIDs as the primary key on a huge, write heavy table without thinking about index cost.
  • Trusting timestamps from different machines to decide what happened first.
  • Two generators accidentally sharing the same machine id.

Security lens

Ids and clocks have security uses.

  • Do not use guessable ids for private objects, or check access on every request. Sequential ids invite enumeration.
  • Random ids like UUID version 4 are hard to guess, but they are not a replacement for authorization.
  • Signatures and tokens rely on time. Keep clocks synced with NTP, and allow a small skew when checking expiry.
  • Logs from many machines need synced clocks, or an incident timeline becomes guesswork.
