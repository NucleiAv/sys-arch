GraphQL, ask for exactly what you need

GraphQL lets the client write one query that names exactly the fields it wants, even across many related things. Learn schemas, queries, mutations, resolvers and the traps that come with this power.

The idea in one minute

With REST, a screen often needs many calls. One call for the user, one for the user's orders, one for each order's items. And each call may send fields the screen does not need.

GraphQL fixes this. The server publishes a schema, a typed list of everything you can ask for. The client sends one query that names the exact fields it wants. The server returns JSON in the same shape as the query.

Facebook built GraphQL in 2012 for its mobile apps and released it as open source in 2015. The GraphQL Foundation now looks after it.

Think of it like this

REST is like a set menu. You order "meal 3" and get what comes with it. GraphQL is like a form where you tick exactly the items you want. You get only those items, on one plate.

Words you need

Schema
The typed description of all data and operations the API offers.
Type
A shape of data, such as User with fields id, name and orders.
Query
A read operation.
Mutation
A write operation, such as createOrder.
Subscription
A long lived operation where the server pushes updates, usually over WebSocket.
Resolver
The function on the server that returns the data for one field.
N+1 problem
One query for a list, then one more query for each item in the list.
DataLoader
A pattern and library that batches and caches many small lookups into one.
Introspection
A built in query that asks the server to describe its own schema.
Persisted query
A query stored on the server and called by id or hash, so clients send less and servers can allow only known queries.

How it works

A schema

type User {
  id: ID!
  name: String!
  orders(last: Int): [Order!]!
}
type Order {
  id: ID!
  total: Int!
  items: [Item!]!
}
type Query {
  user(id: ID!): User
}
type Mutation {
  createOrder(items: [ItemInput!]!): Order!
}

The ! means the field can never be null.

A query and its answer

query {
  user(id: "7") {
    name
    orders(last: 3) { id total }
  }
}
{"data": {"user": {"name": "Asha",
  "orders": [{"id": "91", "total": 450}, {"id": "88", "total": 120}, {"id": "80", "total": 999}]}}}

How it travels

Most servers use one URL, such as POST /graphql, with the query in a JSON body. Errors often come back inside an errors list, sometimes with status 200. So monitoring must read the body, not only the status code.

The traps and their fixes

TrapFix
N+1 database queriesBatch with DataLoader
Very deep or huge queries that overload the serverDepth limits, cost limits, timeouts
Hard to cache, every request is a POST to one URLPersisted queries sent with GET, plus client side caches
Anyone can read the whole schemaTurn off introspection in production if needed, and check permissions per field
Key point

GraphQL does not replace your services. It is usually a layer in front of them that shapes data for clients. Large companies join many service schemas into one with federation.

Real life scenarios

GitHub's public GraphQL API

GitHub offers a GraphQL API next to its REST API. It limits each query with a points based cost, so one huge query cannot overload the servers.

A slow profile page

A team added GraphQL and the page got slower. Each of 50 friends triggered its own database query. Adding DataLoader cut 51 queries to 2.

Mobile data savings

A shop app used REST endpoints that returned 80 fields per product. The list screen needed 6. With GraphQL the product list payload became much smaller.

Trade-offs

ChoiceGood atCosts you
GraphQLOne round trip, exact fields, strong types, great for many client screens.Harder caching, query cost control, more server complexity.
RESTSimple, HTTP caching works, every tool understands it.Over fetching, under fetching and many round trips for complex screens.
Federated GraphQLOne graph across many teams.Another layer to run and govern.

Common mistakes

  • No depth or cost limits, so one query can overload the server.
  • Resolvers that each hit the database, causing N+1 queries.
  • Checking permissions only at the endpoint, not per field.
  • Monitoring only HTTP status codes when errors come back with 200.
  • Using GraphQL for simple service to service calls where gRPC or REST is simpler.

Security lens

GraphQL gives clients a lot of power, so you must set limits.

  • Depth and cost limits. A deeply nested query can ask for millions of objects. Limit depth, complexity and page size.
  • Field level authorization. Every resolver checks if this user may see this field. One endpoint does not mean one check.
  • Introspection. Turn it off in production for private APIs, or at least do not rely on hiding the schema.
  • Batching. Many queries in one request can bypass rate limits. Count operations, not HTTP requests.
  • Persisted queries. For your own apps, allow only queries you approved ahead of time.
