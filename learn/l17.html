Designing for failure, timeouts, retries and circuit breakers

In a big system something is always broken. Learn the small patterns that stop one slow part from dragging the whole system down.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

The most dangerous failure is not a server that dies. It is a server that becomes slow. Callers wait for it, their threads fill up, then they become slow, and their callers wait on them. One slow service can freeze everything. This chain reaction is a cascading failure.

A few simple habits stop it. Never wait forever, use timeouts. Try again, but gently, with retries with backoff. Stop calling something that is clearly broken, with a circuit breaker. Keep failures in their own box, with bulkheads. And when a part is down, show something useful anyway, called graceful degradation.

Think of it like this

If you call a friend and they do not pick up, you do not hold the phone for an hour. You hang up after a while, try again later, and after a few tries you stop calling and send a text instead.

Words you need

Timeout
The longest you will wait for an answer before giving up.
Retry
Trying a failed call again.
Exponential backoff
Waiting longer after each failed try, like 100 ms, 200, 400, 800.
Jitter
Adding randomness to wait times so many clients do not retry at the same moment.
Circuit breaker
Stops calling a failing dependency for a while, then tests it again.
Bulkhead
Separate pools of threads or connections per dependency, so one cannot use them all.
Graceful degradation
Showing a simpler result when a part is down, instead of an error.
Retry storm
Many clients retrying at once and making the outage worse.
Fallback
What you return when the real call fails, like cached or default data.

How it works

Timeouts

Every network call needs one. Base it on the dependency's normal p99 plus a margin, not on "30 seconds just in case". Also set an overall deadline for the user's request and pass the time left down the chain, so deep services do not keep working on a request the user already gave up on.

Retries, done safely

  1. Only retry errors that might pass, like timeouts and 503. Never retry a 400.
  2. Only retry idempotent calls, or use idempotency keys.
  3. Use exponential backoff with jitter.
  4. Cap the number of tries, usually 2 or 3.
  5. Retry at one layer only. If 4 layers each retry 3 times, one failure becomes 81 calls.

Bulkheads

Ships have walls between compartments so one leak does not sink the whole ship. Give each dependency its own small connection pool. If recommendations hang, they use up only their own pool, and checkout still has connections.

Graceful degradation

Part downDegraded answer
RecommendationsShow best sellers from a cache
ReviewsHide the section
Personal pricesShow the standard price
SearchShow categories to browse
Key point

Decide what the critical path is, the few things that must work, like login, cart and pay. Everything else should be able to fail quietly.

Practice failing

Chaos engineering means breaking things on purpose, in a controlled way, to prove the system copes. Netflix's Chaos Monkey randomly kills servers in production so teams build services that survive it.

Real life scenarios

Netflix and the Simian Army

Netflix built Chaos Monkey to kill production servers at random, and later tools that drop whole regions. Engineers designed for failure because failure was guaranteed every day.

AWS us-east-1 in 2021

Network congestion inside AWS caused many internal services to time out and retry, which added even more traffic. The AWS write-up describes how retries can amplify problems.

A homepage that died for a widget

A news site's homepage waited for a weather widget with no timeout. When the weather provider hung, the whole homepage hung. A 300 ms timeout and hiding the widget on failure fixed it.

Trade-offs

ChoiceGood atCosts you
Short timeoutFails fast, protects threads.May cut off calls that would have succeeded.
Long timeoutFewer false failures.Threads pile up when a dependency is slow.
More retriesHides brief blips.Multiplies load during real outages.
Circuit breakerStops cascades, gives the dependency room to recover.Needs tuning, may trip on short spikes.
Degrade instead of errorUsers keep going.Shows less, needs product decisions and testing.

Common mistakes

  • No timeout, or a default of minutes.
  • Retrying instantly, with no backoff or jitter.
  • Retrying at every layer of the stack.
  • Retrying non idempotent calls like payments without idempotency keys.
  • Treating every feature as critical, so any failure is a full outage.
