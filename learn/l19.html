Security for architects

Security is part of the design, not a coat of paint at the end. Learn how to check who someone is, what they may do, and how to protect data in motion and at rest.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Every design must answer four questions.

  1. Who are you? That is authentication, logging in.
  2. What may you do? That is authorization, permissions.
  3. Can anyone read or change the data on the way or on disk? That is encryption.
  4. If something is broken into, how much damage can it do? That is least privilege and defense in depth.
Think of it like this

A hotel checks your ID at the front desk, that is authentication. Your key card opens only your room and the gym, not other rooms, that is authorization. The safe in your room is encryption. Even if a thief gets one key card, they get one room, not the whole hotel. That is least privilege.

Words you need

Authentication
Proving who you are. Passwords, passkeys, one time codes.
Authorization
Deciding what you are allowed to do.
OAuth 2.0
A standard for letting an app get limited access tokens on a user's behalf.
OpenID Connect
A layer on OAuth that also tells the app who the user is. Used for Sign in with Google and similar.
JWT
JSON Web Token. A signed token that carries claims like user id and expiry.
RBAC
Role based access control. Permissions come from roles like admin or viewer.
Encryption in transit
Data is encrypted while moving, with TLS.
Encryption at rest
Data is encrypted on disk, so stolen disks or backups are unreadable.
Least privilege
Every user and service gets only the access it needs.
Secrets manager
A safe service that stores passwords and keys, like Vault or AWS Secrets Manager.

How it works

Passwords done right

Never store passwords. Store a slow, salted hash, made with bcrypt, scrypt or Argon2. Add rate limits on login, see lesson 3.3, and offer multi factor login or passkeys.

Sessions or tokens

Server sessionsSigned tokens, JWT
Where state isSession storeInside the token
Check costA lookup per requestVerify a signature
Log out instantlyEasy, delete the sessionHard, wait for expiry or keep a deny list
Good forWebsitesAPIs and many services

A common mix is short lived access tokens, around 15 minutes, plus a longer refresh token that can be revoked.

Authorization patterns

  • Check permission in the service that owns the data, on every request.
  • IDOR, insecure direct object reference, is the classic bug. Changing /invoices/1001 to /invoices/1002 shows someone else's invoice. Always check ownership.
  • Use roles for simple cases and attribute or relationship rules, like "member of this team", for richer ones.

Service to service

Inside your network, do not trust a call just because it is internal. Use mutual TLS so each service proves its identity, and give each service its own narrow permissions. This is the idea behind zero trust.

Defense in depth

Layers, each catching what the last missed. Edge protection against floods, a web application firewall, rate limits, authentication at the gateway, authorization in services, input validation, encryption, audit logs, backups.

Careful

The most common real breaches are boring. Public storage buckets, secrets committed to code, missing permission checks and unpatched software. Design these out first.

Real life scenarios

Capital One breach, 2019

A misconfigured web firewall let an attacker reach the cloud metadata service and use a role with far too many permissions to read S3 buckets with over 100 million customer records. Least privilege on that role would have limited it.

Secrets in a public repository

Developers often push cloud keys to public code repositories by accident. Bots scan for them within minutes and start crypto mining. Use a secrets manager and scanning before commit.

An IDOR in a food app

Changing an order number in the URL showed other people's names, addresses and phone numbers. The API checked that the user was logged in but not that the order was theirs.

Common mistakes

  • Storing passwords in plain text or with fast hashes like MD5.
  • Checking that a user is logged in but not that they own the object.
  • Long lived tokens with no way to revoke them.
  • Secrets in code, config files or logs.
  • Trusting every request from inside the network.
