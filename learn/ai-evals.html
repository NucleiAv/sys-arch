Evaluating, observing and guarding AI systems

AI output changes when you change a prompt, a model or the data behind it, and normal unit tests cannot say whether an answer is good. Learn how to build evaluation sets, trace every step of an AI request, add guardrails on input and output, and roll out changes safely.

The idea in one minute

Normal code gives the same output for the same input. LLMs do not always, and "correct" is often a judgement, not an exact string. So AI systems need evaluations, or evals, a repeatable way to measure quality on a fixed set of test cases.

An eval set is a list of real looking inputs with what a good result looks like. You run it on every change, a new prompt, a new model, a new retrieval setting, and compare scores before you ship. Scores come from three kinds of grader.

  1. Code checks. Is the output valid JSON? Does it cite a source? Is it under 200 words?
  2. Model graders, also called LLM as a judge. A strong model scores answers against a rubric, such as "Is every claim supported by the passages?"
  3. People. Experts review a sample, and check that the model graders agree with them.

In production you also need tracing, a record of every step of a request, retrieval, prompts, tool calls, tokens, cost and latency, and guardrails, checks before and after the model that block or fix unsafe inputs and outputs.

Think of it like this

Before a school changes its exam, teachers give the new exam to a few students whose level they already know. If those students suddenly score much worse, the new exam has a problem. Evals are that test run for your AI.

Words you need

Eval
A repeatable test of AI quality on a fixed set of cases.
Golden set
A curated list of test cases with known good answers or rubrics.
LLM as a judge
Using a model to grade outputs against a rubric.
Faithfulness
Whether every claim in an answer is supported by the given sources.
Hallucination
A confident answer that is false or not supported by any source.
Tracing
Recording every step of a request, with timing, tokens and inputs and outputs.
Guardrail
A check before or after the model that blocks, changes or flags content or actions.
Red teaming
Trying on purpose to make the system misbehave, to find weaknesses before attackers do.

How it works

Build an eval set

  1. Collect real cases from logs, with personal data removed, plus hard and adversarial cases.
  2. Write what good looks like, an exact answer, required facts, or a rubric.
  3. Cover each feature and risk, such as refunds, out of scope questions, prompt injection attempts and empty retrieval.
  4. Grow it every time a bug is found in production. Each bug becomes a test.

Graders and their limits

GraderGood atWatch out
Code checkFormat, length, citations present, forbidden wordsCannot judge meaning
Model graderMeaning, faithfulness, tone, at scaleBias, such as preferring longer answers. Check it against people
PeopleHard and high stakes casesSlow, costly, need clear rubrics

What to trace

For every request, record the prompt version, model, retrieved document ids, each tool call and result, tokens, cost, latency and any guardrail decision. OpenTelemetry has semantic conventions for generative AI, so traces can flow into your normal observability tools, lesson 4.2. Redact personal data in traces.

Guardrails

  • Input. Block or flag known jailbreak patterns, personal data the user should not send, and requests outside the product's purpose.
  • Output. Check format, remove secrets and personal data, check claims against sources, and block unsafe content.
  • Action. For agents, check every tool call against policy, see lesson 8.7.

Guardrails reduce risk but are not perfect. Classifiers can be fooled, so combine them with limits on what the system can do.

Roll out like code

Version prompts and models. Run evals in CI. Use shadow mode or canaries, compare live signals such as user feedback, guardrail blocks, cost and latency, and keep instant rollback.

Key point

If you cannot measure quality, you cannot safely change a prompt, a model or a retrieval setting. Evals come before optimization.

Real life scenarios

Air Canada's chatbot, 2024

A customer relied on Air Canada's website chatbot, which wrongly said a bereavement discount could be claimed after travel. A Canadian tribunal ordered the airline to pay the difference and rejected the idea that the chatbot was responsible for its own words. Companies own what their AI says.

The one dollar car

In December 2023 users got a car dealership's chatbot to agree to sell a new SUV for one dollar by telling it to agree with anything. No sale happened, but it showed why bots need scope limits and output checks.

Evals catch a model upgrade

A team upgraded to a newer model expecting better answers. Their eval suite showed a drop in following the required JSON format. They adjusted the prompt before rollout instead of discovering the breakage in production.

Trade-offs

ChoiceGood atCosts you
Large eval suiteCatches more regressions.Slower and costlier to run on every change.
Model gradersCheap and scalable.Can be biased or wrong, need checks against people.
Strict guardrailsFewer harmful outputs.More false blocks of valid requests.
Full prompt and output loggingEasy debugging.Privacy risk and storage cost.

Common mistakes

  • Changing prompts or models with no eval set.
  • Trusting a model grader without checking it against people.
  • Logging full prompts with personal data and no retention limit.
  • Relying on guardrails alone, with no limits on what the system can do.
  • Not turning production bugs into new eval cases.

Security lens

Evals are also a security tool. Include red team cases, such as prompt injection inside documents, attempts to extract the system prompt and requests for other users' data, and run them on every change. Keep traces in a restricted store, because they may contain secrets and personal data, and set short retention. Monitor for spikes in guardrail blocks, which can signal an active attack.
