Replication, keeping copies of your data

Copies of your database protect you when a machine dies and let more machines answer reads. But copies can fall behind. Learn the main setups and their surprises.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Replication means keeping the same data on more than one machine. It does two jobs. If one machine dies, another has the data, so you stay up. And many copies can answer reads, so you can serve more users.

The most common setup is leader and followers. All writes go to one machine, the leader. It sends every change to the followers, also called replicas. Reads can go to any of them.

The catch is replication lag. A follower may be a little behind the leader, usually milliseconds, sometimes seconds. So a user might save something and then not see it.

Think of it like this

A teacher writes on the main board, and helpers copy it onto boards in other rooms. Students in any room can read. But a helper who copies slowly shows yesterday's sentence for a moment.

Words you need

Replica
A copy of the database on another machine.
Leader
The one copy that accepts writes. Also called primary.
Follower
A copy that receives changes from the leader. Also called secondary or read replica.
Replication lag
How far behind a follower is.
Synchronous replication
The leader waits for a follower to confirm before saying OK. Safer, slower.
Asynchronous replication
The leader says OK at once and sends changes later. Faster, can lose recent writes on failover.
Failover
Promoting a follower when the leader dies.
Split brain
Two machines both think they are the leader and both take writes. Very bad.
Quorum
A majority. With 3 copies, writing to 2 and reading from 2 means a read always sees the latest write.

How it works

Three setups

SetupHow writes workGood forHard part
Single leaderOne leader takes all writesMost apps, simpleLeader is a write bottleneck and failover needs care
Multi leaderSeveral leaders, often one per regionWrites from many regions, offline appsTwo leaders can change the same thing, conflicts
LeaderlessWrite to several copies, read from severalAlways on, Cassandra and DynamoDB styleTuning quorums, fixing stale copies

Sync or async

Most systems use semi sync. The leader waits for one follower to confirm, and the rest catch up in the background. That way at least two machines have every write, without waiting for all.

Quorums in leaderless systems

With N copies, write to W of them and read from R of them. If W + R > N, every read overlaps at least one copy with the latest write. A common choice is N = 3, W = 2, R = 2.

Handling conflicts

If two leaders change the same record, someone must win. Last write wins uses timestamps, simple but can silently drop a change. Better options merge the changes, like adding both items to a cart, or use special data types called CRDTs that always merge cleanly.

Careful

Replication is not a backup. If someone runs DELETE FROM users, the delete is copied to every replica in milliseconds. You still need backups you can restore from.

Real life scenarios

GitHub's 24 hour outage in 2018

A 43 second network cut between data centers led to an automatic failover. Both sides had taken writes, and the data had to be reconciled by hand. Failover sounds simple and is one of the hardest parts of running databases.

A profile that looks unchanged

Users edited their bio and saw the old one. Reads went to replicas that lagged under load. The fix was routing a user's reads to the leader for 10 seconds after any write they made.

Read replicas save a news site

On election night reads jumped 20 times. The site added 5 read replicas and sent all article reads to them, while the leader only handled comments and edits.

Trade-offs

ChoiceGood atCosts you
SynchronousNo lost writes on failover.Every write waits for a follower. A slow follower slows everything.
AsynchronousFast writes.Recent writes can be lost if the leader dies.
Read from followersMany more reads served.Stale reads, need read your writes tricks.
Multi leaderLocal writes in every region, works offline.Write conflicts you must resolve.
Leaderless with quorumsNo single leader to fail, always writable.More complex reads, tuning, and repair.

Common mistakes

  • Treating replicas as backups.
  • Sending a read to a replica right after the same user wrote.
  • Automatic failover without fencing, which can cause split brain.
  • Assuming replication lag is always tiny. Watch it as a metric and alert on it.

Security lens

Every replica is another copy to protect.

  • Encrypt replication traffic, especially across regions.
  • Replicas need the same access control as the primary. A read replica used for analytics is a common leak.
  • Backups are not replicas. Replication copies a mistake or a ransomware encryption instantly. Keep point in time backups as well.
  • Delete requests under privacy laws must reach every replica and backup within your stated time.
