Distributed locks, leases and fencing tokens

Sometimes only one machine may do a job at a time, such as running the nightly invoice batch. Learn how distributed locks work, why every lock must expire, and why a lock alone cannot stop a paused worker from doing damage.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

On one machine, a lock is simple. A thread takes it, does the work and lets it go. Across many machines it is harder. The machines share no memory, they can pause, and the network can fail.

A distributed lock lives in a shared service, such as Redis, etcd, ZooKeeper or a database row. A worker asks for the lock. If it gets it, it does the job.

Every distributed lock needs a lease, a time limit. If the worker crashes while holding the lock, the lease runs out and someone else can take over. Without a lease, a crashed worker would hold the lock forever.

Leases bring a new danger. A worker can pause, for example during a long garbage collection, while its lease runs out. Another worker takes the lock and starts writing. Then the first worker wakes up, still believes it holds the lock, and writes too. The fix is a fencing token, a number that goes up every time the lock is granted. The storage refuses any write with a token older than the newest it has seen.

Think of it like this

A shared meeting room has a booking that ends at 3 pm. If you fall asleep inside, someone else books it at 3. Fencing is a door code that changes with each booking. When you wake up at 3:10, your old code no longer opens the door.

Words you need

Distributed lock
A lock held in a shared service, so only one of many machines does a task.
Lease
A lock that expires after a set time unless renewed.
Fencing token
A number that grows with every lock grant. Storage rejects writes with older tokens.
Process pause
A time when a program stops running, such as garbage collection, swapping or a paused VM.
Leader election
Choosing one node to act as leader, often done with the same tools as locks.
Ephemeral node
In ZooKeeper, a node that disappears when the session that made it ends.

How it works

Ways to build a lock

ToolHowFencing token
RedisSET lock:invoices worker1 NX PX 10000 sets the key only if it does not exist, with a 10 second expiryNot built in, you add a counter
etcdA lease with a TTL and a key bound to itUse the key's revision number
ZooKeeperAn ephemeral sequential nodeUse the transaction id or sequence number
DatabaseA row with an owner and an expiry, or a database advisory lockA version column that grows

Rules for using a lock safely

  1. Always set a lease. Pick it longer than the normal job, and renew it while you work.
  2. Release only your own lock. Store a unique value, and delete the key only if it still holds your value. In Redis, do the check and delete in one Lua script.
  3. Use fencing for anything that writes data. Pass the token to the storage, and have storage reject older tokens.
  4. Make the work idempotent anyway. A job can still run twice in rare cases.

Do you need a lock at all?

Often a lock is the wrong tool.

  • To stop two writers changing the same row, use a database transaction or a conditional update.
  • To run a job once, give it a unique id and let a queue deliver it to one worker.
  • To pick one leader, use an election in etcd, ZooKeeper or your platform. Kubernetes has a built in Lease object for this.
Careful

A lock that is only "for efficiency", to avoid doing the same work twice, can be simple. A lock that protects correctness, so data is not corrupted, needs fencing and a strongly consistent lock service. Know which one you are building.

Real life scenarios

The Redlock debate, 2016

Martin Kleppmann wrote that the Redlock algorithm for locks across several Redis servers is unsafe for correctness, because it depends on timing and has no fencing. Redis's creator Salvatore Sanfilippo replied with a defence. The debate is a good lesson in what locks can and cannot promise.

The cron job that ran twice

Two servers both ran the nightly invoice job after a failover, and some customers got two invoices. A lease based lock plus an invoice table with a unique rule per customer and month stopped repeats.

HBase and a long pause

Kleppmann's article points out that HBase once had exactly this problem. A server paused for garbage collection, its lease ran out, and it could still write after it woke up. Fencing is the standard defence.

Trade-offs

ChoiceGood atCosts you
Redis single node lockFast and simple.Lost on failover, no built in fencing.
etcd or ZooKeeper lockStrongly consistent, revisions work as fencing tokens.Another system to run, slower than Redis.
Database row lockNo new system, works with transactions.Load on the main database.
No lock, idempotent workNothing to fail or expire.Not every task can be made idempotent.

Common mistakes

  • A lock with no expiry.
  • Deleting a lock without checking that you still own it.
  • Trusting the lock alone to protect data, with no fencing.
  • A lease shorter than the job, with no renewal.
  • Using a distributed lock where a database transaction would do.

Security lens

Lock services are shared infrastructure. Require authentication, so a buggy or hostile client cannot take or delete every lock and freeze all jobs. Limit who can write lock keys, and alert when a lock is held much longer than normal.
