How a request travels across the internet

When you open a website, your phone finds the right computer, opens a line to it, asks a question and gets an answer. Every system you will ever design sits on top of this trip.

The idea in one minute

Every app is two sides talking. The client is the thing in your hand, like a phone app or a browser. The server is a computer somewhere else that holds the data and does the work. They talk by sending messages called requests and responses.

Before the client can ask anything, it has to find the server. Computers find each other by number, called an IP address. People remember names, like shop.com. So the first step is always to turn the name into a number. That is what DNS does.

Think of it like this

Sending a request is like sending a letter. DNS is the phone book that turns "Grandma" into her street address. TCP is the postal service that makes sure every page of the letter arrives, in order. HTTP is the language you write the letter in. TLS is the sealed envelope so nobody can read it on the way.

Words you need

Client
The side that asks. A browser, a phone app, or even another server.
Server
The side that answers. A computer that runs your code and holds or reaches your data.
IP address
The number of a computer on the internet, like 203.0.113.7. Like a street address.
DNS
Domain Name System. The internet's phone book. Turns shop.com into an IP address.
TCP
A way to send data that checks every piece arrives, in order, and resends lost pieces.
UDP
A faster way to send data with no checks. Lost pieces stay lost. Good for live video and games.
HTTP
The language of the web. A request has a method like GET or POST, a path and maybe a body. A response has a status code and a body.
TLS
The encryption layer. HTTP plus TLS is HTTPS.
Latency
How long one trip takes. Measured in milliseconds, written ms.
Port
A door number on a server. Web traffic uses 443 for HTTPS and 80 for plain HTTP.

How it works

Step 1. DNS turns a name into a number

Your phone first checks its own memory. If it does not know the answer, it asks a resolver, usually run by your internet provider or by a public service. The resolver may ask a chain of servers, the root, then the .com servers, then the servers that own shop.com. The answer comes back with a TTL, time to live, which says how many seconds it can be reused.

Key point

DNS is also a tool for architects. You can point one name at many servers, or at the closest data center. Short TTLs let you move traffic fast when something breaks.

Step 2. TCP opens a reliable line

TCP numbers every piece of data. The other side says "got it" for each one. Missing pieces are sent again. This makes TCP reliable, but every new connection costs a round trip before any real data moves. That is why apps reuse connections.

Step 3. TLS locks it

TLS proves the server is really shop.com with a certificate, then agrees on secret keys. Modern TLS 1.3 needs only one extra round trip.

Step 4. HTTP asks and answers

The request says what you want. The response says what happened.

Status codeMeaning in plain words
200OK, here is your answer
201Created the new thing you sent
301It moved, go here instead
400Your request is broken
401 and 403Who are you, or you are not allowed
404Not found
429Slow down, too many requests
500 and 503The server broke, or it is too busy

Why round trips matter

Light in fiber travels about 200,000 km a second. A trip from India to the US and back is about 200 ms no matter how fast your server is. So good designs cut the number of trips and move servers closer to users.

Real life scenarios

A website is down for some people only

The team moved the site to a new server and changed the DNS record. But the old record had a TTL of one day. Phones that had saved the old answer kept going to the old, empty server for up to a day. Lesson. Lower the TTL a day before a planned move, then raise it again after.

A shopping app feels slow on mobile data

Each screen made 12 separate requests, and each one opened a fresh connection. On a weak network each handshake took 300 ms. Reusing one connection and joining the calls into two requests cut load time by more than half.

A video call app picks UDP

If one frame of video is lost, resending it is pointless, because the moment has passed. The app uses UDP so it never waits for old data. A chat message in the same app uses TCP, because every word must arrive.

Trade-offs

ChoiceGood atCosts you
TCPEvery byte arrives, in order. Web pages, payments, chat messages.Extra round trips. One lost piece stalls the ones behind it.
UDPFast and simple. Live video, voice, games, DNS lookups.No delivery promise. Your app must handle loss itself.
Long DNS TTLFewer lookups, faster first load.Slow to move traffic when a server dies.
Short DNS TTLMove traffic in seconds. Good for failover.More DNS lookups, a little more latency.

Common mistakes

  • Thinking the server is the only thing that is slow. Often the network trips cost more than your code.
  • Forgetting that DNS answers are saved on phones and in resolvers, so a change is not instant.
  • Opening a new connection for every request instead of reusing one.
  • Using plain HTTP anywhere. Every link should be HTTPS, even between your own servers.

Security lens

Every hop a request makes is a place where it can be read, changed or faked.

  • DNS can be spoofed or hijacked. DNSSEC signs answers, and DNS over HTTPS hides them from the local network.
  • Plain HTTP can be read and changed by anyone on the path. Use HTTPS everywhere, with HSTS so browsers never fall back.
  • TLS proves the server's name with a certificate. Never turn off certificate checks in code.
  • BGP mistakes or attacks can send traffic to the wrong network. RPKI helps networks reject false routes.
