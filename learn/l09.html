Sharding and consistent hashing

When data is too big or writes are too many for one database, you split it across many. The hard part is choosing how to split and moving data when you add machines.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Replication copies all data to every machine. That helps reads but not writes, and every machine still holds everything. When the data or the write load is too big for one machine, you shard, also called partitioning. Each machine holds only part of the data.

The big decision is the shard key, the field that decides where each row goes. A good key spreads data and traffic evenly and keeps things that are read together on the same shard.

Think of it like this

A library too big for one room splits books into rooms by the author's last name. A to F in room 1, G to M in room 2, and so on. Finding a book is still easy if you know the author. But if half the authors start with S, room 4 gets crowded.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Shard
One piece of the data on its own machine.
Shard key
The field that decides which shard a row lives on.
Range sharding
Split by ranges of the key, like A to F. Good for range queries, risk of hot ranges.
Hash sharding
Split by a hash of the key. Spreads evenly, but range queries must ask every shard.
Consistent hashing
A ring of hash values where adding or removing a shard moves only a small share of keys.
Virtual nodes
Many points per real shard on the ring, for even spread.
Hot spot
One shard getting far more traffic than the others.
Scatter gather
A query that must ask every shard and combine the answers. Slow and expensive.

Choosing a shard key

  1. High cardinality. Many distinct values. country is bad, user_id is good.
  2. Even traffic. Avoid keys where one value is very busy.
  3. Matches your main query. If most queries are "this user's messages", shard by user_id so one query hits one shard.

Hot spots, the celebrity problem

Even with a good key, one value can be very busy, like a celebrity with 100 million followers. Fixes include adding a random suffix to split one hot key across several shards, caching hot items in front, or giving very large customers their own shard.

What you give up

  • Joins across shards are slow or impossible. Design so common queries stay in one shard.
  • Transactions across shards need extra machinery, see lesson 3.5.
  • Unique ids must work across shards, see lesson 3.4.
  • Resharding later is hard. Plan for growth, often by starting with many small logical shards that can move between machines.
Key point

Shard last, not first. Scale up, add replicas and caches first. Sharding solves real problems but makes every later change harder.

Real life scenarios

Instagram's shard ids

Instagram split data into thousands of logical shards mapped onto fewer physical Postgres servers. Moving a logical shard to a new server is much easier than rehashing everything.

The tenant that ate a shard

A business software company sharded by customer. One huge customer grew to 40 percent of all traffic and overloaded its shard. They moved big customers onto dedicated shards.

Discord's hot channels

A few huge servers sent most messages to a few partitions. Discord added request coalescing and routing changes so one hot channel could not swamp a storage node.

Common mistakes

  • Sharding by a low cardinality key like country or status.
  • Sharding too early, before trying bigger machines, replicas and caches.
  • Picking a key that makes the main query a scatter gather.
  • Using hash mod N, which makes adding a shard move almost everything.
  • Forgetting that celebrity keys can still create hot spots.

Security lens

Sharding can help security and can hurt it.

  • Tenant isolation. Sharding by customer can keep one customer's data apart from another's. Some customers ask for this.
  • Data residency. Shards in one country can keep data there to meet local law.
  • More shards means more places to patch, back up and monitor. Automate it.
  • Shard keys can leak. Do not use emails or national ids as visible keys.
