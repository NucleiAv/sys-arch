Your first AWS account, tools and a safe start

The first hour in a new cloud account decides a lot. Learn what the root user is and how to lock it away, the three ways to control AWS, how every resource is named, and how to stop a surprise bill before it happens.

The idea in one minute

When you create an AWS account, you get a root user, the email and password you signed up with. The root user can do everything, including closing the account and changing billing. It cannot be limited by normal permissions.

So the very first steps are always the same.

  1. Turn on MFA for the root user.
  2. Do not create access keys for the root user.
  3. Create named identities for daily work, ideally with IAM Identity Center for single sign on, or an IAM user with MFA in a small personal account.
  4. Set a budget with alerts, so you hear about cost early.
  5. Turn on CloudTrail logging.

You control AWS in three ways. The console, a website. The CLI, a command line tool. And SDKs and infrastructure as code, where programs or files describe what to build. Every call, from every tool, goes to the same AWS APIs and is checked against the same permissions.

Think of it like this

The root user is the master key to a building. You lock it in a safe and give everyone their own key card for daily use. You also put a meter on the door that warns you if the electricity bill gets too high.

Words you need

Root user
The identity created with the account. It has full, unlimited access.
MFA
Multi factor authentication. A second proof, such as a code or a security key.
Console
The AWS website for managing resources.
CLI
The AWS command line interface, for scripts and quick tasks.
SDK
Libraries for programming languages that call AWS APIs.
ARN
Amazon Resource Name. A unique name for any AWS resource.
Tag
A key and value label on a resource, such as owner=payments or env=prod.
CloudFormation
AWS's infrastructure as code service, using YAML or JSON templates.
AWS CDK
Cloud Development Kit. Write infrastructure in a programming language, which becomes CloudFormation.
Service quota
A limit on how much of a resource you can use, many can be raised on request.

How it works

Every resource has an ARN

arn:aws:s3:::my-report-bucket
arn:aws:iam::123456789012:role/app-reader
arn:aws:ec2:ap-south-1:123456789012:instance/i-0abc123

The parts are partition, service, region, account id and resource. Some fields are empty for global resources, like S3 bucket names and IAM.

Three ways to control AWS

WayGood forWatch out
ConsoleLearning, looking aroundClicks are hard to repeat and review
CLIQuick tasks, scriptsLong lived keys on laptops are risky. Use SSO login
Infrastructure as codeEverything in productionLearn one tool well, CloudFormation, CDK or Terraform

With the CLI, aws sso login gives short lived credentials, so no permanent keys live on your laptop.

Tags make the bill readable

Tag every resource with at least an owner, an environment and a cost center. Turn on cost allocation tags in billing so the bill can be split by them. Lesson 5.4 builds on this.

Avoid the classic surprise bills

  • Servers or databases left running after a test.
  • NAT gateways, which charge per hour and per GB.
  • Large GPU instances.
  • Data transfer out to the internet.
  • Logs kept forever.

The Free Tier covers some use of many services, but the rules differ by service and change over time. Always read them and always set a budget.

Key point

First hour checklist. Root MFA, no root keys, named users with MFA, budget alerts, CloudTrail on.

Real life scenarios

Code Spaces, 2014

Attackers got into the AWS console of Code Spaces, a code hosting company, and deleted most of its data and backups when the company would not pay. The company shut down. Backups in the same account, with no separate protection, could not save it.

The leaked key and the mining bill

A student pushed an access key to a public GitHub repository. Within hours, bots used it to start many servers for crypto mining in several regions. GitHub secret scanning and AWS now often detect such leaks fast, but the bill can still be large.

Console clicks nobody could repeat

A team built its first production setup by clicking in the console. When they needed a second region, nobody remembered every setting. They rebuilt it as code, which then took minutes to repeat.

Trade-offs

ChoiceGood atCosts you
ConsoleEasy to learn and explore.Hard to repeat, review or undo.
Infrastructure as codeRepeatable, reviewable, versioned.Learning curve, needs a pipeline.
IAM Identity CenterShort lived access, one place to manage people.A little setup at the start.
Long lived IAM user keysSimple for scripts.Leak risk. Prefer roles and short lived credentials.

Common mistakes

  • Using the root user for daily work.
  • Creating access keys for the root user.
  • Putting access keys in code or public repositories.
  • No budget alert.
  • Building production by clicking in the console.

Security lens

Treat account setup as a security task. Enable MFA everywhere, prefer short lived credentials from SSO and roles, enable CloudTrail in all regions with logs in a protected bucket, enable GuardDuty, and set alternate contacts for security and billing so AWS can reach the right people. Keep backups protected from the account they back up, lesson 5.3.
