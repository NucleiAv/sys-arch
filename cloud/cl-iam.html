IAM in depth, users, roles and policies

In the cloud, identity is the new firewall. Every request to AWS is checked against IAM. Learn users, groups and roles, how to read and write a policy, how AWS decides allow or deny, and why roles with short lived credentials beat stored keys.

The idea in one minute

IAM, Identity and Access Management, answers two questions for every AWS API call. Who is calling? And are they allowed to do this action on this resource?

IAM has a few kinds of identity.

  • Users. A person or an app with long lived credentials. In companies, people should usually sign in through IAM Identity Center instead, lesson 2.2.
  • Groups. A set of users that share permissions.
  • Roles. An identity that someone or something assumes for a while. It has no password or long lived key. When assumed, AWS's Security Token Service, STS, hands out temporary credentials that expire.

Permissions come from policies, JSON documents that say which actions are allowed or denied on which resources. By default everything is denied. A request is allowed only if some policy allows it and no policy denies it.

The golden rule is least privilege. Give each identity only the actions and resources it needs.

Think of it like this

IAM is the security desk of a huge building. Users are staff with permanent badges. Roles are visitor badges that work for an hour and then stop. Policies are the list on the guard's desk of which badge opens which door. If a door is not on the list, it stays shut.

Words you need

IAM user
An identity with long lived credentials, such as a password or access keys.
IAM group
A collection of users that share policies.
IAM role
An identity assumed for a limited time, giving temporary credentials.
STS
Security Token Service. Issues temporary credentials when a role is assumed.
Policy
A JSON document that allows or denies actions on resources.
Identity based policy
Attached to a user, group or role. Says what that identity can do.
Resource based policy
Attached to a resource, such as an S3 bucket policy. Says who can use it.
Explicit deny
A Deny statement. It always wins over any Allow.
Permissions boundary
A policy that sets the most permissions an identity can ever have.
Instance profile
The container that gives an EC2 instance a role.

How it works

Reading a policy

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ReadReports",
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": ["arn:aws:s3:::reports-bucket", "arn:aws:s3:::reports-bucket/*"],
    "Condition": {"Bool": {"aws:SecureTransport": "true"}}
  }]
}
  • Effect. Allow or Deny.
  • Action. Which API calls, written as service:Action.
  • Resource. Which ARNs. Note ListBucket applies to the bucket ARN, GetObject to the objects under it.
  • Condition. Extra rules, here only over HTTPS. Others include aws:MultiFactorAuthPresent, aws:SourceIp and aws:PrincipalOrgID.

How AWS decides, simplified

  1. Start with deny by default.
  2. If any applicable policy has an explicit Deny, the answer is deny. Stop.
  3. Organization SCPs and permissions boundaries must allow the action. They never grant on their own, they only limit.
  4. An identity based or resource based policy must allow it.
  5. Otherwise, deny.

For access across accounts, both sides must agree. The caller's identity policy must allow the action, and the resource's policy, or a role trust policy, must allow the caller.

Tools for least privilege

  • IAM Access Analyzer finds resources shared outside your account and can generate policies from what an identity actually used in CloudTrail.
  • Last accessed information shows permissions never used, so you can remove them.
  • Policy simulator tests a policy before you apply it.
Key point

Prefer roles and temporary credentials. Long lived access keys are the most common way AWS accounts get breached.

Real life scenarios

Capital One, 2019

An attacker used a server side request forgery flaw in a web firewall to get the temporary credentials of the instance's role from the metadata service. The role could list and read far more S3 buckets than it needed. Data on over 100 million people was taken. Least privilege on that role would have limited the damage.

Keys in a public repository

Long lived keys leaked to public code are found by bots within minutes. Moving CI pipelines to OIDC federation removes stored keys completely.

The wildcard policy

A developer gave a Lambda function "Action" "*" and "Resource" "*" to make an error go away. Months later a dependency in that function was compromised, and the attacker had full account access. Access Analyzer's policy generation now replaces such policies with what the function really uses.

Trade-offs

ChoiceGood atCosts you
IAM users with keysSimple for one off scripts.Keys leak and live forever unless rotated.
Roles and temporary credentialsExpire automatically, no secrets to store.A little more setup, especially across accounts.
Broad managed policiesQuick to start.Far more power than needed.
Custom least privilege policiesSmall blast radius.Need upkeep as the app changes.

Common mistakes

  • Using "Action": "*" with "Resource": "*" in application roles.
  • Long lived access keys for apps that could use roles.
  • Sharing one IAM user between several people.
  • Forgetting that an explicit Deny always wins, then debugging the wrong policy.
  • Trust policies that let any AWS account assume a role.

Security lens

IAM is your main security boundary. Enforce MFA for people, use roles for workloads, remove unused permissions every quarter, alert on new access keys, root sign ins and policy changes, and require IMDSv2 on EC2 so stolen metadata credentials are much harder to get through server side request forgery. Lesson 6.2 shows the attack paths that bad IAM opens.
