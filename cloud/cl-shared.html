The shared responsibility model and the Well-Architected Framework

AWS secures the cloud. You secure what you put in it. Learn exactly where that line sits for different services, and learn the six pillars of the AWS Well-Architected Framework, the checklist architects use to judge any cloud design.

The idea in one minute

Shared responsibility means security and running the system is split between the provider and you.

  • AWS is responsible for security OF the cloud. The buildings, the hardware, the global network, and the software that runs the services.
  • You are responsible for security IN the cloud. Your data, who can access it, how you set up the services, your operating systems if you run servers, and your code.

The line moves with the service. With an EC2 server, you patch the operating system. With a managed database like RDS, AWS patches the database engine, but you still decide who can connect. With S3, AWS runs the storage, but you choose whether a bucket is public.

The AWS Well-Architected Framework is a set of questions and best practices for building good cloud systems. It has six pillars.

  1. Operational excellence. Run and improve the system.
  2. Security. Protect data and systems.
  3. Reliability. Recover from failures and meet demand.
  4. Performance efficiency. Use resources well as needs change.
  5. Cost optimization. Avoid spending you do not need.
  6. Sustainability. Reduce the environmental impact.
Think of it like this

You rent a flat. The landlord fixes the roof, the pipes and the front door of the building. You lock your own door, choose who gets a key, and do not leave the windows open. Both of you must do your part.

Words you need

Shared responsibility model
AWS secures the cloud itself. Customers secure what they build and store in it.
Security of the cloud
AWS's part. Facilities, hardware, network, and the software that runs the services.
Security in the cloud
Your part. Data, identity, configuration, operating systems and code.
Well-Architected Framework
AWS's best practices for cloud systems, organized in six pillars.
Pillar
One area of quality, such as security or reliability.
Well-Architected Tool
A free AWS console tool that walks you through review questions and records risks.
Lens
Extra questions for a type of workload, such as serverless or machine learning.

The six pillars, with one key practice each

PillarKey practice
Operational excellenceInfrastructure as code, small reversible changes, learn from incidents
SecurityStrong identity, least privilege, encryption, traceability, automate security
ReliabilityMulti AZ, automatic recovery, test recovery, scale with demand
Performance efficiencyPick the right service and size, use managed services, measure
Cost optimizationPay only for what you need, measure cost per feature, use the right pricing model
SustainabilityUse less, use efficient hardware, right size, remove idle resources

Sustainability was added as the sixth pillar in December 2021.

How to run a Well-Architected review

  1. Pick one workload and the people who know it.
  2. Answer the questions for each pillar in the Well-Architected Tool.
  3. Record high risk issues and medium risk issues.
  4. Make an improvement plan with owners and dates.
  5. Repeat after big changes or once a year.

Microsoft Azure and Google Cloud have similar frameworks, called the Azure Well-Architected Framework and the Google Cloud Architecture Framework.

Key point

Most cloud breaches happen on the customer's side of the line. Misconfigured storage, leaked keys and too broad permissions.

Real life scenarios

Gartner's prediction

Gartner predicted in 2019 that through 2025, 99 percent of cloud security failures would be the customer's fault. Whatever the exact number, most public cloud breaches come from configuration and identity mistakes.

Public buckets and Block Public Access

After several years of data leaks from S3 buckets that were made public by mistake, AWS added S3 Block Public Access in 2018, and since April 2023 new buckets block public access by default.

A review finds a single point of failure

A team ran a Well-Architected review before a big launch and found their database ran in one AZ with no tested restore. They switched on multi AZ and ran a restore drill the week before launch.

Common mistakes

  • Assuming "it is in AWS, so it is secure".
  • Thinking a managed database means AWS controls who can connect.
  • Running a Well-Architected review once and never acting on it.
  • Optimizing one pillar, such as cost, and silently breaking another, such as reliability.

Security lens

The shared responsibility model is the start of every cloud threat model. For each service, write down which controls are yours, then check you have them, identity, network rules, encryption, logging and patching. Compliance reports from AWS, available in AWS Artifact, cover AWS's side only. Your auditors will still check yours.
