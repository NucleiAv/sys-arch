EC2, pricing options, Auto Scaling and load balancers

Virtual servers are the oldest cloud building block and still run a huge share of workloads. Learn how to pick an instance type, the four ways to pay, how Auto Scaling keeps the right number of servers, and which load balancer to use.

The idea in one minute

Amazon EC2 rents virtual servers, called instances. You pick an instance type, which sets CPU, memory, network and sometimes GPUs, and an AMI, the disk image with the operating system.

How you pay matters as much as what you run.

  • On Demand. Pay by the second or hour, no commitment. Most expensive per hour, most flexible.
  • Savings Plans and Reserved Instances. Commit to a steady amount of use for 1 or 3 years for a large discount.
  • Spot. Use spare AWS capacity at a big discount, but AWS can take it back with a two minute warning. Great for work that can stop and restart.
  • Dedicated Hosts. A whole physical server for you, for some licences and compliance needs.

An Auto Scaling group keeps the number of instances right. It replaces unhealthy ones, spreads them across AZs, and adds or removes instances as load changes. A load balancer spreads requests across them and only sends to healthy ones.

Think of it like this

EC2 is renting cars. On Demand is a taxi, pay per ride. Savings Plans are a yearly car lease, cheaper if you drive a lot. Spot is a cheap ride share that can drop you off early. Auto Scaling is a manager who calls more cars when the queue grows and sends them away when it shrinks.

Words you need

Instance type
The size and kind of an EC2 server, such as m7g.large. The letter is the family, the number the generation.
AMI
Amazon Machine Image. The template disk an instance boots from.
Launch template
Saved settings for launching instances, such as AMI, type, network and role.
On Demand
Pay per second or hour with no commitment.
Savings Plans
A 1 or 3 year commitment to spend per hour, for large discounts.
Spot Instance
Spare capacity at a big discount that AWS can reclaim with a two minute notice.
Auto Scaling group
Keeps a healthy number of instances, spread across AZs, scaling with load.
ALB
Application Load Balancer. Layer 7, routes HTTP and HTTPS by path, host and headers.
NLB
Network Load Balancer. Layer 4, TCP and UDP, very high throughput, static IP per AZ.
Placement group
Controls how instances are placed, cluster for low latency, spread for isolation, partition for big distributed systems.

How it works

Instance families, the first letter

FamilyGood for
General purpose, such as M and TWeb apps, small databases. T types are burstable
Compute optimized, CBatch, video encoding, high CPU
Memory optimized, R and XLarge caches, in memory databases
Storage optimized, I and DHigh disk throughput, local NVMe
Accelerated, such as G, P, Inf, TrnGPUs and AI chips, ML training and inference

A g after the generation number, such as m7g, means an AWS Graviton ARM processor, often cheaper for the same work.

Paying for compute

OptionDiscount versus On DemandFits
On DemandNoneSpiky, short, unknown workloads
Savings Plans or Reserved InstancesUp to about 72 percentSteady base load
SpotUp to about 90 percentBatch, CI, stateless workers that can be stopped

A common mix is Savings Plans for the base, On Demand for peaks, and Spot for anything that can be interrupted.

Scaling policies

  • Target tracking. Keep a metric near a target, such as 50 percent CPU. The simplest good default.
  • Step scaling. Add more instances as an alarm gets worse.
  • Scheduled. Scale before known events, such as 9 am on weekdays.
  • Predictive. Uses past patterns to scale ahead of daily cycles.

Load balancer types

TypeLayerUse
Application Load Balancer7, HTTP and HTTPSWeb apps, path and host routing, WAF
Network Load Balancer4, TCP, UDP, TLSExtreme throughput, static IPs, non HTTP
Gateway Load Balancer3, IP packetsThird party firewalls and inspection appliances

Make instances disposable

Build images or launch templates so any instance can be replaced at any time. Keep no important data on the instance. Use user data or configuration tools for setup, and Systems Manager for access instead of SSH.

Key point

Treat servers like cattle, not pets. If any instance can die and be replaced automatically, Auto Scaling, Spot and multi AZ all become easy.

Real life scenarios

Spot for big batch jobs

Many companies run CI builds, rendering and data processing on Spot, saving most of the On Demand price. Jobs save progress often, so an interruption only repeats a few minutes of work.

The burstable surprise

A team ran a busy API on a small T instance. It was fast for an hour, then very slow, because it used up its CPU credits. Moving to an M instance gave steady speed.

Scaling on the wrong metric

An app was limited by database connections, not CPU. Scaling on CPU added servers that only opened more connections and made things worse. Scaling on request latency and fixing the connection pool solved it, see Concepts lesson 2.8.

Trade-offs

ChoiceGood atCosts you
On DemandNo commitment.Highest price per hour.
Savings PlansLarge discount for steady use.1 or 3 year commitment.
SpotVery cheap.Can be stopped with two minutes notice.
Larger instances, fewer of themFewer things to manage.Each failure removes more capacity.
Smaller instances, more of themFiner scaling and smaller failures.More instances to run.

Common mistakes

  • Keeping important data only on an instance's local disk.
  • Running all instances in one AZ.
  • Using Spot for work that cannot be interrupted.
  • Scaling on a metric that is not the real bottleneck.
  • Paying On Demand for a steady base load for years.

Security lens

Instances need patching, so build images regularly and replace instances instead of patching by hand. Require IMDSv2, give each instance a least privilege role, keep instances in private subnets, use Systems Manager Session Manager instead of open SSH, encrypt EBS volumes by default, and scan images with Amazon Inspector.
