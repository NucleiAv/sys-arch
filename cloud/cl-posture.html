GuardDuty, Security Hub, Inspector, Macie and posture management

AWS gives you a set of security services that watch for attacks, scan for weak spots and check settings against best practice. Learn what each one does, how they fit together across many accounts, and how cloud security posture management keeps hundreds of accounts in good shape.

The idea in one minute

Two different questions matter in cloud security.

  1. Is someone attacking us right now? That is threat detection. GuardDuty answers it.
  2. Are we set up safely? That is posture. Security Hub, AWS Config, Inspector, Macie and IAM Access Analyzer answer it.

Cloud security posture management, or CSPM, means checking all your cloud settings all the time against rules, such as "no bucket is public" and "every volume is encrypted", and fixing what fails. Most cloud breaches come from misconfiguration, not from clever exploits, so posture is where most of the work is.

  • GuardDuty reads CloudTrail, VPC Flow Logs and DNS logs, plus optional sources such as S3 data events, EKS logs and runtime agents, and finds threats like stolen keys used from a strange place, crypto mining or calls to known bad hosts.
  • Inspector scans EC2 instances, container images in ECR and Lambda functions for known software vulnerabilities and open network paths.
  • Macie finds sensitive data, such as card numbers and personal data, in S3, and flags buckets that are public or shared.
  • IAM Access Analyzer finds resources shared outside your account or organization, and unused access.
  • AWS Config records settings and checks them with rules.
  • Security Hub collects findings from all of these, and from partner tools, into one place, and scores you against standards such as the CIS AWS Foundations Benchmark and AWS Foundational Security Best Practices.
  • Detective builds graphs from logs to help you investigate a finding.
Think of it like this

Think of a big school. GuardDuty is the guard who watches the cameras for intruders. Inspector checks every door lock for known faults. Macie finds where the exam papers are kept and warns if one is left on a public table. Config and Security Hub are the safety inspector with a checklist who visits every classroom every day and gives the school a score.

How it works

Turn it on everywhere, manage it from one place

  1. In AWS Organizations, make the security account the delegated administrator for GuardDuty, Security Hub, Inspector, Macie, Config and Access Analyzer.
  2. Turn the services on for all accounts and all regions, including regions you do not use, since attackers like those.
  3. Use auto enable so new accounts are covered from day one.
  4. Send findings to one place. Security Hub, then your SIEM and ticket system.

What to look at first

PriorityExample
Active threatGuardDuty high severity, root account use, keys used from a new country
Exposed dataPublic buckets, Macie finding sensitive data, Access Analyzer external sharing
Exploitable vulnerabilityInspector critical CVE on an internet facing instance
Weak settingsSecurity Hub failed controls, such as no MFA on root or unencrypted volumes

From finding to fix

  • Automatic remediation for safe, clear cases, such as turning Block Public Access back on.
  • Tickets with owners for the rest, found by account and tags.
  • Prevent repeats with SCPs, templates and checks in the pipeline, so the same mistake cannot be deployed again.
  • Measure time to fix by severity.

Third party CSPM and CNAPP

Many companies also use tools that cover AWS, Azure and Google Cloud together and draw attack paths, such as "public instance, with a critical CVE, with a role that can read the customer bucket". These are often called cloud native application protection platforms, or CNAPP. Open source tools such as Prowler and ScoutSuite run similar checks for free.

Key point

Detection tells you about attacks. Posture stops most attacks from working in the first place. Turn both on in every account and region, and manage them from a delegated security account.

Real life scenarios

Leaked keys and crypto mining

Leaked AWS keys in public code are found by bots within minutes and are often used to launch crypto mining instances. AWS also scans public GitHub for its keys and warns the account owner. GuardDuty has specific findings for this pattern.

Public buckets keep happening

Over the years, many companies exposed data in public S3 buckets by mistake, from voter records to customer files. S3 Block Public Access, and since April 2023 private by default for new buckets, plus Config and Macie checks, are the fixes.

Hundreds of accounts, one view

Large AWS users run GuardDuty and Security Hub across hundreds of accounts from one security account. A new account gets the same detection automatically within minutes of being created.

Trade-offs

ChoiceGood atCosts you
All services in all regionsNo blind spots.Cost grows with log volume and accounts.
Automatic remediationFast fixes, less manual work.A bad rule can break production, start with alerts.
Native AWS toolsDeep AWS coverage, simple setup.One cloud only. Multi cloud teams add a third party tool.

Common mistakes

  • Turning on GuardDuty in only one region.
  • Thousands of findings and no owners, so nothing gets fixed.
  • Fixing findings by hand without adding a guardrail.
  • Letting each team turn security services off in its own account.
  • Treating a high Security Hub score as proof of being secure.

Security lens

Protect the security tooling itself. Run it from a dedicated security account, use SCPs so member accounts cannot disable GuardDuty, Config or CloudTrail, and alert if anyone tries. Restrict who can archive or suppress findings, since an attacker with that power can hide. Test your detections with safe attack simulation tools such as Stratus Red Team in a lab account.
