Managed databases, RDS, Aurora, DynamoDB, ElastiCache and friends

AWS runs databases for you, backups, patching, replicas and failover included. Learn the difference between multi AZ and read replicas, when Aurora or DynamoDB fits, how caches cut load, and how to pick from AWS's many purpose built databases.

The idea in one minute

Running a database yourself means installing it, patching it, backing it up, copying it to standby servers and handling failover at 3 am. Managed databases do most of that for you.

  • Amazon RDS runs familiar relational engines, such as PostgreSQL, MySQL, MariaDB, Oracle and SQL Server.
  • Amazon Aurora is AWS's own engine, compatible with PostgreSQL and MySQL, built for the cloud. Its storage keeps six copies across three AZs and grows automatically.
  • Amazon DynamoDB is a serverless key value and document database with single digit millisecond reads at any scale.
  • Amazon ElastiCache runs Redis compatible engines, including Valkey, or Memcached, as an in memory cache.

Two words that people mix up.

  • Multi AZ is for availability. A standby copy in another AZ takes over if the primary fails.
  • Read replicas are for read scaling. Copies that serve read only queries, updated asynchronously, so they can be slightly behind.
Think of it like this

A managed database is like a library with full time staff. They fix the shelves, keep a spare copy of every book in another building, and can open extra reading rooms when the library gets busy. You just bring readers and books.

Words you need

RDS
Relational Database Service. Managed PostgreSQL, MySQL, MariaDB, Oracle and SQL Server.
Aurora
AWS's cloud native relational engine, compatible with MySQL and PostgreSQL.
Multi AZ
A standby in another AZ for automatic failover. For availability, not read scaling, in classic RDS.
Read replica
An asynchronous read only copy for scaling reads or reporting.
DynamoDB
Serverless key value and document database with predictable low latency at any scale.
GSI
Global secondary index in DynamoDB, for querying by another key.
DAX
DynamoDB Accelerator. An in memory cache in front of DynamoDB.
ElastiCache
Managed in memory cache with Redis compatible engines or Memcached.
Redshift
A columnar data warehouse for analytics over large data.
Point in time recovery
Restoring a database to any second within a retention window.

Aurora in short

  • Storage keeps 6 copies across 3 AZs and grows automatically.
  • Up to 15 low lag Aurora Replicas share the same storage, and one is promoted on failure.
  • Aurora Global Database copies to other regions, usually with under a second of lag, for disaster recovery and local reads.
  • Aurora Serverless v2 scales capacity up and down in small steps.

DynamoDB in short

  • Pick a good partition key, as in Concepts lesson 2.4, so load spreads evenly.
  • On demand capacity for unknown traffic, provisioned with auto scaling for steady traffic.
  • Global tables for active active multi region.
  • Items up to 400 KB. Point in time recovery up to 35 days.
  • Design the table around your access patterns, not around entities.

Key point

Multi AZ keeps you up. Read replicas spread reads. Backups and point in time recovery save you from mistakes. You usually need all three.

Real life scenarios

Amazon's Prime Day on DynamoDB

AWS has reported that DynamoDB peaked at more than 100 million requests per second during recent Amazon Prime Day events, while keeping single digit millisecond latency.

Read replica as a backup

A team thought its read replica was a backup. A bad migration dropped a table, and the drop replicated to the replica within seconds. Point in time recovery from automated backups saved them.

The hot partition

A DynamoDB table used the date as its partition key, so every write of the day went to one partition and was throttled. A key with many values, such as the user id, spread the load.

Common mistakes

  • Treating a read replica or multi AZ standby as a backup.
  • Expecting the classic multi AZ standby to serve reads.
  • A DynamoDB partition key with few distinct values.
  • Running a database on EC2 by hand when a managed service fits.
  • No tested restore.

Security lens

Keep databases in isolated subnets with security groups that allow only the app tier. Encrypt at rest with KMS and in transit with TLS. Use IAM database authentication or Secrets Manager with rotation instead of fixed passwords, turn on deletion protection, and copy backups to a separate account. Turn on database activity logs, and never make a snapshot public.
