KMS, encryption and secrets on AWS

Encryption on AWS is mostly a few clicks, but only if you understand who holds the keys and who may use them. Learn KMS and envelope encryption, the S3 encryption options, where to keep passwords and API keys, and how TLS certificates are managed.

The idea in one minute

Encryption turns data into unreadable bytes that only someone with the right key can turn back. On AWS, keys live in AWS KMS, the Key Management Service. KMS keeps keys inside hardware security modules, and the key material never leaves them unencrypted.

KMS does not encrypt your large files directly. It uses envelope encryption.

  1. A service asks KMS for a data key.
  2. KMS returns the data key twice, once in plain form and once encrypted under your KMS key.
  3. The service encrypts your data with the plain data key, throws the plain key away, and stores the encrypted data key next to the data.
  4. To read, it sends the encrypted data key to KMS. If the caller is allowed, KMS decrypts it, and the service decrypts the data.

The important part is step 4. Every decrypt needs permission to use the KMS key, and every use is logged in CloudTrail. So encryption with your own KMS key adds a second lock. Even someone who can read the S3 object cannot decrypt it without kms:Decrypt on that key.

Passwords, API keys and database credentials are secrets. Keep them in Secrets Manager or Parameter Store, never in code or plain environment variables.

Think of it like this

Your diary is locked with a small padlock. You put the padlock's key in a bank safety box. To open the diary, you must go to the bank, show your ID, and the bank writes down every visit. KMS is the bank.

Words you need

KMS
AWS Key Management Service. Creates and controls encryption keys, kept in hardware security modules.
KMS key
The main key in KMS, used to encrypt data keys. Its material never leaves KMS unencrypted.
Data key
A key used to encrypt the actual data, stored encrypted next to it.
Envelope encryption
Encrypting data with a data key and encrypting the data key with a master key.
Key policy
The resource policy on a KMS key that says who can use and manage it.
CloudHSM
Dedicated hardware security modules that you control, for strict key custody needs.
Secrets Manager
Stores secrets and can rotate them automatically.
Parameter Store
Part of Systems Manager. Stores configuration and secrets as SecureString values.
ACM
AWS Certificate Manager. Issues and renews TLS certificates for AWS services.

How it works

Three kinds of KMS keys

KindWho managesUse
AWS ownedAWS, invisible to youDefault encryption in some services
AWS managedAWS, in your account, named like aws/s3Easy encryption, you cannot change its policy
Customer managedYouYour own key policy, rotation and audit. Best for sensitive data

Customer managed keys can rotate automatically, by default once a year. Old versions stay available to decrypt old data.

S3 encryption options

OptionKeyNotes
SSE-S3Keys managed by S3Default for all new objects since January 2023
SSE-KMSA KMS keyExtra access control and audit through KMS
DSSE-KMSTwo layers with KMSFor rules that need dual layer encryption
SSE-CA key you send with each requestAWS does not store your key
Client sideYou encrypt before uploadAWS never sees plain data

Where secrets go

NeedChoice
Database password with automatic rotationSecrets Manager
Simple config values and some secrets, low costParameter Store SecureString
Keys used by many apps, with cross account sharingSecrets Manager with a resource policy

Apps read secrets at runtime using their role. Nothing is written in code, images or plain environment variables that many people can read.

Certificates

ACM gives free public TLS certificates for services such as load balancers, CloudFront and API Gateway, and renews them automatically. Private certificates for internal services come from AWS Private CA.

Data in transit

Use TLS everywhere. Many policies can require it, for example the S3 condition aws:SecureTransport.

Key point

Encryption with a customer managed key adds an access check and an audit log on every read. Who may decrypt is as important as who may read.

Real life scenarios

Uber, 2016

Attackers found AWS access keys in a private code repository and used them to download data on 57 million riders and drivers from S3. Secrets in code, even private code, are a classic path to a breach.

Keys that saved a leak

A bucket was accidentally shared with another account. Because its objects used a customer managed KMS key that the other account could not use, the files could not be read.

Rotation without downtime

A team moved database passwords to Secrets Manager with automatic rotation. Apps fetched the current value at start and on connection errors, so passwords changed every 30 days with no outage.

Trade-offs

ChoiceGood atCosts you
AWS managed keyNo setup.No custom key policy, less control.
Customer managed keyYour own policy, audit and rotation.Small cost per key and per request, more to manage.

Common mistakes

  • Secrets in code, Docker images or plain environment variables.
  • Thinking encryption at rest protects against a user who is allowed to decrypt.
  • Key policies that let everyone in the account use the key.
  • Deleting a KMS key that still protects data. KMS enforces a waiting period of 7 to 30 days for this reason.
  • No TLS between internal services.

Security lens

Treat kms:Decrypt as a sensitive permission. Separate key administrators from key users, keep key policies tight, alert on key deletion or disabling, and review CloudTrail for unusual decrypt calls. For backups, use keys in a separate account so a compromised workload account cannot destroy both the data and its keys.
