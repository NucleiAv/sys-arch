Tier 1. A mission critical payments API across two regions

A bank's payment API must keep working when a whole AWS region fails, with seconds of data loss at most and no double payments. Design it active active across Mumbai and Hyderabad, with cells, static stability, controlled failover and PCI grade security.

The ask

The bank runs a payment API that apps and partners call to send money and approve card payments. If it stops, customers cannot pay and the bank breaks its rules with the regulator. Design it as a tier 1 system on AWS.

This is a fictional design for learning. Real national payment switches, such as UPI, run in their operators' own data centers.

Pin down the requirements

What it must do

  • Accept a payment request, check balance and limits, run fraud checks, record it and reply.
  • Return the same result if a client retries the same request.
  • Send events for settlement, notifications and the ledger.

How well it must do it

  • Availability 99.99 percent. RTO under 5 minutes. RPO a few seconds.
  • Survive the loss of one AZ with no impact and one region with a short, controlled failover.
  • p99 latency under 300 ms inside India.
  • Never pay twice. Data stays in India. PCI DSS for card data.

Out of scope, say it out loud

  • Interbank settlement and the core banking ledger internals.

Do the math

Peak load is 6,000 payments a second in total during festival sales. Each payment writes 3 records. Each region must be able to take all traffic alone. Each region has 3 AZs and must keep full speed if one AZ fails.

Key point

Tier 1 is expensive on purpose. Each region is sized for the whole peak, and each region for an AZ loss, so failure needs no scaling during the crisis.

The API

POST /v1/payments
Idempotency-Key: 7f3c...        (required, unique per payment)
{ "from": "acct_123", "to": "vpa:asha@bank", "amount": 1250.00, "currency": "INR" }

201 { "payment_id": "pay_9x...", "status": "approved", "region": "ap-south-1" } 409 same key with a different body GET /v1/payments/{id} ```

Partners call over mutual TLS with signed requests. Retries with the same key always return the first result.

The big picture

  1. Two regions, both active. Mumbai and Hyderabad, three AZs each, each sized for full peak. No region depends on the other to serve its own cells.
  2. Cells. Customers are split into cells, each a full copy of the stack with its own capacity. A bad deploy or poison request hurts one cell, not everyone.
  3. Home region per customer. All writes for one customer go to one region at a time, which avoids conflicting writes. DynamoDB global tables replicate to the other region.
  4. Routing. Route 53 with health checks, and Application Recovery Controller routing controls for a deliberate, tested failover switch that does not need the failing region's control plane.
  5. Compute. EKS or ECS on Fargate across three AZs per region, with pre scaled capacity, not waiting for auto scaling in a crisis.
  6. Idempotency. Every write is keyed by the client's idempotency key, stored with the result.
  7. Async side work. Ledger posting, settlement and notifications run from events, so they cannot slow the payment path.
  8. Operations. Deploy one cell and one region at a time with automatic rollback, game days every quarter, and regional failover tested in production with real traffic.

Deep dives

Why not let both regions write the same customer

With async replication, two regions could approve two payments from the same balance at the same moment. A home region per customer gives one writer at a time. The cost is a tiny window of unreplicated writes during a sudden region loss, handled by idempotency and reconciliation.

Static stability

A system is statically stable when it keeps working through a failure without needing to change anything, such as launching instances or changing DNS in the failing region. Pre provisioned capacity and data plane routing give that.

Why a manual switch for regions

Automatic region failover can flip back and forth on noisy health checks and cause more harm. Many tier 1 teams use automatic AZ failover but a deliberate, rehearsed one click region failover, with clear criteria.

Dependencies must be tier 1 too

If fraud scoring, keys or DNS live in one region, the payment API cannot really survive that region. Every dependency in the payment path is checked for its own multi region design, or removed from the critical path with a safe fallback.

Security and abuse

  • PCI DSS scope kept small. Card numbers are tokenized in a separate PCI account. The payment API sees only tokens.
  • Keys. Customer managed KMS keys per region, multi Region keys only where needed, CloudHSM for card and PIN related keys.
  • Edge. AWS WAF with rate limits per partner, Shield Advanced, mutual TLS and request signing for partners.
  • Network. No inbound internet to app subnets. Private endpoints for AWS services. Egress only to named partners through the inspection VPC.
  • Identity. Workload roles per service, no human write access to production data, just in time access with approval for break glass.
  • Fraud and abuse. Velocity limits and fraud scoring inline with a strict time budget, and a safe default if the scorer times out.
  • Evidence. CloudTrail, data events on sensitive tables, and all failover actions logged for the regulator.
