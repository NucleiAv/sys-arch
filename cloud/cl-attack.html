How cloud accounts get attacked, and how to respond

Attackers in the cloud rarely break encryption. They steal keys, abuse trust, and use your own APIs against you. Walk through the common attack paths with real breaches, learn how to block each step, and practise the incident response playbook for a compromised AWS account.

The idea in one minute

In the cloud, the API is the attack surface. Anyone with valid credentials can do anything those credentials allow, from anywhere on the internet. So most cloud attacks are about getting credentials and then using permissions.

A typical attack path has these steps.

  1. Initial access. Leaked access keys in code, a server side request forgery bug that reads the instance metadata service, a phished SSO login, or a vulnerable public app.
  2. Discovery. Calls like sts:GetCallerIdentity and listing buckets, roles and instances to see what the credentials can do.
  3. Privilege escalation. Using a risky permission, such as creating a new policy version or passing an admin role to a new Lambda function, to become more powerful.
  4. Persistence. Creating new access keys, new users, or roles that trust the attacker's own account.
  5. Defense evasion. Stopping CloudTrail, deleting GuardDuty detectors, or working in unused regions.
  6. Impact. Copying data out, mining crypto, or deleting resources and backups for ransom.

Defenders break this chain at every step. No long term keys, IMDSv2, least privilege, SCPs that protect logging, detection, and isolated backups.

Think of it like this

A thief does not need to break the bank vault if they can find a staff badge on the floor. In the cloud the badge is an access key. Once inside, the thief tries every door the badge opens, looks for a master key, hides from the cameras, and takes what they can. Good banks give each badge only a few doors, make badges expire fast, and keep cameras the thief cannot switch off.

Words you need

Attack path
The chain of steps an attacker takes from first access to their goal.
SSRF
Server side request forgery. Tricking a server into making a request for the attacker.
Instance metadata service
An internal address on EC2 that gives the instance its settings and role credentials.
IMDSv2
Version 2 of the metadata service, which needs a session token from a PUT request first.
Privilege escalation
Using one permission to gain more permissions.
Persistence
Ways an attacker keeps access, such as new keys or trusted roles.
Data perimeter
Policies that allow access only from your identities, your resources and your networks.
Containment
Stopping an attack from spreading while you investigate.
Forensics
Collecting and studying evidence, such as disk snapshots and logs.

Common initial access, and the fix

How attackers get inFix
Access keys in code, images or laptopsNo long term keys. Roles, Identity Center, OIDC for CI. Secret scanning.
SSRF to the metadata serviceRequire IMDSv2, set hop limit 1 for containers, fix the app
Phished console or SSO loginPhishing resistant MFA, short sessions

Third party with too much accessExternal ID, narrow roles, review trust policies

Risky permissions that allow privilege escalation

  • iam:CreatePolicyVersion, iam:AttachUserPolicy, iam:PutRolePolicy. Change your own permissions.
  • iam:PassRole with lambda:CreateFunction or ec2:RunInstances. Run code as a more powerful role.
  • iam:CreateAccessKey on other users. Become them.
  • sts:AssumeRole on a role with a weak trust policy.

Use permissions boundaries, limit iam:PassRole to specific roles, and check with Access Analyzer and tools like Prowler.

Incident response for a compromised account

  1. Prepare. Logs in a separate account, break glass access, a written playbook, contacts, and practice.
  2. Detect and analyse. GuardDuty, alerts, CloudTrail. Which identity, from where, what did it call?
  3. Contain. Deactivate the keys, revoke active role sessions, isolate instances with an empty security group, block the attacker's IPs. Do not delete evidence.
  4. Collect evidence. Snapshot EBS volumes, save memory if needed, copy logs.
  5. Eradicate. Remove new users, keys, roles, trust policies and resources the attacker created, in every region.
  6. Recover. Rebuild from known good templates and clean backups. Rotate secrets.
  7. Learn. Post incident review and new guardrails.
Key point

Assume keys will leak. Make them short lived, narrow and usable only from places you expect, and make sure you will see and stop their misuse quickly.

Real life scenarios

Capital One, 2019

An attacker used SSRF through a misconfigured web application firewall on EC2 to get role credentials from the metadata service, then read S3 data on about 106 million people. US regulators fined the bank 80 million dollars. AWS released IMDSv2 later that year.

Code Spaces, 2014

An attacker got into the company's AWS control panel and demanded a ransom. When staff tried to take back control, the attacker deleted servers, data and backups, which were in the same account. The company shut down within days.

Uber, 2016

Attackers found AWS credentials in a private code repository used by Uber engineers and used them to download data on 57 million riders and drivers from S3.

Common mistakes

  • Long term access keys for apps and CI.
  • IMDSv1 still allowed.
  • Roles with s3:* on all buckets "for convenience".
  • Backups in the same account as production.
  • Cleaning up in one region and missing the others.
  • No practice before the real incident.

Security lens

Practise attacks only on systems you own or have written permission to test, or on purpose built labs such as flAWS, CloudGoat and CloudFoxable listed on the track page. AWS allows customers to test their own resources for many services without asking first, but some activities, such as DoS tests, have their own rules, so read the AWS penetration testing policy before you start.
