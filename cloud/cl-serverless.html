Lambda, API Gateway, SQS, SNS, EventBridge, Step Functions and Kinesis

Serverless means you write the code and AWS runs, scales and patches everything under it, and you pay per request. Learn Lambda's limits, how API Gateway fronts it, and how queues, topics, event buses, workflows and streams connect services so they can fail and scale on their own.

The idea in one minute

AWS Lambda runs your function when an event happens, such as an HTTP request, a file landing in S3, or a message on a queue. You do not manage servers. Lambda starts as many copies as needed and you pay for the number of requests and the time your code runs.

Lambda has limits to remember. A function can run for at most 15 minutes, use 128 MB to 10,240 MB of memory, and the first request to a new copy can be slower, a cold start.

API Gateway puts an HTTPS API in front of Lambda or other backends, with authentication, throttling and request checks.

To connect services without tight coupling, AWS has several integration services, the cloud versions of Concepts lessons 3.2 and 3.6.

  • SQS. A queue. One consumer handles each message.
  • SNS. A topic. One message fans out to many subscribers.
  • EventBridge. An event bus with rules that route events to targets, including events from AWS services and SaaS apps.
  • Step Functions. Workflows with steps, retries, branches and waits, drawn as a state machine.
  • Kinesis Data Streams. An ordered stream with shards, like Kafka, for high volume real time data.
Think of it like this

Serverless is like ordering food delivery instead of running a kitchen. You choose the dish, they cook it when you order, and you pay per meal. SQS is a ticket rail, SNS is a loudspeaker, EventBridge is a post office sorting room, and Step Functions is the recipe card that says which step comes next.

Words you need

Lambda
Runs functions on events with no servers to manage, billed per request and duration.
Cold start
Extra delay when a new copy of a function starts for the first time.
Concurrency
How many copies of a function run at once. Accounts have a regional limit.
API Gateway
A managed front door for HTTP, REST and WebSocket APIs.
SQS
Simple Queue Service. Standard queues are at least once with best effort order. FIFO queues keep order.
Visibility timeout
How long a received SQS message is hidden from other consumers while it is processed.
SNS
Simple Notification Service. Pub sub topics that fan out to many subscribers.
EventBridge
An event bus that routes events by rules to targets.
Step Functions
Managed workflows built as state machines with retries and error handling.
Kinesis Data Streams
Ordered, replayable streams split into shards, for real time data.

Pick the integration service

NeedChoose

SQS settings that matter

  • Visibility timeout must be longer than processing time, or messages are handled twice. Default 30 seconds, up to 12 hours.
  • Message retention from 1 minute to 14 days, default 4 days.
  • Dead letter queue with a maximum receive count, so poison messages move aside.
  • Long polling reduces empty responses and cost.

API Gateway types

  • HTTP API. Cheaper, faster, simpler, good default for Lambda proxies.
  • REST API. More features, such as usage plans, API keys and request validation.
  • WebSocket API. Two way connections for chat and live updates.

Remember API Gateway's integration timeout, 29 seconds by default. Long work should be queued and answered later.

Key point

Serverless removes servers, not design. You still need idempotent handlers, dead letter queues, limits and timeouts, as in Concepts levels 3 and 4.

Real life scenarios

iRobot on serverless

iRobot has described running much of the cloud backend for its connected robot vacuums on serverless AWS services, so a small team could serve millions of devices without managing servers.

The visibility timeout bug

A team's function took 45 seconds per message, but the queue's visibility timeout was 30 seconds. Messages reappeared and were processed twice, sending duplicate emails. Raising the timeout and making the handler idempotent fixed it.

Recursive loop bill

A Lambda triggered by S3 uploads wrote its output to the same bucket, which triggered it again and again. Lambda now detects and stops some recursive loops, but separate buckets or prefixes are the real fix.

Common mistakes

  • Long jobs in Lambda that hit the 15 minute limit.
  • Visibility timeout shorter than processing time.
  • No dead letter queue.
  • A Lambda that writes to the bucket that triggers it.
  • Synchronous chains of Lambdas calling each other through API Gateway.

Security lens

Give each Lambda its own execution role with least privilege, keep secrets in Secrets Manager, validate every event, since an S3 key or a queue message is still untrusted input, set reserved concurrency to cap cost and blast radius, and protect API Gateway with authorizers, WAF and throttling. Serverless still needs dependency scanning, as functions ship libraries too.
