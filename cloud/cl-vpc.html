VPC design, subnets, routes and firewalls

A VPC is your own private network inside AWS. Learn how to plan IP ranges, split public and private subnets across zones, route traffic to the internet safely, and use security groups and network ACLs as two layers of firewall.

The idea in one minute

A VPC, Virtual Private Cloud, is a private network you create inside a region. You choose its IP range, for example 10.0.0.0/16, which gives 65,536 addresses.

You split the VPC into subnets, and each subnet lives in one Availability Zone.

  • A public subnet has a route to an internet gateway. Load balancers and NAT gateways live here.
  • A private subnet has no direct route from the internet. App servers and databases live here.

Servers in private subnets often still need to reach the internet, for example to download updates. A NAT gateway in a public subnet lets them make outbound connections, while nothing on the internet can start a connection to them.

Two firewalls protect traffic.

  • Security groups attach to each resource, such as a server or database. They are stateful, so if you allow a request in, the reply goes out automatically. They only have allow rules.
  • Network ACLs attach to a subnet. They are stateless, so you must allow both directions, and they can have allow and deny rules, checked in number order.
Think of it like this

A VPC is a gated housing estate. Public subnets are the houses near the gate, where visitors are allowed. Private subnets are houses deep inside, where only residents go. The NAT gateway is a delivery hatch. Residents can send letters out and get replies, but strangers cannot walk in.

Words you need

VPC
A logically isolated private network in one AWS region.
CIDR block
A way to write an IP range, such as 10.0.0.0/16. Smaller number after the slash means more addresses.
Subnet
A range of IPs inside a VPC, in one Availability Zone.
Route table
Rules that say where traffic for each destination goes.
Internet gateway
Connects a VPC to the internet. A subnet whose route table points to it is public.
NAT gateway
Lets private resources start outbound connections to the internet, but blocks inbound ones.
Security group
A stateful firewall on a resource, with allow rules only.
Network ACL
A stateless firewall on a subnet, with numbered allow and deny rules.
VPC Flow Logs
Records of IP traffic going to and from network interfaces in a VPC.
Elastic IP
A static public IPv4 address you can attach to resources.

How it works

Plan the IP ranges

  • Pick a VPC range that does not overlap with your office networks or other VPCs you may connect later. Overlaps block peering and VPNs.
  • A VPC can be from /16, 65,536 addresses, to /28, 16 addresses.
  • AWS reserves 5 addresses in every subnet, the first four and the last one.
  • Leave room to grow. Changing ranges later is painful.

A standard layout

Subnet typeIn each AZRoute to internetHolds
PublicYesInternet gatewayLoad balancers, NAT gateways, bastion if any
PrivateYesNAT gateway in the same AZApp servers, containers, Lambda in VPC
Isolated, sometimes called dataYesNoneDatabases, caches

Put one NAT gateway in each AZ, with each private subnet routing to the NAT in its own AZ. One shared NAT gateway is a single point of failure and adds cross AZ cost.

Security groups versus network ACLs

Security groupNetwork ACL
Applies toA resource's network interfaceA whole subnet
StateStateful, replies allowed automaticallyStateless, both directions need rules
RulesAllow onlyAllow and deny, checked by number
Typical useMain firewall, reference other security groupsCoarse extra layer, block known bad ranges

Referencing another security group as the source, such as "allow 5432 from app-sg", is better than IP ranges, because it follows servers as they scale.

See the traffic

Turn on VPC Flow Logs to S3 or CloudWatch Logs. They help debug "why can't A reach B?" and they are evidence during incidents.

Key point

Public subnets only for things that must face the internet. Everything else private, with security groups that name each other.

Real life scenarios

The open database

Security researchers regularly find databases such as Elasticsearch and MongoDB on cloud servers with public IPs and open ports, holding millions of records. A private subnet and a tight security group would have prevented each one.

The overlapping ranges

Two companies merged and tried to connect their AWS networks. Both used 10.0.0.0/16, so routing between them was impossible without re-addressing. Planning ranges centrally avoids this.

The NAT gateway bill

A team ran one NAT gateway for three AZs and pulled large container images through it every deploy. Cross AZ and NAT data charges grew big. A NAT per AZ, VPC endpoints for S3 and ECR, and image caching cut the cost.

Trade-offs

ChoiceGood atCosts you
NAT gateway per AZNo single point of failure, no cross AZ charges.Hourly cost for each one.

Common mistakes

  • Putting databases or app servers in public subnets.
  • Security group rules like "0.0.0.0/0 on port 22".
  • VPC ranges that overlap with offices or other VPCs.
  • One NAT gateway for all AZs in production.
  • Forgetting return traffic rules in network ACLs.

Security lens

Network controls are a second line behind identity. Keep management ports closed to the internet and use Systems Manager Session Manager instead of SSH bastions, enable VPC Flow Logs, and use VPC endpoints so traffic to AWS services stays private, lesson 3.2. Review security groups regularly for 0.0.0.0/0 rules, which tools such as AWS Config and Security Hub can flag automatically.
