Backup, disaster recovery strategies and moving to the cloud

Every system will fail one day. The question is how much data you may lose and how long you may be down. Learn RPO and RTO, the four AWS disaster recovery strategies from cheap to instant, how AWS Backup protects data, and the seven ways to migrate apps to the cloud.

The idea in one minute

Two numbers drive every disaster recovery plan, as in Concepts lesson 5.1.

  • RPO, recovery point objective. How much data you can afford to lose, measured in time. RPO of 5 minutes means you may lose up to the last 5 minutes of writes.
  • RTO, recovery time objective. How long you can afford to be down.

AWS describes four disaster recovery strategies, from cheapest and slowest to most expensive and fastest.

  1. Backup and restore. Keep backups in another region. Rebuild everything when disaster strikes. Hours of RTO.
  2. Pilot light. Keep the core, usually the database replica, running in the second region. Start the rest when needed. Tens of minutes.
  3. Warm standby. A smaller but fully working copy runs all the time in the second region. Scale it up on failover. Minutes.
  4. Multi site active active. Full capacity in two or more regions serving traffic all the time. Near zero RTO.

Faster recovery costs more. Pick by business impact, not by fear.

Think of it like this

Backup and restore is keeping spare house keys at a friend's place across town. Pilot light is a small heater kept on in a second house. Warm standby is a second house with the lights on and some food in the fridge. Active active is living in two houses at once.

Words you need

RPO
Recovery point objective. Maximum acceptable data loss, measured in time.
RTO
Recovery time objective. Maximum acceptable downtime.
Backup and restore
Restore from backups in another region. Cheapest, slowest.
Pilot light
Core data kept live in the recovery region. The rest is started on failover.
Warm standby
A scaled down, fully working copy always running in the recovery region.
Multi site active active
Full capacity serving in several regions at once.
AWS Backup
Central, policy based backups across many AWS services and accounts.
Backup vault lock
Write once protection for backups so they cannot be deleted early.
AWS Elastic Disaster Recovery
Continuously replicates servers so they can be recovered in AWS.

How it works

The four strategies compared

StrategyTypical RTOTypical RPOCost
Backup and restoreHoursHours, depending on backup frequencyLowest
Pilot lightTens of minutesSeconds to minutesLow
Warm standbyMinutesSecondsMedium
Multi site active activeNear zeroNear zeroHighest

These are typical, not fixed. Measure yours in drills.

Building blocks for each

  • Backups. AWS Backup plans across EBS, RDS, DynamoDB, EFS, S3 and more, with copies to another region and another account.
  • Data replication. S3 Cross Region Replication, Aurora Global Database, DynamoDB global tables, RDS cross region read replicas.
  • Infrastructure as code so the recovery region can be built in minutes.
  • Traffic switching. Route 53 failover or latency records, Global Accelerator.

Protect backups from attackers

  • Copy backups to a separate account that the production account cannot change.
  • Use AWS Backup Vault Lock or S3 Object Lock in compliance mode.
  • Use different encryption keys and admins for backups.
  • Test restores regularly. An untested backup is a hope.

Moving to the cloud, the seven Rs

StrategyMeaning
RehostLift and shift servers as they are
ReplatformSmall changes, such as moving a database to RDS
RefactorRe-architect for cloud native services
RepurchaseMove to a SaaS product
RelocateMove a whole platform, such as VMware, as is
RetainKeep it where it is for now
RetireSwitch it off

AWS Application Migration Service helps rehost servers, and Database Migration Service moves databases with little downtime.

Key point

Agree RPO and RTO with the business first. Then pick the cheapest strategy that meets them, and prove it with drills.

Real life scenarios

OVHcloud fire, 2021

A fire destroyed a data center building in Strasbourg in March 2021. Customers with backups only in the same site lost data. Customers with copies elsewhere recovered. Distance between copies matters.

The untested backup

A company's nightly database backup had silently failed for months because a password changed. They found out during a real restore. Monthly automated restore tests now check every backup.

Game days

Many teams run planned game days, deliberately failing over to the recovery region during business hours. Each drill finds a missing permission, a hard coded endpoint or an expired certificate before a real disaster does.

Trade-offs

ChoiceGood atCosts you
Backup and restoreCheap and simple.Long downtime and more data loss.
Pilot lightLow cost, data already copied.Must start and scale the app tier on failover.
Warm standbyFast recovery, tested daily by real traffic if you send some.Pays for a second smaller environment.
Active activeNear zero downtime.Hardest data consistency and highest cost.

Common mistakes

  • No agreed RPO and RTO.
  • Backups in the same account and region as production.
  • Never testing restores or failover.
  • Recovery regions with outdated templates or missing quotas.
  • Treating replication as backup, so deletes replicate too.

Security lens

Backups are a ransomware target. Keep them in a separate account with vault lock or Object Lock, separate keys and separate admins, monitor for deletion attempts, and include "restore from clean backups" in your incident response plan, lesson 6.2. Also check the recovery region has the same security controls, logging and guardrails as the primary.
