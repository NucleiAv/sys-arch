Git basics, save every version of your work

Git keeps a history of every change to your project. You can see who changed what, go back to any old version, and work with others without losing work.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Git is a version control system. Linus Torvalds wrote it in 2005 to manage the Linux kernel. Today almost every software team uses it.

Git saves your project as a series of commits. A commit is a snapshot of all your files at one moment, with a message that says what changed and why. Each commit has a unique id, a long hash such as 3f9a2c1.

Before you commit, you choose which changes go into the snapshot. You put them in the staging area. This lets you make one clean commit per idea.

Think of it like this

Git is like a photo album of your project. Each commit is a photo. The staging area is the table where you arrange things before you take the photo. You can always look at an old photo and put things back the way they were.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Repository
A project folder that Git tracks, with all its history. Also called a repo.
Commit
A saved snapshot of the project with a message, an author and a unique hash.
Working folder
The files you see and edit. Also called the working tree.
Staging area
The list of changes that will go into the next commit. Also called the index.
HEAD
A pointer to the commit you are on now.
Hash
The unique id of a commit, made from its content.
.gitignore
A file that lists files Git must not track, such as node_modules/ or .env.

How it works

Your first repository

git init                      # start tracking this folder
git status                    # what changed?
git add app.py                # stage one file
git add .                     # stage all changes in this folder
git commit -m "First version" # save a snapshot
git log --oneline             # list commits

See what changed

git diff            # changes not staged yet
git diff --staged   # changes staged for the next commit
git show HEAD       # the last commit

Undo things safely

You want toCommand
Throw away changes to a file you have not stagedgit restore app.py
Unstage a file but keep your changesgit restore --staged app.py
Undo a commit that others already havegit revert 3f9a2c1, which makes a new commit that does the opposite
Fix the message of your last commit, before you share itgit commit --amend

Good commits

  1. One commit for one idea.
  2. Write the message as a command, such as "Add login check".
  3. Never commit secrets, such as passwords or keys. List files like .env in .gitignore.
Careful

If a secret goes into a commit, it stays in the history even after you delete the file. Change the secret at once. Then clean the history if needed.

Real life scenarios

A bug that came from last week

A page broke and nobody knew why. git log and git diff showed one changed line from last Tuesday. git revert undid it in one minute.

An API key on a public repository

A student pushed a file with a cloud key. Bots found it within minutes and started paid servers. Deleting the file was not enough because it stayed in the history. The fix was to cancel the key and add .env to .gitignore.

Trade-offs

ChoiceGood atCosts you
Many small commitsEasy to read, easy to undo one change.More messages to write.
One big commitFast to make.Hard to review and hard to undo only one part.
git revertSafe on shared history, keeps a record.Adds a new commit.
git resetMoves your branch back.Rewrites history. Do not use it on commits others already have.

Common mistakes

  • Committing secrets or large generated files.
  • Messages like "fix" or "stuff".
  • Using git add . without checking git status first.
  • Using git reset --hard without knowing it deletes uncommitted work.
