Kubernetes basics, pods, deployments and services

Kubernetes runs containers across many machines and keeps them in the state you asked for. Learn the cluster parts, pods, deployments, services and kubectl.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Kubernetes, often written K8s, is a system that runs containers on a group of machines called a cluster. Google released it as open source in 2014. The Cloud Native Computing Foundation looks after it now.

You do not tell Kubernetes "start this container on machine 3". You tell it the desired state. For example, "always run 3 copies of shop version 1.4". Kubernetes compares the real state with the desired state all the time, and fixes any difference. If a machine dies, it starts the lost copies elsewhere. This loop is called reconciliation.

Think of it like this

You tell a robot gardener "I want 3 tomato plants in this bed, always". You do not say how. If a plant dies, the robot plants a new one. If you change the number to 5, it plants 2 more.

Words you need

Cluster
A set of machines that Kubernetes manages as one.
Node
One machine in the cluster that runs pods.
Control plane
The brain. API server, scheduler, controllers and etcd, the database of desired state.
kubelet
The agent on each node that starts and watches containers.
Pod
The smallest unit. One or more containers that share a network address and storage.
Deployment
Describes how many replicas of a pod to run and how to update them.
ReplicaSet
Keeps the right number of pod copies running. Deployments manage it for you.
Service
A stable address and DNS name in front of a changing set of pods.
Label
A key and value on an object, such as app: shop, used by selectors to find objects.
Namespace
A folder like group of objects inside a cluster, such as dev and prod.
kubectl
The command line tool to talk to the Kubernetes API.

How it works

A Deployment and a Service

apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop
spec:
  replicas: 3
  selector:
    matchLabels:
      app: shop
  template:
    metadata:
      labels:
        app: shop
    spec:
      containers:
        - name: shop
          image: registry.example.com/shop:1.4
          ports:
            - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  selector:
    app: shop
  ports:
    - port: 80
      targetPort: 3000

The Service finds pods by the label app: shop. Other pods in the namespace can now call http://shop.

Service types

TypeWho can reach it
ClusterIPOnly inside the cluster. The default.
NodePortA port on every node
LoadBalancerA cloud load balancer with a public or private address

kubectl commands

kubectl apply -f shop.yaml          # create or update from a file
kubectl get pods                    # list pods
kubectl describe pod shop-7d9f-x2   # details and events
kubectl logs shop-7d9f-x2           # container output
kubectl scale deployment shop --replicas=5
kubectl rollout status deployment shop
Key point

Pods are temporary. Never rely on a pod's IP address. Always reach pods through a Service.

Real life scenarios

A node lost at night

A cloud machine failed at 3 AM. Kubernetes moved its pods to other nodes in about a minute. The team read about it in the morning.

Calling a pod by IP

A service saved another pod's IP address in its config. After a restart, the pod got a new IP and calls failed. Using the Service name fixed it.

Trade-offs

ChoiceGood atCosts you
KubernetesSelf healing, scaling, rolling updates, huge ecosystem.Complex to learn and to run.
Managed Kubernetes, such as EKS, GKE or AKSThe cloud runs the control plane.Costs money, still a lot to learn.
Simpler container services, such as ECS or Cloud RunMuch less to manage.Less flexible, tied to one cloud.

Common mistakes

  • Running pods directly instead of through a Deployment, so nothing replaces them.
  • Labels in the Service selector that do not match the pod labels.
  • Using latest image tags, so Kubernetes cannot tell versions apart.
  • Using Kubernetes for one small app that one server could run.
