AWS networks and storage, VPC, S3, RDS and DynamoDB

Build a private network in the cloud, decide what is public and what is not, and pick the right place for files, relational data and key value data.

The idea in one minute

A VPC, virtual private cloud, is your own private network inside AWS. You split it into subnets. A public subnet can reach the internet directly. A private subnet cannot be reached from the internet. Your database belongs in a private subnet.

Then you choose where data lives.

  • S3 for files of any size.
  • RDS for managed relational databases, such as PostgreSQL and MySQL.
  • DynamoDB for a managed key value and document database that scales very far.
Think of it like this

A VPC is a fenced campus. The public subnet is the reception area by the gate. The private subnet is the back office with no door to the street. Visitors talk to reception, and reception walks to the back office for them.

Words you need

VPC
Your private network in AWS, with an address range such as 10.0.0.0/16.
CIDR
A way to write an address range. /16 has 65,536 addresses, /24 has 256.
Subnet
A smaller range inside a VPC, in one availability zone.
Internet gateway
Connects a VPC to the internet. Public subnets route to it.
NAT gateway
Lets private servers start connections to the internet, but blocks connections from it.
Security group
A stateful firewall on a resource. Only allow rules. Return traffic is allowed automatically.
Network ACL
A stateless firewall on a subnet, with allow and deny rules.
ALB and NLB
Application Load Balancer works at layer 7, Network Load Balancer at layer 4.
S3
Object storage. Buckets hold objects of any size. Designed for 11 nines of durability.
RDS
Managed relational databases. AWS handles backups, patches and failover.
Multi-AZ
RDS keeps a standby copy in another zone and fails over to it automatically.
DynamoDB
Managed key value and document database. You choose a partition key, and it scales very far.

How it works

A typical VPC layout

SubnetZone aZone bHolds
Public10.0.0.0/2410.0.1.0/24Load balancer, NAT gateway
Private app10.0.10.0/2410.0.11.0/24App servers or containers
Private data10.0.20.0/2410.0.21.0/24RDS, caches

Security groups chain together

  • Load balancer group. Allow 443 from 0.0.0.0/0.
  • App group. Allow 8080 only from the load balancer group.
  • Database group. Allow 5432 only from the app group.

Refer to other security groups, not to IP addresses. Then new servers fit in automatically.

S3 basics

  • Keep Block Public Access on, at the account level.
  • Turn on versioning for important buckets, so you can recover deleted or overwritten objects.
  • Use lifecycle rules to move old objects to cheaper storage classes, such as Glacier.
  • Serve public files through CloudFront, the AWS CDN.

Choosing a database service

NeedService
Relational data with joins and transactionsRDS or Aurora
Huge scale lookups by key, steady low latencyDynamoDB
A cache in front of a databaseElastiCache for Redis or Valkey
SearchOpenSearch Service

RDS high availability

Multi-AZ keeps a synchronous standby in a second zone. If the main one fails, RDS moves the database name to the standby, usually within a minute or two. Read replicas are separate copies for read traffic. They use asynchronous replication.

Key point

With DynamoDB, design the keys from your queries first. A good partition key, such as user_id, spreads traffic. A bad one, such as date, creates hot partitions.

Real life scenarios

Public buckets in the news

Many data leaks came from S3 buckets that someone made public by mistake. AWS now turns on Block Public Access for new buckets by default.

The expensive NAT gateway

A team's servers downloaded large files from S3 through a NAT gateway and paid processing fees on every gigabyte. A free S3 gateway endpoint removed most of that cost.

Trade-offs

ChoiceGood atCosts you
Public subnet for app serversSimple.Servers are reachable from the internet, a bigger attack surface.
Private subnets with NATSafer.NAT gateways cost money by the hour and by the gigabyte.

DynamoDBScales very far, no servers.Queries must follow the key design, joins are not possible.

Common mistakes

  • Putting databases in public subnets.
  • Security groups that allow 0.0.0.0/0 on database or SSH ports.
  • Turning off Block Public Access to share one file.
  • Running production RDS without Multi-AZ or tested backups.
  • Choosing DynamoDB keys before knowing the queries.

Security lens

Network and storage settings cause many cloud breaches.

  • Keep databases in private subnets. Use security groups that allow only the app tier.
  • Turn on S3 Block Public Access for the account.
  • Encrypt S3, RDS and DynamoDB with KMS keys, and control who can use the keys.
  • Use VPC endpoints so traffic to S3 does not cross the internet.
