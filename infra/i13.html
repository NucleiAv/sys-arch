Infrastructure as code with Terraform

Clicking in a cloud console is slow, hard to repeat and easy to get wrong. Infrastructure as code describes your servers, networks and databases in files that you review, version and apply. Learn it with Terraform.

The idea in one minute

Infrastructure as code, IaC, means you describe your infrastructure in text files and let a tool create it. The files live in Git. You review changes in pull requests like normal code. You can build the same setup again for a test environment or a new region in minutes.

Terraform is a popular IaC tool from HashiCorp. You write files in HCL, a simple config language. You say what you want, not the steps to get there. This is called declarative. Terraform compares your files with what exists and makes a plan of the changes. Then it applies the plan.

In 2023 HashiCorp changed Terraform's license to the Business Source License. A community fork called OpenTofu, under the Linux Foundation, keeps an open source version that works almost the same way.

Think of it like this

Instead of telling a builder "put a brick here, then here", you give them a drawing of the finished wall. The builder looks at what is already built and adds only what is missing.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Infrastructure as code
Describing infrastructure in versioned files that a tool turns into real resources.
Declarative
You describe the end state. The tool works out the steps.
Provider
A Terraform plugin that talks to one API, such as AWS, Google Cloud or GitHub.
Resource
One thing Terraform manages, such as an S3 bucket or a VPC.
Variable and output
Inputs to your config, and values it prints or passes on.
State
Terraform's record of what it created and its real IDs. It maps your files to real resources.
Remote backend
Storing state in a shared place, such as S3, with locking.
Module
A reusable folder of Terraform code, such as a standard VPC.
Drift
When the real infrastructure no longer matches the code, often because someone clicked in the console.

How it works

A small example

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
  backend "s3" {
    bucket       = "acme-tf-state"
    key          = "shop/prod.tfstate"
    region       = "ap-south-1"
    use_lockfile = true
  }
}

provider "aws" { region = var.region }

variable "region" { default = "ap-south-1" }

resource "aws_s3_bucket" "images" { bucket = "acme-shop-images-prod" }

resource "aws_s3_bucket_versioning" "images" { bucket = aws_s3_bucket.images.id versioning_configuration { status = "Enabled" } }

output "bucket_name" { value = aws_s3_bucket.images.bucket } ```

aws_s3_bucket.images.id refers to another resource. Terraform sees this link and creates the bucket before the versioning setting.

The commands

CommandWhat it does
terraform initDownload providers, set up the backend
terraform fmtFormat the files
terraform validateCheck the syntax
terraform planShow what would change
terraform applyMake the changes
terraform destroyDelete everything this config manages

Look after the state

The state file is important and can hold secrets. Store it in a remote backend with encryption and locking, never in Git. Older setups lock with a DynamoDB table. Newer Terraform versions can lock with a lock file in S3 itself.

Good habits

  1. Run plan in CI on every pull request and apply only after review.
  2. Split state by environment and area, such as network, data and app, so one mistake cannot touch everything.
  3. Use modules for repeated patterns.
  4. Do not change managed resources by hand in the console.

Careful

Read every plan before you apply. A changed resource name can mean "destroy and create again", which deletes data in a database or bucket.

Real life scenarios

A test environment in 20 minutes

A team needed a copy of production for load tests. With Terraform modules and a new variables file, they built it in 20 minutes and destroyed it the same evening.

The rename that deleted a database

An engineer renamed a resource block in Terraform. The plan said destroy and create. Nobody read it, and the database was deleted. They restored from backup, then added prevent_destroy to critical resources and required plan review.

Trade-offs

ChoiceGood atCosts you
IaCRepeatable, reviewable, versioned.Learning curve, state to manage.
Clicking in the consoleFast for one experiment.Not repeatable, no review, drift.
One big stateSimple to start.Slow plans, one mistake can touch everything.
Many small statesSafer, faster.You must pass values between them.

Common mistakes

  • Storing state in Git or on one laptop.
  • Applying without reading the plan.
  • Changing resources by hand, which causes drift.
  • Putting secrets as plain values in .tf files.
  • No locking, so two applies run at once.

Security lens

Infrastructure as code lets you review and test security before anything exists.

  • Scan Terraform with tools like Checkov, tfsec or Trivy in CI.
  • The state file can hold secrets. Store it in an encrypted, access controlled backend with locking.
  • Use policy as code, like OPA or Sentinel, to block public buckets and open security groups.
  • Review terraform plan output in pull requests. It shows exactly what will change.
