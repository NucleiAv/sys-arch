Docker Compose, many containers on one machine

A real app needs a web server, a database and a cache. Compose starts them all with one command from one file, and lets them find each other by name.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Running one container with docker run is easy. A real app has several. Typing long docker run commands for each one in the right order is slow and easy to get wrong.

Docker Compose reads one YAML file, usually compose.yaml, that lists every service, its image, ports, settings and storage. docker compose up starts them all. Compose also makes a private network, so services reach each other by their service name, such as db.

Think of it like this

Compose is the conductor of a small band. The sheet music, the YAML file, says who plays which part. The conductor starts everyone together, and the players can hear each other.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Compose file
A YAML file, usually compose.yaml, that describes all services of an app.
Service
One container definition in a Compose file, which can run as one or more containers.
Named volume
Docker managed storage with a name, kept when containers are removed.
Bind mount
A folder from your computer mounted into a container. Useful for live code changes in development.
depends_on
Starts services in order. With a health check condition it can wait until a service is healthy.
Health check
A command that tells Docker if a container is really ready.

How it works

A compose.yaml for a web app, a database and a cache

services:
  web:
    build: .
    ports:
      - "8080:3000"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/shop
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started

db: image: postgres:16 environment: POSTGRES_USER: app POSTGRES_PASSWORD: secret POSTGRES_DB: shop volumes: - db-data:/var/lib/postgresql/data healthcheck: test: ["CMD-SHELL", "pg_isready -U app"] interval: 5s retries: 5

cache: image: redis:7

volumes: db-data: ```

The commands

CommandWhat it does
docker compose up -dBuild if needed and start everything in the background
docker compose psList the services and their state
docker compose logs -f webFollow the logs of one service
docker compose downStop and remove containers and the network, keep volumes
docker compose down -vAlso delete the volumes, which deletes the data

Where Compose fits

Compose is great for local development, tests in CI and small single server deployments. It runs on one machine. When you need many machines, self healing and rolling updates, you move to Kubernetes or a managed container service.

Careful

The passwords in the example are for local development only. In real deployments, read secrets from a secrets manager or Compose secrets, not from the file in Git.

Real life scenarios

New developer, ready in ten minutes

A team used to need a full day to set up a laptop. With one compose.yaml, a new developer runs docker compose up and has the app, database and cache running in ten minutes.

Data gone after cleanup

A developer ran docker compose down -v to free space and lost the local test data. Named volumes survive down, but -v deletes them.

Trade-offs

ChoiceGood atCosts you
ComposeSimple, one file, perfect for development.One machine only, no self healing across machines.
KubernetesMany machines, self healing, rolling updates.Much more to learn and run.
Database in a containerEasy local setup.In production, a managed database is usually safer for backups and failover.

Common mistakes

  • Using localhost inside a container to reach another container. Use the service name.
  • Assuming depends_on waits until the database is ready, without a health check.
  • Committing real passwords in compose.yaml.
  • Publishing database ports to the internet.

Security lens

Compose files often end up with weak defaults.

  • Do not publish database ports to the host unless you need to.
  • Keep secrets in a .env file that git ignores, or use Docker secrets.
  • Do not mount the Docker socket into containers. It gives root on the host.
