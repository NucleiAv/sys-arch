Git branches, merging and rebasing

Branches let you work on a new idea without breaking the main code. Learn to create branches, join them with merge or rebase, and fix conflicts calmly.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

A branch is a movable label that points to a commit. When you make a new commit on a branch, the label moves forward. The main branch is usually called main.

You make a branch for each new feature or fix. You work there safely. When it is ready, you merge it back into main.

Sometimes two branches change the same lines. Git cannot guess which one is right. That is a merge conflict. You choose the correct lines by hand.

Think of it like this

A branch is like a copy of a story where you try a new ending. The original story stays safe. If you like the new ending, you add it to the original. If two people rewrote the same sentence, you must decide which sentence to keep.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Branch
A movable label that points to a commit.
main
The usual name of the main branch. Older projects use master.
Merge
Joining the work of one branch into another.
Fast forward
A merge where the target branch has no new commits, so Git only moves the label forward.
Merge commit
A commit with two parents that joins two branches.
Rebase
Replaying your commits on top of another branch, which makes a straight history and new commit ids.
Merge conflict
Both branches changed the same lines. You must choose by hand.
git stash
Puts your unfinished changes aside so you can switch branches, and gives them back later.

How it works

Everyday branch commands

git branch                 # list branches
git switch -c fix-login    # create a branch and move to it
git switch main            # move back to main
git merge fix-login        # bring fix-login into the branch you are on
git branch -d fix-login    # delete the label after the merge

Older guides use git checkout -b fix-login. It does the same as git switch -c fix-login.

Merge or rebase

MergeRebase
HistoryKeeps the real shape, with merge commitsOne straight line
Commit idsUnchangedNew ids for your rebased commits
Safe on shared branchesYesNo. Rebase only your own unpushed or private work
Careful

The golden rule. Do not rebase commits that other people already pulled. Rebase rewrites them, and their copies no longer match.

Fixing a conflict

Git marks the clash in the file.

<<<<<<< HEAD
price = 100
=======
price = 120
>>>>>>> feature
  1. Choose the correct text. Delete the markers.
  2. Run git add on the file.
  3. Run git commit to finish the merge, or git rebase --continue during a rebase.

A simple team flow

Keep main always working. Make short branches for each change. Merge them through pull requests, which you learn in the next lesson.

Real life scenarios

Two developers, one price

Two people changed the same price line on different branches. The second merge stopped with a conflict. They talked for one minute, kept the new price and merged.

A rebase that confused a team

A developer rebased a shared branch and force pushed it. Teammates then had commits that no longer matched. The team agreed to rebase only private branches.

Trade-offs

ChoiceGood atCosts you
Merge commitsTrue history, safe.History looks busy.
Rebase before mergingClean straight history.Rewrites commits, risky on shared branches.
Long lived branchesBig features stay isolated.Many conflicts when you finally merge.
Short branchesSmall, easy merges.Big features need feature flags to hide unfinished work.

Common mistakes

  • Working directly on main.
  • Branches that live for weeks and drift far from main.
  • Rebasing a branch that others use.
  • Leaving conflict markers in the file and committing them.
