Linux and servers for beginners

Almost every server and container runs Linux. Learn the few commands and ideas you need to log in, find what is running, read logs and fix the most common problems.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

A server is a computer that runs programs for other computers. Most servers run Linux, a free operating system. You usually have no screen. You control it with text commands in a shell, over a secure connection called SSH.

On a server, your app is a process, a running program. It listens on a port, a numbered door, such as port 443. A service manager, usually systemd, starts the process at boot and restarts it if it crashes.

Think of it like this

A server is a kitchen with no lights you can see. You talk to the chef through a speaking tube, that is SSH. Each cook is a process. Each serving window has a number, that is the port. The head chef, systemd, wakes the cooks in the morning and replaces any cook who faints.

Words you need

Shell
A program that reads your typed commands and runs them, such as bash.
SSH
Secure Shell. An encrypted way to log in to another computer, usually on port 22.
Process
A running program with an id, called a PID.
Port
A number from 0 to 65535 that names one door for network traffic on a machine.
systemd
The service manager on most Linux systems. It starts, stops and restarts services.
root
The all powerful user. Use sudo to run one command as root.
Permissions
Rules about who may read, write or run each file.
Environment variable
A named value that a process can read, such as DATABASE_URL.

How it works

Ten commands to start with

CommandWhat it does
ssh user@hostLog in to a server
ls -laList files with details
cd /var/logChange folder
cat file, less file, tail -f fileRead a file, page through it, follow new lines
ps aux, topList processes, see CPU and memory live
systemctl status nameCheck a service
journalctl -u nameRead a service's logs
ss -tlnpShow which processes listen on which ports
curl -I http://localhost:8080Send a test HTTP request
df -h, free -hDisk space and memory

File permissions

ls -l shows something like -rwxr-x---. The three groups are owner, group and others. r is read, w is write, x is run. chmod 600 key.pem lets only the owner read and write the file. SSH refuses private keys that others can read.

SSH keys, not passwords

  1. Make a key pair on your laptop with ssh-keygen -t ed25519.
  2. Put the public key in ~/.ssh/authorized_keys on the server.
  3. Keep the private key only on your laptop.
  4. Turn off password login on the server.

A service file

# /etc/systemd/system/shop.service
[Unit]
Description=Shop app
After=network.target

[Service] User=shop Environment=PORT=8080 ExecStart=/usr/bin/node /opt/shop/server.js Restart=always

[Install] WantedBy=multi-user.target ```

Restart=always makes systemd start the app again if it crashes. User=shop runs it as a normal user, not root.

Key point

Ports below 1024 need extra rights. So apps often listen on a high port, such as 8080, and a reverse proxy like Nginx listens on 80 and 443.

Real life scenarios

The disk that filled up

A server stopped writing orders. df -h showed the disk 100 percent full of old logs. Log rotation, which deletes old logs on a schedule, fixed it for good.

Running as root

An app ran as root. A bug let an attacker run commands, and they owned the whole machine. Running the app as a normal user would have limited the damage.

Trade-offs

ChoiceGood atCosts you
SSH keysStrong, no passwords to guess.You must protect and rotate keys.
Password loginEasy.Bots try to guess passwords all day.
Logging in to fix servers by handQuick for one problem.Changes are not recorded, servers drift apart. Prefer automation.

Common mistakes

  • Running apps as root.
  • Leaving password SSH login on.
  • Private keys that other users can read.
  • No log rotation, so disks fill up.
  • Fixing production by hand and never writing it down.

Security lens

Basic Linux hygiene stops many attacks.

  • Log in with SSH keys, turn off password and root login.
  • Keep packages updated, with automatic security updates where safe.
  • Run services as non root users with only the files they need.
  • Close unused ports with a firewall like ufw or nftables.
  • Check file permissions. A world writable script run by root is a path to full control.
