GitHub Actions, continuous integration and delivery

Let a robot test every change and ship it when it is good. Learn CI and CD, and write GitHub Actions workflows step by step.

The idea in one minute

Continuous integration, or CI, means every change is built and tested automatically, many times a day, as soon as it is pushed. Problems show up in minutes, not weeks.

Continuous delivery, or CD, means every change that passes CI is ready to release with one click. Continuous deployment goes one step further. It releases every passing change automatically.

GitHub Actions is the CI/CD service built into GitHub. You describe the work in a workflow file written in YAML. GitHub runs it on a fresh machine, called a runner, when an event happens, such as a push or a pull request.

Think of it like this

A bakery has a taster at the door. Every new cake goes to the taster first. If it tastes good, it goes on the shelf. If not, it goes back to the baker with a note. CI is the taster. CD is the delivery van that takes good cakes to the shops.

Watch it, step by step

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Workflow
A YAML file in .github/workflows/ that describes automated work.
Event
What starts a workflow, such as push, pull_request, schedule or workflow_dispatch.
Job
A group of steps that run on one runner. Jobs run in parallel unless one needs another.
Step
One command or one action inside a job.
Action
A reusable step, such as actions/checkout.
Runner
The machine that runs a job. GitHub hosts Linux, Windows and macOS runners, or you can host your own.
Secret
An encrypted value, such as an API key, used in a workflow as ${{ secrets.NAME }}.
Matrix
Runs the same job for several versions or systems.
Artifact
A file that a job saves, such as a test report or a build.

How it works

A CI workflow for a Node.js app

# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs: test: runs-on: ubuntu-latest strategy: matrix: node: [20, 22] steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: node-version: ${{ matrix.node }} cache: npm - run: npm ci - run: npm run lint - run: npm test ```

Read it top down. The name. The events that start it. One job called test that runs on Ubuntu, twice, once for Node 20 and once for Node 22. Then the steps. Check out the code, install Node, install packages, lint, test.

A deploy job that waits for tests

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh

needs: test means deploy starts only after test passes. environment: production can require a person to approve. id-token: write lets the job get a short lived cloud login with OIDC, so you do not store long lived cloud keys as secrets.

Good CI habits

  1. Keep CI fast, under about 10 minutes. Use caches.
  2. Run the same checks on every pull request.
  3. Pin actions to a version or a commit hash.
  4. Give the workflow the smallest permissions it needs.
  5. Never print secrets in logs.
Careful

Workflows that run on pull requests from forks can be abused to steal secrets. GitHub does not pass secrets to fork pull requests by default. Be careful with the pull_request_target event.

Real life scenarios

Tests that run on every change

A team that ran tests once a week found 30 bugs at a time and spent days on them. With CI on every pull request, each bug showed up minutes after it was written.

A leaked cloud key

A workflow printed environment values in a debug step. The cloud key appeared in public logs. The team switched to OIDC with short lived credentials, so there was no long lived key to leak.

Trade-offs

ChoiceGood atCosts you
Continuous deploymentFastest feedback, small releases.Needs strong tests, monitoring and quick rollback.
Continuous delivery with approvalA person chooses the moment.Slower, people become a bottleneck.
GitHub hosted runnersNo servers to run.Limited power, cost for heavy use.
Self hosted runnersFast machines, access to private networks.You must secure and update them.

Common mistakes

  • Slow CI that people skip.
  • Long lived cloud keys stored as secrets when OIDC is possible.
  • Workflows with write permission to everything.
  • Using actions from unknown authors without pinning a version.
  • Tests that fail randomly, so people ignore red builds.

Security lens

CI pipelines hold powerful secrets, so attackers target them.

  • Set permissions in workflows to the least needed, for example contents: read.
  • Pin actions to a full commit SHA, not a moving tag, so a hacked action cannot change under you.
  • Do not run untrusted pull request code with secrets. Be careful with pull_request_target.
  • Use OIDC to get short lived cloud credentials instead of storing long lived keys.
  • Never echo secrets in logs.
