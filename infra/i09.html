Kubernetes in practice, config, health, scaling and updates

A real app on Kubernetes needs a way in from the internet, settings and secrets, health checks, resource limits, autoscaling and safe updates. Learn each one with a small YAML example.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Infra lesson 2.4 showed the basic objects. Real apps need more.

  • Ingress sends outside HTTP traffic to the right Service, by host name and path.
  • ConfigMaps and Secrets hold settings outside the image.
  • Probes tell Kubernetes if a container is alive and ready for traffic.
  • Requests and limits say how much CPU and memory a container needs and may use.
  • The Horizontal Pod Autoscaler adds and removes pods with the load.
  • Rolling updates replace pods a few at a time, so there is no downtime.
Think of it like this

You hired a robot gardener in the last lesson. Now you give it a gate for visitors, a notebook of instructions, a way to check each plant is healthy, a water budget per plant, permission to plant more in summer, and a rule to replace plants one row at a time.

Words you need

Ingress
Rules that send outside HTTP and HTTPS traffic to Services by host and path. An ingress controller, such as NGINX, does the work.
ConfigMap
Non secret settings, such as a log level, given to pods as environment variables or files.
Secret
Sensitive values, such as passwords. Stored base64 encoded, which is not encryption.
Liveness probe
If it fails, Kubernetes restarts the container.
Readiness probe
If it fails, the pod gets no traffic, but it is not restarted.
Requests
The CPU and memory a container needs. The scheduler uses them to place pods.
Limits
The most CPU and memory a container may use. Over the memory limit, the container is killed.
HPA
Horizontal Pod Autoscaler. Changes the replica count based on metrics such as CPU.
Helm
A package manager for Kubernetes that installs apps from templated charts.
StatefulSet
Like a Deployment, but each pod keeps a stable name and its own storage. Used for databases.

How it works

Config and secrets

apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-config
data:
  LOG_LEVEL: info
---
# in the container spec
envFrom:
  - configMapRef:
      name: shop-config
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: shop-db
        key: password
Careful

Secrets are only base64 encoded by default. Turn on encryption at rest for etcd, limit who can read Secrets, or use an external secrets manager.

Probes and resources

readinessProbe:
  httpGet: { path: /ready, port: 3000 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /healthz, port: 3000 }
  initialDelaySeconds: 10
resources:
  requests: { cpu: 250m, memory: 256Mi }
  limits:   { memory: 512Mi }

250m means a quarter of one CPU core. A liveness probe should only check the process itself. If it checks the database, a database blip restarts every pod.

Autoscaling

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: shop
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: shop }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }

The HPA keeps average CPU near 70 percent of the requested CPU. It needs requests to be set.

Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: shop, port: { number: 80 } }

Packaging with Helm

Helm charts bundle many YAML files with variables. helm install shop ./chart -f prod-values.yaml installs the app with production values. helm rollback shop 3 goes back to release 3.

Real life scenarios

The liveness probe that caused an outage

A liveness probe checked the database. The database was slow for 20 seconds, every pod failed its probe, and Kubernetes restarted all of them at once. The probe was changed to check only the process.

Out of memory kills

Pods kept restarting with reason OOMKilled. The memory limit was lower than the app needed at peak. Measuring real use and raising the limit fixed it.

Trade-offs

ChoiceGood atCosts you
Tight limitsProtect other pods on the node.Containers get killed or slowed when they spike.
No limitsApps can burst freely.One app can starve its neighbours.
Rolling updateNo downtime, simple.Two versions run at the same time for a while.
Kubernetes SecretsBuilt in and simple.Only base64 by default, needs extra protection.

Common mistakes

  • Liveness probes that check shared dependencies.
  • No readiness probe, so traffic reaches pods that are still starting.
  • No resource requests, so the scheduler and the HPA cannot work well.
  • Thinking base64 Secrets are encrypted.
  • Running a database in a Deployment instead of a StatefulSet or a managed service.

Security lens

Config and secrets need special care in Kubernetes.

  • Kubernetes Secrets are only base64 encoded. Turn on encryption at rest for etcd, or use an external secrets manager.
  • Set resource limits so one pod cannot starve the node.
  • Set readOnlyRootFilesystem, drop Linux capabilities and disallow privilege escalation in the pod security context.
  • Use admission policies, like OPA Gatekeeper or Kyverno, to block risky manifests.
