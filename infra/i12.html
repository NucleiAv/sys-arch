Serverless, Lambda, API Gateway, SQS and events

With serverless, you upload small functions and AWS runs them only when something happens. You never manage a server. Learn Lambda, the services around it and when serverless is a bad fit.

The idea in one minute

"Serverless" does not mean there are no servers. It means you do not manage them. You give AWS a function. AWS runs it when an event happens, such as an HTTP request, a new file in S3 or a message in a queue. It runs as many copies as needed, and stops them when there is no work. You pay only for the time your code runs.

AWS Lambda runs the functions. API Gateway turns HTTP requests into Lambda events. SQS is a queue. SNS sends one message to many subscribers. EventBridge routes events between services by rules.

Think of it like this

A normal server is a shop that stays open all day, even with no customers. Serverless is a food truck that appears only when someone is hungry, and you pay the cook only for the minutes they cook.

Words you need

Serverless
You run code or use services without managing servers. You pay per use.
Lambda function
Code that AWS runs on an event. It can run up to 15 minutes per call.
Trigger
The event source that starts a function, such as API Gateway, S3, SQS or a schedule.
Cold start
The extra time when AWS must start a new copy of your function before it runs.
Concurrency
How many copies of a function run at the same moment.
SQS
Simple Queue Service. Standard queues deliver at least once. FIFO queues keep order and remove duplicates.
Visibility timeout
While one consumer works on a message, SQS hides it from others for this time.
SNS
Simple Notification Service. Publish once, deliver to many subscribers.
EventBridge
An event bus that routes events to targets by matching rules.
Step Functions
A service that runs a workflow of steps, with retries and branches.

How it works

A Lambda function in Python

import json

def handler(event, context): name = event.get("queryStringParameters", {}).get("name", "world") return { "statusCode": 200, "headers": {"Content-Type": "application/json"}, "body": json.dumps({"hello": name}), } ```

AWS calls handler with the event. With API Gateway, the return value becomes the HTTP response.

When serverless fits and when it does not

Good fit. Spiky or unpredictable traffic, event processing, scheduled jobs, glue between services, small APIs.

Poor fit. Long running jobs over 15 minutes, steady very high traffic where servers are cheaper, very low latency needs where cold starts hurt, and apps that need long open connections.

Key point

Lambda functions must be stateless. Keep state in DynamoDB, S3 or a cache. Make functions idempotent, because SQS and many triggers can deliver the same event twice.

Real life scenarios

A spike with no servers to scale

A ticket site's confirmation emails ran on Lambda behind SQS. On a sale day, messages grew to 200 thousand. Lambda scaled out, worked through the queue and scaled back to zero by evening.

A Lambda that cost more than a server

A service handled thousands of requests every second, all day. The Lambda bill was higher than a few containers would cost. They moved the steady part to containers and kept Lambda for spikes and events.

Common mistakes

  • Storing state in the function's memory between calls.
  • Non idempotent functions behind SQS.
  • A visibility timeout shorter than the function's run time, so messages are processed twice.
  • No dead letter queue for failed messages.
  • Calling Lambda functions from Lambda functions in long chains instead of using queues or Step Functions.

Security lens

Serverless removes servers, not security work.

  • Give each function its own role with the least permissions.
  • Validate every event. An S3 file name or a queue message is untrusted input.
  • Store secrets in Secrets Manager or Parameter Store, not in plain environment variables visible to many people.
  • Set concurrency limits so an attack cannot run up a huge bill.
