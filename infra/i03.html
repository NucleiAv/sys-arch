GitHub, remotes and pull requests

GitHub keeps a shared copy of your Git repository online. Learn to push and pull, open pull requests, review code and protect the main branch.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

Git works on your own computer. To work with a team, you need a shared copy of the repository that everyone can reach. GitHub is a website that hosts that shared copy. GitLab and Bitbucket are similar services.

The shared copy is called a remote, usually named origin. You push your commits to it and pull other people's commits from it.

To add your work to main, you open a pull request, or PR. A pull request says "please merge my branch". Teammates read the changes, comment and approve. Automatic tests also run. Then someone merges it.

Think of it like this

Your laptop has your notebook. GitHub has the class notebook on the wall. You copy your new pages to the wall notebook. Before a page goes into the main chapter, the class reads it and agrees.

Press Next or Play. Each step lights up one part and moves the requests. Arrow keys move steps after you click the diagram.

Words you need

Remote
Another copy of the repository, usually on GitHub, named origin.
Clone
Download a full copy of a remote repository, with all history.
Push
Upload your commits to a remote.
Fetch
Download new commits from a remote without changing your files.
Pull
Fetch, then merge the new commits into your branch.
Pull request
A request to merge one branch into another, with review and checks. GitLab calls it a merge request.
Fork
Your own copy of someone else's repository on GitHub, used to contribute to projects you cannot push to.
Branch protection
Rules that stop direct pushes to main and require reviews and passing checks.
CODEOWNERS
A file that names who must review changes to each part of the code.

How it works

Commands you use with a remote

git clone https://github.com/team/shop.git
git switch -c fix-login
# edit, add, commit
git push -u origin fix-login   # first push of a new branch
git pull                        # get new commits on your branch
git fetch                       # look at what changed without merging

How a good pull request looks

  1. Small. Under about 400 changed lines is much easier to review.
  2. A clear title and a description of what and why.
  3. Linked to an issue or ticket.
  4. All automatic checks pass.

Three ways to merge a pull request

WayResult on main
Merge commitAll branch commits plus one merge commit
Squash and mergeOne new commit with all the changes
Rebase and mergeThe branch commits replayed on main, no merge commit

Protect main

In the repository settings, add a branch protection rule or ruleset for main. Require a pull request, at least one approval and passing status checks. Block force pushes. Now nobody, by mistake or on purpose, can break main without review.

Key point

Code review is not only about bugs. It spreads knowledge, so more than one person understands each part.

Real life scenarios

Open source contributions

You cannot push to a famous open source project. You fork it, push to your fork, and open a pull request to the original. The maintainers review it.

A Friday push to main

A developer pushed straight to main on a Friday evening and broke the site. After that, the team turned on branch protection with required checks.

Trade-offs

ChoiceGood atCosts you
Squash and mergeClean main history, one commit per change.Loses the small steps inside the branch.
Merge commitFull history.Busier history.
Required reviewsFewer bugs, shared knowledge.Changes wait for a reviewer.

Common mistakes

  • Huge pull requests that nobody can review well.
  • Approving without reading.
  • Pushing straight to main without protection.
  • Forgetting to pull before starting new work, so the branch starts from old code.

Security lens

GitHub is part of your supply chain.

  • Require MFA for everyone in the organization.
  • Use branch protection and CODEOWNERS so sensitive files need the right reviewers.
  • Turn on secret scanning and push protection, and Dependabot alerts.
  • Review third party GitHub apps and their permissions. Give the least access.
  • Use fine grained personal tokens with expiry instead of classic tokens.
