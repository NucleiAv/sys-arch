Shipping safely, rolling, blue green, canary and GitOps

Most outages start with a change. Learn the deploy strategies that limit the damage of a bad release, how feature flags separate deploy from release, and how GitOps keeps clusters in sync with Git.

The idea in one minute

A deploy puts new code on servers. A release shows the new behavior to users. Good teams keep these two apart, so they can deploy often and release carefully.

There are a few main ways to deploy.

  • Rolling. Replace servers a few at a time.
  • Blue green. Run the new version next to the old one, then switch all traffic at once. Switch back if needed.
  • Canary. Send a small share of traffic, such as 5 percent, to the new version. Watch the metrics. Increase step by step.

GitOps means the desired state of your system lives in Git, and a tool in the cluster keeps the cluster equal to Git.

Think of it like this

A canary deploy is like tasting a new recipe with five friends before you serve it at a party of a hundred. If the five friends make a face, only five people had a bad bite.

Words you need

Deploy
Putting a new version on servers.
Release
Turning the new behavior on for users.
Rolling update
Replacing instances a few at a time.
Blue green
Two full environments. Switch traffic from blue to green at once, and back if needed.
Canary
Sending a small share of traffic to the new version first.
Feature flag
A switch in the code that turns a feature on or off without a deploy.
Rollback
Going back to the previous version.
GitOps
Git holds the desired state. An agent in the cluster pulls it and applies it.
Expand and contract
Changing a database in steps, add the new thing, move to it, then remove the old thing, so old and new code both work.

How it works

Compare the strategies

StrategySpeed of rollbackExtra costRisk during deploy
RollingMedium, roll forward or back againLowTwo versions run at once
Blue greenVery fast, switch backDouble capacity for a whileAll users switch at once
CanaryFast, shift traffic backLowSmall share of users affected

Feature flags

if flags.enabled("new_checkout", user):
    return new_checkout(cart)
return old_checkout(cart)

Deploy the code with the flag off. Turn it on for staff, then 1 percent of users, then everyone. If something breaks, turn the flag off in seconds, without a deploy. Remove old flags after the release, or the code fills with dead branches.

Database changes without downtime

Old and new code run at the same time during a rollout. So database changes must work with both.

  1. Expand. Add the new column. Old code ignores it.
  2. Migrate. New code writes both columns. Copy old data across.
  3. Contract. When no old code is left, stop using the old column, then drop it.

GitOps

repo: deploy-config
  apps/shop/values-prod.yaml   image: shop:1.5

A tool like Argo CD or Flux runs in the cluster. It watches this repository. When you merge a change to the image tag, it pulls the change and applies it. If someone edits the cluster by hand, it notices the difference and puts it back. Git is the single source of truth, and its history is your audit log.

Key point

Deploy small changes often. A small change is easy to understand, easy to test and easy to roll back.

Real life scenarios

A canary that saved a launch

A team rolled out a new search version to 5 percent of users. Latency doubled for that group. The automatic analysis rolled it back within minutes, and most users never noticed.

The column that broke the old pods

A deploy renamed a database column. Old pods, still running during the rolling update, failed on every request. The team switched to expand and contract migrations.

Trade-offs

ChoiceGood atCosts you
RollingSimple, built into Kubernetes.Slower rollback, mixed versions.
Blue greenInstant switch and switch back.Double infrastructure during the switch.
CanaryLimits damage, real traffic tests.Needs good metrics and traffic splitting.

Common mistakes

  • Deploying large changes rarely.
  • No automatic rollback based on metrics.
  • Database changes that break the old version.
  • Leaving hundreds of old feature flags in the code.
  • Hand editing production while GitOps keeps reverting it.

Security lens

Deployment is a security moment.

  • Deploy only signed, scanned artifacts that came from your pipeline.
  • Canary and staged rollouts limit the damage of a bad or malicious change.
  • GitOps gives an audit trail, every change is a reviewed commit.
  • Keep a fast rollback path for security fixes that break things, and a fast path to ship urgent patches.
