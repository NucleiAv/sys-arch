Docker images and containers

The old excuse "it works on my machine" stops when you ship the machine too. Learn images, containers and how to write a small, safe Dockerfile.

The idea in one minuteWatch it, step by stepWords you needHow it worksReal life scenariosTrade-offsCommon mistakesSecurity lensPractice. Check yourselfPractice. Interview questionsPractice deskGo deeper

The idea in one minute

An app needs more than its code. It needs the right language version, libraries and settings. If a server has slightly different versions, the app breaks.

Docker packs the app and everything it needs into an image. An image is a read only template made of layers. When you run an image, you get a container, a running, isolated process with its own files, network and limits.

Containers are not virtual machines. A virtual machine has its own full operating system. A container shares the host's Linux kernel, so it starts in under a second and uses little memory.

Think of it like this

An image is a recipe plus all the ingredients in a sealed box. A container is the dish you cook from it. You can cook many identical dishes from one box, in any kitchen.

Words you need

Image
A read only package of an app and everything it needs, made of layers.
Container
A running instance of an image, isolated from other processes.
Dockerfile
A text file with instructions to build an image.
Layer
One step of an image. Layers are cached and shared between images.
Registry
A server that stores images, such as Docker Hub, GitHub Container Registry or Amazon ECR.
Tag
A name for an image version, such as shop:1.4.
Volume
Storage that lives outside the container, so data survives when the container is removed.
Multi-stage build
A Dockerfile with several stages, where the final image copies only what it needs from earlier stages.
Namespaces and cgroups
Linux features that isolate what a container sees and limit how much CPU and memory it uses.

How it works

A good Dockerfile for a Node.js app

# stage 1, build
FROM node:22-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# stage 2, run FROM node:22-slim WORKDIR /app ENV NODE_ENV=production COPY package*.json ./ RUN npm ci --omit=dev COPY --from=build /app/dist ./dist USER node EXPOSE 3000 CMD ["node", "dist/server.js"] ```

Why this order? Docker reuses cached layers until one changes. Package files change rarely, code changes often. So copy the package files and install first. Then a code change does not reinstall every package.

The commands you use most

CommandWhat it does

docker run -d -p 8080:3000 name:tagRun in the background, map host port 8080 to container port 3000
docker psList running containers
docker logs -f idFollow a container's output
docker exec -it id shOpen a shell inside a running container
docker stop idStop a container
docker run -v data:/var/lib/data ...Keep data in a named volume
docker run -e DATABASE_URL=... ...Pass an environment variable

Rules for good images

  1. Start from a small, official base image, such as a slim or alpine variant.
  2. Use multi-stage builds, so build tools do not ship.
  3. Run as a normal user with USER, not as root.
  4. Add a .dockerignore file so node_modules, .git and .env stay out.
  5. Never bake secrets into an image. Pass them at run time.
  6. Tag images with a version or commit hash, not only latest.
Key point

EXPOSE only documents the port. It does not open it. You publish ports with -p when you run the container.

Real life scenarios

The 2 GB image

A team copied the whole project folder, including node_modules and test data, into the image. It was 2 GB and slow to deploy. A .dockerignore file and a multi-stage build made it under 200 MB.

The secret inside an image

A developer copied .env into an image and pushed it to a public registry. Anyone could pull the image and read the database password. Secrets must come from the environment at run time.

Common mistakes

  • Running containers as root.
  • Secrets inside images.
  • Copying everything before installing packages, which breaks the cache.
  • Storing data inside the container instead of a volume.
  • Deploying latest and not knowing which version is live.

Security lens

Containers are not a security boundary by default. Harden them.

  • Use small base images, like distroless or alpine, so fewer packages can have bugs.
  • Run as a non root user with the USER line.
  • Scan images for known vulnerabilities, with tools like Trivy or Grype.
  • Never put secrets in the image or in ENV lines. They stay in the layers.
  • Pin base images by digest, and sign images, for example with cosign.
